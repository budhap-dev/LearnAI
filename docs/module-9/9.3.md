## The one idea

"How slow is the model?" has no single answer, because a response time is two numbers added
together:

```diagram
latency-waterfall
```

- **Time to first token (TTFT):** queue time plus reading the prompt. Grows with *input* size.
- **Generation:** output tokens divided by the model's tokens-per-second. Grows with *output*
  size.

They have different causes and different fixes, so you tune them separately:

```code
model
```

```output
two-numbers
```

Output dominates the total; the prompt dominates the TTFT. A long answer is slow no matter how
short the prompt; a huge prompt delays the first token no matter how short the answer.

## Report percentiles, not the mean

Real traffic has a heavy tail — most requests are small, a few are large — so the mean is a
number no user experiences:

```code
percentiles
```

```output
percentiles
```

The mean sits around the common case and hides the heavy requests entirely; the **p95 and
p99** are the experience of your worst-served one-in-twenty and one-in-hundred requests, and
that is what an SLO is written about. "Average latency is fine" is the sentence that precedes
every latency incident. Alert on the tail, not the mean (9.8).

## Streaming changes which number the user feels

The total work is unchanged, but streaming hands the user the first token the moment TTFT
ends, so what they *feel* is TTFT — often ten times smaller than the total:

```output
streaming
```

Same requests, same total generation time, but the perceived-latency percentile drops from
seconds to a fraction of a second. This is the single biggest latency UX win available, and
it costs nothing in quality (Lesson 5.2). If a human is waiting on a multi-sentence answer,
stream it.

## Throughput is a different axis

Latency is "how long one request takes"; throughput is "how many per second you can serve".
They are related but not the same — you can have low latency and low throughput (one fast
request at a time) or high throughput and high latency (huge batches):

```output
throughput
```

To serve more requests you raise concurrency (which needs the provider to grant you the rate
headroom), shorten outputs, or move unwatched work to batch (5.5) — not the same levers as
making one request faster.

## The levers, in order of effect

```output
levers
```

```check
Users complain your assistant "feels slow", though your dashboard shows a healthy 4-second mean total latency. What is the first thing to check and the first fix to try?
- Buy a faster model
- * Check the p95/p99 (the mean hides the tail), and turn on streaming so users feel TTFT (~sub-second) instead of the full total — no quality cost
why: The mean hides the tail, and "feels slow" is usually time-to-first-token. Streaming and the percentile view address both before any model change.
```

```check
A summarisation endpoint returns a 1,500-token summary and is too slow. The prompt is small. Which lever helps most?
- Shrink the prompt
- * Shorten the output — total latency scales with output tokens, so cap length / ask for a terser summary; the small prompt is not the bottleneck
why: Generation time dominates total and scales with output tokens. TTFT (prompt) is already small here, so output length is the lever.
```

## What a senior engineer should take from this

- **Latency = TTFT + generation.** Prompt size moves TTFT; output size moves generation;
  tune them separately.
- **Stream anything a human waits on** — it moves the felt latency to TTFT for free.
- **Report p95/p99, never the mean.** The tail is the SLO; the mean is where incidents hide.
- **Throughput is a separate axis** with separate levers (concurrency, batching, shorter
  outputs).

## Exercises

1. Instrument one of your endpoints (or reason about it) to emit TTFT and total per request.
   What is the p95 of each, and which is your users' actual complaint?
2. Your p99 total is 25s because of a 5% tail of long-context requests. Give three ways to
   pull the tail in without slowing the common case.
3. Streaming a tool-calling agent (7.2) is harder than streaming a single answer. Why, and
   what can you still stream to keep the UI alive?
4. Write the latency section of an SLO for a chat feature: which percentile of which number,
   at what threshold, and what happens when it is breached?

## Model answers (sketch)

1. Usually TTFT is the complaint for chat (felt), total for batch jobs; measure both, because
   the fix differs.
2. Route long-context requests to a faster/cheaper path, cap max input (retrieve less, 2.5),
   or handle them async so they do not block the interactive path.
3. The agent's latency is many round trips; you cannot stream the final answer until the loop
   ends, but you can stream *progress* (which tool it is calling, partial reasoning) to keep
   the user informed.
4. e.g. "p95 TTFT < 800ms and p95 total < 6s for chat; breach pages on-call and triggers the
   latency runbook (9.8)."
