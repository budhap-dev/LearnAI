## The one idea

You have now built every piece of a production LLM feature across Modules 4–8. This lesson
assembles them into the shape they almost always take, so you can draw it from memory and
use it as a checklist against any real design:

```diagram
reference-architecture
```

The single most important thing this picture says: **the model is one box.** A demo is the
model box and a prompt. A production system is the *other twelve* — and that is where the
reliability, the safety, the cost control and the ability to change vendors live.

## The boxes, and the lesson each one is

| Box | Responsibility | Where you learned it |
|---|---|---|
| **Client** | a user or a job originates a request | — |
| **Gateway** | the one service holding keys; auth, per-tenant quotas, rate limits, routing, fallback, the first log line | 9.2 |
| **Orchestration** | the control flow: a single call, a workflow, or an agent loop with budgets | 7.1, 7.2 |
| **Retriever** | moves the facts the answer needs into the prompt, with citations | Module 6 |
| **Tools** | lets the model act, under least privilege, with consequential actions gated | 7.3, 7.6 |
| **Guardrails** | input and output checks in code that the model cannot talk past | 9.7 |
| **Model** | turns context into a distribution — reached only through the gateway | Module 2, 5 |
| **Tracing / evals / cost** | cross-cut every box: every request traced, every change eval-gated, every call costed | 5.7, Module 8, 9.4 |

## Reading a design against the shape

The architecture is most useful as a *gap finder*. Put any proposed LLM feature next to it
and ask, box by box, "where is this?":

- No **gateway**? Then keys are in application code, one tenant can starve the rest, and
  swapping models is a code change (9.2).
- No **guardrails** box? Then the model's output acts on your system unchecked — the naive
  refund tool from 7.3, at scale (9.5, 9.7).
- No **tracing/evals** band? Then you cannot tell a fix from a regression, or reconstruct an
  incident (Module 8, 9.8).
- **Retriever** missing on a feature that answers from private or fresh data? Then it is
  hallucinating instead of retrieving (Module 6).

Most production incidents you will read about are a missing box on this diagram, not a bad
model.

```check
A team demos an LLM support assistant: a prompt, a model call, and the answer shown to the user. Against the reference architecture, name the two most dangerous missing boxes.
- Retriever and orchestration
- * Guardrails (output acts on/reaches the user unchecked) and gateway (no keys isolation, quotas, routing, or tracing)
- Tools and client
why: The demo has the model box and nothing that makes it safe or operable. Guardrails and the gateway (with its tracing) are what stand between a demo and a system.
```

## Why it is always roughly this shape

The shape is not fashion; it falls out of Module 2's facts. The model is a stateless,
probabilistic next-token function with a knowledge cutoff. Everything around it exists to
compensate for exactly those properties:

- **stateless** → orchestration and memory re-send context (7.5);
- **probabilistic** → guardrails and evals check what comes out (8, 9.7);
- **cutoff / no private data** → retrieval puts facts in (Module 6);
- **can't act** → tools, under least privilege (7.3);
- **metered, versioned, vendor-specific** → a gateway isolates and controls it (9.2).

Change the model and the boxes stay; that is the point of the shape. It is also why "we'll
just call the API" is never the whole design — the API is one box.

```check
Your company wants to switch LLM vendors. In the reference architecture, how much of the system should that change touch?
- Most of it — the vendor is central
- * Almost none — only the gateway's routing config; the model is one box behind it, which is why the gateway exists
why: Isolating the vendor behind the gateway is precisely what makes the switch a config change instead of a codebase-wide edit (9.2).
```

## What a senior engineer should take from this

- **The model is one box; the system is the other twelve.** Reliability, safety, cost and
  vendor-independence live in the boxes around it.
- **Use the shape as a gap finder** — read any design box by box and name what is missing.
- **The boxes exist because of Module 2's facts** (stateless, probabilistic, cutoff, metered)
  — so they survive a model change.
- **A demo is the model box and a prompt.** The rest of Module 9 builds the boxes that make
  it production.

## Exercises

1. Draw the reference architecture from memory, then annotate each box with the specific
   technology your team would use for it. Which box is least defined? That is your design risk.
2. Take a real LLM feature (yours or a described one) and mark each box as present / partial /
   missing. What is the single most dangerous gap?
3. For a feature that is *just* "prompt → model → show answer", list every box it is missing
   and the failure each omission invites.
4. Argue the case for the gateway to a skeptical colleague who says "it's just an HTTP call —
   why add a service?". Use the vendor-switch and multi-tenant arguments.

## Model answers (sketch)

1. Usually the retriever or the evals band is least defined; whichever you cannot name a
   concrete implementation for is where the design is hand-wavy.
2. Common worst gap: no output guardrails (the model's answer reaches users or acts on data
   unchecked) or no evals (changes ship blind).
3. Missing gateway (keys, quotas, tracing), guardrails (unchecked output), retriever (if it
   needs private/fresh facts), evals (blind changes) — each maps to a Module 9/8 failure.
4. The gateway isolates keys (security), enforces per-tenant quotas (fairness), routes and
   fails over (reliability), and makes the vendor a config value (portability) — none of which
   an inline HTTP call gives you.
