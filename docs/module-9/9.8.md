## The one idea

Shipping is the middle of the story, not the end. A production LLM feature is a system you
*operate* — and operating it means the same disciplines as any service, plus two that are
specific to models: quality drifts even when nothing in your code changed, and the vendor will
one day deprecate the model you depend on. Everything in this lesson assumes the trace (5.7),
the gateway (9.2) and the evals (Module 8) you already built; operations is where they pay off.

## SLOs: promise the numbers that matter

An SLO is a written promise about a measurable signal. For an LLM feature, the signals are not
just uptime:

| Signal | Example SLO | From |
|---|---|---|
| **Latency** | p95 TTFT < 800ms, p95 total < 6s | 9.3 |
| **Quality** | grounded-answer rate ≥ 90% on the online sample | 8.5 |
| **Guardrail** | validation-pass rate ≥ 99%; zero critical-slice breaches | 8.6, 9.7 |
| **Cost** | cost/request within X% of baseline | 9.4 |
| **Availability** | successful-response rate ≥ 99.9% (incl. fallback) | 9.2 |

The rule from 9.3 holds across all of them: **alert on the tail and the rate, not the mean.**
A quality SLO on the *mean* answer hides the slice that regressed; a latency SLO on the mean
hides the tail users actually feel.

```check
Your only alert is "error rate > 1%". Over a week, users increasingly escalate to human agents, but no alert fires. What SLO was missing?
- None — error rate is the right signal
- * A quality SLO: the feature was returning successful-but-worse answers (a silent quality regression), which an error-rate alert cannot see; watch grounded-answer rate / escalation rate (8.5)
why: LLM features fail by returning fluent wrong answers, not errors (2.8). Quality and escalation signals catch what an error-rate SLO cannot.
```

## The incident playbook

When an SLO breaks, the trace makes the investigation a checklist, not a guess (this is the
9.1 architecture and 5.7 trace paying off). Work it in order:

1. **Which versions were live?** Prompt, model, retrieval index, artefact — and were they what
   you evaluated? A silent vendor model bump is the classic cause (below).
2. **What did the model actually receive?** From the trace: the prompt, retrieved sources, tool
   results, tokens per part, whether context was truncated (2.5).
3. **What checked the output — and why didn't it catch this?** The guardrails and validation
   (9.7). A gap here is often the real defect.
4. **Which source did the failure come from** — model, input, system, or organisation (1.6's
   taxonomy)? That tells you where the fix lives.
5. **Would the golden set have caught it?** If not, the incident becomes a new golden case
   (8.2, 8.5) — so it can never ship again.

The single most useful sentence in an AI incident is "here is exactly what the model
received", and you can only say it if you traced it.

```check
Answers suddenly got worse overnight; your code, prompts and index are unchanged. What is the most likely cause and the first check?
- The users changed
- * The vendor rolled the model version under you; check which model version the trace records vs what you evaluated, and pin/roll back while you re-run the eval gate
why: A floating model version changes behaviour with no deploy on your side (9.2's pinning). The trace's recorded version is the first thing to check.
```

## Drift and deprecations — the two model-specific certainties

- **Drift.** Even with everything pinned, the *world* changes: users ask new things, your
  documents update, the input distribution shifts (3.5's drift, now in production). Watch it
  with the online signals (8.5) — a rising escalation rate or falling grounded-answer rate is
  drift talking — and feed every miss back into the golden set. A golden set that is not
  growing is a feature slowly going out of date.
- **Deprecations.** The vendor *will* retire the model you use. Because it is pinned behind the
  gateway (9.2), you control the migration: when the successor ships, add it to the routing
  config for a canary, run the eval gate (8.4) against it, and shift traffic as the numbers
  hold — a rollout ladder (8.5), not a forced flag-day. "Our model is being deprecated next
  month and we've never evaluated the replacement" is a preventable emergency.

## Change management: prompts and models are code

The through-line of the whole course: a prompt, a model version, a retrieval index and a
guardrail are **versioned, tested, rollback-able artefacts** (4.4, 8.4, 9.2). Changing any of
them is a deploy, gated on evals, logged with the trace, and reversible in one step. Operating
an LLM feature is not a new discipline — it is your existing change-management and on-call
discipline, applied to a component that happens to be probabilistic and whose "correct" is a
rate, not an assertion.

```check
A product manager wants to tweak the system prompt directly in production "to fix a phrasing issue" without a deploy. Why push back, and what is the right path?
- Let them — it's just a prompt
- * A prompt is code: the change must be versioned (4.4), pass the eval gate (8.4), and be rollback-able; an untested live prompt edit can silently regress a behaviour the golden set would have caught
why: Prompts change behaviour like code changes it. The registry + eval gate + trace exist so a prompt edit is a reviewed, reversible, measured deploy — not a hot-patch.
```

## What a senior engineer should take from this

- **Operate it like a service, plus two model specifics:** SLOs on latency, quality,
  guardrails and cost (alert on tail and rate); an incident playbook driven by the trace.
- **The trace is the incident tool** — "here is what the model received" is only sayable if
  you logged it.
- **Drift and deprecation are certainties**, not risks: watch drift with online signals and
  grow the golden set; handle deprecation as a gated rollout because the model is pinned behind
  the gateway.
- **Prompts and models are code** — versioned, eval-gated, rollback-able. Operating the
  feature is your existing discipline applied to a probabilistic component.

## Exercises

1. Write the SLOs for an LLM feature you know: the signal, the threshold, the percentile/rate,
   and what happens on breach. Which one is currently unmeasured?
2. Walk a hypothetical incident ("answers got worse") through the five-step playbook using a
   feature you know. At which step would your current tracing let you down?
3. Your vendor announces your model retires in 60 days. Write the migration plan as a rollout
   ladder with the eval gate. What is the go/no-go criterion at each rung?
4. Design the weekly operations review for the feature: which SLO trends, drift signals, cost
   numbers and incident learnings go on one page for the team.

## Model answers (sketch)

1. The unmeasured one is usually quality or cost-per-request; both need the online sample
   (8.5) and per-feature accounting (9.4) that error-rate dashboards lack.
2. The playbook breaks at step 2 ("what did the model receive?") for teams that log only
   inputs/outputs, not retrieved sources, tokens-per-part and truncation — which is the gap to
   close.
3. Ladder: pin current → shadow the successor on real traffic → canary 5% → A/B → full;
   go/no-go = the eval gate holds (no slice/critical regression) and cost/latency stay in SLO
   at each rung.
4. p95 latency and quality-rate trends, escalation rate (drift), cost/request per feature, open
   SLO breaches, and one incident's golden-case addition — the loop from 8.5 made visible.
