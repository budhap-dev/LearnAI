## The one idea

LLM security is not "make the model refuse bad things" — the model can always be steered
(8.6). It is a set of **structural controls**, one per known risk class, each a property of
how the system is *wired*. The industry's shared list of risk classes is the **OWASP LLM
Top 10**, and a security review is checking, for each one, whether the control that mitigates
it is present:

## Why every control is structural

```output
mindset
```

Walk the mapping and notice the pattern — **not one control is an instruction to the model**:

| Risk | Control | Model can bypass it? |
|---|---|---|
| Prompt injection (LLM01) | fence untrusted input as data (4.6) | no — it is prompt structure + your parsing |
| Insecure output handling (LLM02) | validate output before acting/rendering (4.3) | no — code checks the bytes |
| Sensitive disclosure (LLM06) | no secrets in context; scope data by caller | no — the secret is not reachable to leak |
| Insecure tools (LLM07) | least privilege; propose-only (7.3) | no — the tool's authority is fixed in code |
| Excessive agency (LLM08) | human gate on irreversible actions (7.6) | no — approval is a separate identity |

A prompt line ("never reveal secrets", "only act on authorised requests") is not a control —
it is a request to a system that can be talked out of it. **The secret that is not in the
context cannot be leaked no matter how the model is manipulated.** That is the whole design
principle.

```check
A pen-tester reports: "I couldn't extract the system prompt in 200 attempts." Is that a passing security result for LLM06 (sensitive disclosure)?
- Yes — 0/200 is a strong result
- * No — the control is "no secrets in context", so there is nothing to extract; if the prompt were extractable at all, 0/200 only means this tester didn't find the 201st attack. Fix structurally, don't measure resistance
why: Resistance rates measure the model's luck, not the system's safety (8.6). The control makes extraction impossible (secrets not in context), which is a property you assert, not a rate you hope for.
```

## The review runs in CI

Because the controls are predicates over config, the review is a test. It runs on every
change, so a refactor that removes a control — un-fences an input, widens a tool's scope,
starts logging PII — **fails the build**, the same way the red-team suite (8.6) does. And
mapping each finding to an OWASP LLM id makes coverage auditable: you can show which risks are
covered and which are knowingly accepted, which is what a security sign-off actually requires.

```check
Your feature calls a third-party MCP tool server (7.4) to fetch web pages for the model to summarise. Which OWASP risks does this introduce, and what is the control?
- None — it's just fetching pages
- * LLM01 (fetched pages are untrusted input → fence them) and LLM03 supply chain (the server is third-party code with your credentials → vet, pin, scope, sandbox it)
why: A content-fetching tool is an injection firehose and a supply-chain dependency at once (4.6, 7.4). Both risks have structural controls; neither is solved by trusting the model or the server.
```

## The one-line threat test

```output
boundary
```

For any LLM feature, ask: **"if the model were actively malicious, what could it make my
system do?"** The answer must be bounded by code — least privilege, gates, validation, scoped
data — never by the model's good intentions. If the honest answer is "issue refunds", "read
other tenants' data", or "delete a workspace", you have found your highest-priority control.

## What a senior engineer should take from this

- **Security is a control per risk, in code** — a property of the system, not an instruction
  to the model.
- **Map to the OWASP LLM Top 10** so coverage is auditable; encode the mapping as a CI check
  so a removed control fails the build.
- **Structural beats resistant:** the secret not in context cannot leak; the ungated action
  cannot fire. Design the harm out, don't measure how often it happens.
- **The threat test:** if the model were malicious, what could it make the system *do*? Bound
  that answer in code.

## Exercises

1. Run the executable review against a feature you know: which controls are open? For each,
   name the code change that closes it and the OWASP id it maps to.
2. Extend the control set with LLM05 (supply chain of training data) and LLM10 (model theft)

3. Apply the one-line threat test to an agent with a `send_email` and a `run_sql` tool. What
   is the worst a malicious model could do, and which control bounds each?
4. A stakeholder wants to "reduce injection risk with a stronger system prompt". Explain why
   that is not a control and what is, using the fencing + validation + least-privilege stack.

## Model answers (sketch)

1. Commonly open: output validation, data scoping, or PII-in-logs; each closes with a
   specific code change (add a validator, scope the query by caller, add a redactor).
2. Add `training_data_provenance_reviewed` and `weights_access_controlled`; predicates assert
   both true — supply chain and theft are config/process controls, not prompts.
3. `run_sql` malicious → read/write anything: bound with a read-only role scoped to the
   caller; `send_email` → mail anyone: bound with recipient allow-list + propose-only + human
   gate on external sends.
4. A stronger prompt is a request the model can be steered past (8.6). The controls are:
   fence the untrusted text (it cannot act as instructions), validate output before acting,
   and least-privilege tools so a successful injection still cannot do harm.
