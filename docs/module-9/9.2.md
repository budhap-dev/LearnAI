## The one idea

In a real system, no application code calls a model vendor directly. Every call goes through
one internal service — the **gateway** — that owns four things application code should never
touch:

1. **Credentials.** The API keys live in one place, not copied into a dozen services.
2. **Limits.** Per-tenant quotas and rate limits, enforced centrally.
3. **Routing.** Which model handles which task, and what to fall back to when one is down.
4. **The log.** Every call recorded in one place — the start of tracing, cost and audit.

## A tiny gateway

The gateway speaks *one internal interface*; what sits behind it is a detail it hides:

```code
request
```

The core is unglamorous, which is the point — it is boring, central plumbing:

```code
gateway
```

### Routing

Route by task, the way Lesson 5.6 routed by cost: cheap work to a small model, judgement to
a large one. The routing table is *config*, so adding or swapping a model is not a code
change:

```output
routing
```

### Rate limiting — fairness across tenants

Without a central limit, one noisy tenant (or a runaway loop, 7.7) consumes the capacity and
starves everyone else. The gateway caps each tenant:

```output
rate-limit
```

The noisy tenant is throttled at its limit; the quiet tenant is still served. This is
multi-tenant fairness, and it is impossible to enforce if each service calls the vendor
directly.

### Fallback — surviving an upstream outage

Models have outages. A gateway fails over through a preference list automatically, so a
single vendor's bad afternoon is not your outage:

```output
failover
```

The primary was down; the gateway logged the failure, tried the backup, and served the
request — application code never knew.

## What it buys you

```output
why
```

Two of these deserve emphasis for an architect:

**Vendor choice becomes reversible.** Because the vendor lives behind the gateway, switching
or adding a model is a change to the routing config, not a codebase-wide edit (Lesson 9.1's
whole point). This is the difference between "we're evaluating a new model" being a
one-week spike versus a quarter.

**Cost and tracing start here.** The gateway is the one place every call passes, so it is
where you attach the trace (5.7), the token accounting (9.4) and the audit log. Cost you
cannot see per-tenant is cost you cannot control (9.4's showback).

```check
Each of your three services calls the model vendor's SDK directly, with the key in each service's env. What breaks when you need to add a per-customer monthly token budget?
- Nothing — add it to each service
- * There is no single place to enforce it: you'd duplicate the budget logic in three services and still miss any new caller; the gateway is the one chokepoint where a budget can actually hold
why: Cross-cutting policy (budgets, quotas, routing, tracing) needs a single chokepoint. Scattering the model call scatters every policy that depends on seeing all calls.
```

> **For the ADR — and the £0 hosting rule.** The gateway is *your* service (a small
> always-on process), not a per-call serverless function. On the free static-hosting tier
> this course targets, note that adding an Azure Functions API is exactly what moves you off
> the free plan — the gateway belongs in your backend, not bolted onto the static site.

```check
A new model version is released. With a gateway in front, how do you adopt it safely?
- Point production at it immediately
- * Add it to the routing config for a canary slice, run the eval gate (8.4), and shift traffic as the numbers hold — all without touching application code
why: The gateway makes model version a routed config value, so adoption is a controlled rollout (8.5) gated on evals (8.4), not a global switch.
```

## What a senior engineer should take from this

- **One door for every model call.** Keys, quotas, routing/fallback and the first log line
  live there and nowhere else.
- **Routing is config**, so the vendor is a value you change, not code you rewrite — that is
  what makes model choice reversible.
- **Per-tenant limits and fallback** need a single chokepoint; direct SDK calls make them
  impossible.
- **Tracing and cost start at the gateway** — the one place that sees every call.

## Exercises

1. Add a per-tenant *daily token budget* to the gateway (not just requests/minute). What does
   it return when the budget is exhausted, and how does it interact with routing (degrade to a
   cheaper model, or refuse)?
2. The failover list is static. Design health-checking so a repeatedly-failing upstream is
   skipped for a cooldown period rather than tried every request.
3. Your gateway is now a single point of failure for every model call. List three things you
   would do so it does not take the whole product down.
4. Sketch the trace record the gateway emits per call so that cost (9.4), latency (9.3) and
   audit (9.5) all have what they need from one log line.

## Model answers (sketch)

1. Track spend per tenant per day; on exhaustion, either degrade to the cheapest model or
   return 402/429 with a clear reason (5.6's degrade-before-refuse); budget check happens
   before routing.
2. A circuit breaker: after N failures, mark the upstream unhealthy for a cooldown, route
   past it, and probe periodically before restoring it.
3. Run it redundant (multiple instances), keep it thin and stateless so it scales
   horizontally, and make it fail *open to a sensible default route* rather than hard-down.
4. trace_id, tenant, task, chosen model + version, tokens in/out (cached vs fresh),
   latency/TTFT, stop_reason, cost, outcome — one line feeding 9.3/9.4/9.5.
