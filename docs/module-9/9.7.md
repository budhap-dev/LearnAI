## The one idea

A guardrail is a check the model **cannot talk its way past, because it is code, not a prompt
line.** "You must never reveal secrets" in the system prompt is a request; a function that
inspects the output and blocks it if it contains a key is a guardrail. They come in layers:

```diagram
guardrail-layers
```

## A guardrail pipeline

Every request runs input guards → model → output guards, and succeeds only if it passes *all*
of them. Input guards are cheap and run first, so obvious abuse is stopped before you pay for
a model call:

```code
input-guards
```

Output guards are the last line — they run on what the model produced, before it is shown or
acted on:

```code
output-guards
```

The pipeline stops at the first failure, and a blocked *output* escalates to a human rather
than silently vanishing:

## Why layers, and why in code

```output
layers
```

The two-sided structure is the point. **Input guards** save money and catch known-bad before
the model. **Output guards** are the ones that matter for safety: a model that was
successfully injected (8.6) still cannot emit a secret, act without an approval token, or leak
PII — because a function checks the actual bytes on the way out. No single check is
sufficient; defence in depth means several independent layers, in *and* out, so a gap in one
is covered by another.

And a blocked output does not disappear. It **escalates** — a human sees the request and the
reason — because silently dropping a request the user made is its own failure mode (they retry,
or think the product is broken). Every guard is independent and unit-testable, and every one
belongs in the red-team suite (8.6) so a regression that weakens it fails CI.

```check
Your output guard blocks a response because it contains what looks like an API key. What should happen to that request?
- Silently return an empty answer
- * Escalate: log it, show the user a safe "we couldn't complete this" and route it to a human, so a false positive is corrected and a true positive is reviewed
why: Silently dropping loses both the false-positive correction and the true-positive signal. Escalation keeps a human in the loop for exactly the cases a guard flagged.
```

## What is not a guardrail

```output
not-a-guardrail
```

The anti-patterns are worth stating plainly, because they are common and they feel like
security:

- **A system-prompt instruction** ("never do X") — the model can be steered past it (2.6, 8.6).
- **A single check** — one regex, one classifier. Defence in depth is layers, in and out.
- **Trusting the model to self-police** — guardrails exist precisely because the model will
  sometimes fail; they are the seatbelt for the crash you expect not to have.

The layers relate directly to the controls of 9.5: guardrails are where several OWASP controls
(insecure output handling, sensitive disclosure, excessive agency) are *implemented* in the
request path.

```check
A team adds an LLM-based moderation model as their only output guard: it reads each answer and returns block/allow. Why is this necessary but not sufficient?
- It's sufficient — a model judge is the strongest check
- * A model guard can itself be wrong or steered (8.3's judge biases); pair it with deterministic code checks (secret patterns, action-approval tokens, PII regex) so a miss by one layer is caught by another
why: A model-based guard adds valuable judgement but inherits every model failing. Defence in depth pairs it with cheap deterministic checks that cannot be argued with.
```

## What a senior engineer should take from this

- **A guardrail is code in the request path**, not a prompt line — the model cannot talk past
  it.
- **Layers, in and out:** input guards save cost and catch known-bad; output guards are the
  safety-critical last line that a steered model still cannot cross.
- **Blocked requests escalate**, never silently vanish — keep a human on the flagged cases.
- **Defence in depth:** several independent, testable checks, in the red-team suite (8.6), so
  no single gap is fatal.

## Exercises

1. Add a fourth output guard to the example: block answers that make a claim without a
   citation (grounding, 6.6). What does it check, and does it block or escalate?
2. One of your input guards (the injection signature regex) is producing false positives on
   legitimate questions. How do you tune it without opening the hole — and what does the
   red-team suite (8.6) have to say about the change?
3. Design the escalation queue for blocked outputs: what is captured, who reviews it, and how
   a confirmed false positive feeds back into tuning.
4. Which of your guardrails should be deterministic code and which should be a model call?
   Give the trade-off (cost, coverage, reliability) for each.

## Model answers (sketch)

1. Check every factual sentence cites a provided passage id; escalate (not block) so a human
   can catch a genuine miss — false positives here are common, so hard-block would be too
   aggressive.
2. Narrow the pattern, measure the false-positive rate on a labelled set (3.3), and re-run the
   red-team suite to confirm the true attacks are still caught — the suite is the guard against
   loosening it too far.
3. Capture request, output, which guard fired, and the reason; a human reviews; a confirmed
   false positive becomes a test case that tunes the guard down without re-opening the hole.
4. Deterministic for exact things (secret patterns, approval tokens, PII regex) — cheap,
   reliable; a model call for judgement (toxicity, off-topic) — broader coverage, but biased
   and costlier, so pair it with the deterministic layer.
