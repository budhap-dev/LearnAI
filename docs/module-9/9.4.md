## The one idea

An LLM bill feels like weather — something that happens to you. It is not. It is the sum of
four levers you control, each independent and each a percentage off the top:

## The four levers

```output
levers
```

- **Route** (5.6): classification and extraction go to a small model; only judgement-heavy
  work needs the large one. The biggest single lever, and free once your evals (8.4) say the
  small model passes.
- **Cache the prefix** (5.5): a stable-first prompt layout turns the system prompt and
  examples into *cached* input, billed at a fraction. A 90% hit rate on a large stable prefix
  is a large discount for a prompt-layout change.
- **Batch the unwatched**: anything nobody is waiting for — nightly classification,
  backfills, evals — goes to the async batch endpoint at a discount. Free money for work that
  does not need to be interactive.
- **Distil at volume** (10.3): for a high-volume task, a fine-tuned small model can be
  cheaper still and repay its training cost quickly on a hot path.

Same product, ~55% less spend — and not one of these changed what the user sees.

## Showback: cost per feature

The levers cut the total; **showback** stops it climbing back. Attribute cost to the feature
or team that spends it, so cost has an owner:

```output
showback
```

Read that table like an engineer: the interactive **chat** dominates the bill (it is on the
large model, human-waiting so it cannot be batched), while the two high-volume background
tasks are cents. That is the opposite of where a naive "reduce our LLM costs" effort would
look. **Cost per feature tells you where the money actually is** — usually the interactive,
judgement-heavy path, not the high-volume cheap one.

why: Volume and cost are not the same. A few thousand long-context large-model calls can outweigh millions of small-model classifications — showback reveals it, intuition misleads.
```

## Cost-per-request is a metric, and a regression is a bug

The final habit: track **cost per request per feature** continuously and alert on it, exactly
like latency (9.3) or an eval score (8.4). A prompt change that adds 2,000 tokens of examples,
a retrieval change that stops the cache from hitting, a model bump that raises the price — each
is a cost *regression*, and it should fail a gate or page someone, not surface in next month's
invoice.

- * The per-user name makes the prefix vary per request, so it stops being cacheable — 90% of input flips from cached price to full price (5.5)
why: Prompt caching needs a byte-identical prefix. A per-user value anywhere in the stable block breaks the cache for everyone — a classic cost regression a per-request-cost alert would catch.
```

## What a senior engineer should take from this

- **Four levers, each a cut off the top:** route, cache the prefix, batch the unwatched,
  distil at volume. Route first.
- **Showback gives cost an owner** and reveals that the interactive judgement path — not the
  high-volume cheap one — usually dominates.
- **Cost per request is a metric**; a rise is a regression to gate and alert on, not an
  invoice surprise.
- **None of the levers touch the product** — same answers, less spend.

## Exercises

1. Estimate your own (or a described) workload's baseline cost, then apply the four levers in
   order. Which moved your bill most, and does that match where you expected?
2. In the showback table, the chat path is the whale. List three ways to cut it specifically
   (not the cheap background tasks) and the eval you would run before each.
3. Design the cost-regression gate: what per-request-cost change on which feature should fail
   CI, and what should merely alert?
4. When does distillation (10.3) pay for itself? Reason about training cost vs per-request
   saving at a given volume.

## Model answers (sketch)

1. Routing is almost always the biggest lever; caching is next when the stable prefix is
   large. If the workload is one big interactive model, routing may not apply and caching
   dominates.
2. Route the easy chat turns to a smaller model (measure quality, 8.4), cache the system
   prompt harder, and cap output length (9.3) — each gated on the golden set.
3. Fail on a >X% cost-per-request rise vs baseline on a hot-path feature; alert on smaller
   drifts and on cache-hit-rate drops (the early warning).
4. Distillation pays when (training cost) < (per-request saving × volume over the model's
   life); high-volume, stable tasks cross that line fast, low-volume ones never do.
