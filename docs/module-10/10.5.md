## The one idea

Everything in Module 6 rode on one assumption: that texts which *mean* the same thing land
*near* each other in vector space. That is the embedding model's job, and **a general embedding
model does not know your domain.** When your users phrase a question differently from how your
passages are written — house jargon, codenames, terse tickets — the right passage can sit
second or third, and no reranker downstream recovers what retrieval failed to surface.

There are two fixes: **pick a stronger base model**, or **adapt** one to your domain using
`(query, relevant-passage)` pairs so the things that should match move closer. And one rule
governs both: **measure the gain on a held-out set** — training-set gains are a mirage.

## Choosing the base model first

Before adapting anything, choose the base well — a stronger base often beats adapting a weak one
and is far less work. The axes that matter:

- **Domain and language coverage** — was it trained on text like yours? This dominates retrieval
  quality and is exactly what a general model lacks for a specialised corpus.
- **Dimension** — more dimensions can carry more nuance but cost more storage and compute per
  vector; it is a quality/cost trade, not "bigger is better."
- **Cost and latency** — you embed the whole corpus once and every query forever; the per-vector
  cost compounds.
- **Max input length** — it must comfortably hold your chunks (6.3).

## Adapting to your domain

When the base still misroutes, adapt it. Real embedding fine-tuning trains the model on your
`(query, passage)` pairs with a contrastive objective — pull matches together, push
non-matches apart. The example does a light-weight, deterministic cousin of that idea: it nudges
each passage toward the centroid of the training queries that should hit it (the same intuition
as attaching generated queries to a passage — "doc expansion"). The corpus is house-style,
jargon-y support docs; the eval queries are the plain language users actually type:

```code
corpus
```

The adapter is fit on a handful of labelled pairs and its strength is tuned by **leave-one-out
on the training pairs** — never on the eval set:

```code
adapt
```

## Measure on a held-out set — the only number that counts

First, the baseline. A general model, no adaptation, scored on the held-out queries:

```output

```

Several plain-language queries miss — the right passage is there, but at rank 2, behind a
lexical near-neighbour. Now fit the adapter on the training pairs and re-measure on the *same*
held-out eval:

```output
gain
```

The gain is real: held-out **recall@1 rises from 5/8 to 7/8 and MRR from 0.81 to 0.94**, from
just sixteen labelled pairs.

```diagram
embedding-adaptation
```

Two things are worth naming honestly. First, one query *still* misses — "refresh the API
tokens" collides with a passage about API rate limits, a jargon overlap a light adapter can't
resolve. **The gain is real but bounded: adaptation aligns a domain, it does not fix a wrong
base model.** Second — and this is the whole discipline — the numbers that count are on the
**held-out** set. On the training pairs the adapter looks perfect, because it was fit to them;
that number tells you nothing about new queries.

```check
After adapting your embeddings, training-set recall@1 is 100% but held-out recall@1 is 78%. Which number do you report, and why?
- 100% — it's the model's best measured performance
- * 78% — the held-out number, because the adapter was fit on the training pairs, so its score there is circular. Only performance on queries it never saw estimates real-world retrieval
- The average of the two
why: The adapter is optimised on the training pairs, so training-set accuracy is guaranteed-optimistic and measures memorisation, not generalisation. Held-out performance is the honest estimate; reporting the training number is the classic evaluation error (8.4).
```

## The operational catch: re-embed everything

Changing or adapting the embedding model changes the vector space. A query embedded with the
new model and a corpus embedded with the old one are **not in the same space**, and cosine
similarity between them is meaningless. So whenever you change or adapt the model, you must
**re-embed the entire corpus** — a real cost to budget, and a real migration to sequence (you
can't do it half-and-half). It is the embedding equivalent of a schema migration.

```check
You fine-tune your embedding model and deploy it for query embedding, but leave the existing corpus vectors (embedded with the old model) untouched to save the re-embedding cost. What happens?
- Retrieval improves for the adapted queries
- * Retrieval breaks — query vectors from the new model and document vectors from the old model live in different spaces, so their cosine similarities are meaningless. You must re-embed the whole corpus with the new model
- Nothing changes; embeddings are interchangeable
why: A similarity score only means something when both vectors come from the same model. Mixing an adapted query encoder with an un-adapted corpus compares vectors across incompatible spaces. Changing the model forces a full corpus re-embed.
```

## What a senior engineer should take from this

- **Retrieval quality is capped by the embedding model** — if meaning-equal texts aren't
  near, nothing downstream recovers it.
- **Choose the base first** on domain/language coverage, dimension, and cost; a stronger base
  often beats adapting a weak one.
- **Adapt on `(query, passage)` pairs from your traffic** for a real but bounded gain —
  measured on a **held-out** set with recall@k / MRR, never on the training pairs.
- **Changing the model means re-embedding the whole corpus** — query and corpus must share one
  space; budget it like a migration.

## Exercises

1. In the example, add more training pairs for the one query that still misses. Does the
   held-out result improve, or is this a base-model limit? How would you tell the difference?
2. You must choose between a 384-dim general model and a 1024-dim one for a 2-million-chunk
   corpus. List the costs each imposes and the evidence you'd gather before deciding.
3. Design the held-out eval for an embedding change: where the `(query, relevant-doc)` pairs come
   from, how many you need, and which metrics gate the rollout (6.7).
4. Write the runbook for swapping in an adapted embedding model in production: the re-embedding
   step, how you avoid a mixed-space window, and how you'd roll back.

## Model answers (sketch)

1. If more pairs fix it, it was a data gap; if it plateaus below rank 1 no matter the data, it's
   a base-model limit (the jargon collision), and the fix is a stronger/domain base, not more
   adaptation. The held-out curve flattening tells you which.
2. 1024-dim costs ~2.7× the storage and more compute per query and per corpus embed (×2M
   chunks); 384-dim is cheaper but may lose nuance. Gather held-out recall@k for both on your
   own labelled pairs before paying for the larger one.
3. Pairs from click logs / annotation on real queries; enough to be representative per query
   type (tens to low hundreds); gate on held-out recall@k and MRR beating the current model by a
   margin that clears noise.
4. Re-embed the corpus with the new model into a *separate* index, switch query and corpus reads
   to the new index atomically (never mix spaces), keep the old index warm, and roll back by
   flipping reads back if eval or live metrics regress.
