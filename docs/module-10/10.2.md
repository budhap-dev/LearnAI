## The one idea

Fine-tuning is not a new mechanism. It is **the training loop you already saw in Lesson 1.2 —
forward, loss, gradient, step — run on your examples instead of the internet.** Supervised
fine-tuning (SFT) shows the model `(prompt, ideal completion)` pairs and nudges its weights so
its output moves toward the ideal. The only questions are *which* weights you're allowed to
move, and how you keep it from memorising.

**Full fine-tuning** moves every weight. It fits best, but it trains and stores a whole copy of
the model per task — expensive to run and to keep. **LoRA (low-rank adaptation)** freezes the
base and trains a small add-on:

```diagram
lora-adapter
```

## LoRA, concretely

A model is thousands of weight matrices. LoRA freezes each one (call it `W₀`) and learns a
low-rank *update* `ΔW = B·A`, where `B` is `d×r` and `A` is `r×d` for a small rank `r`. The
effective weight at inference is `W₀ + B·A`. Because `r` is tiny, the trainable parameters drop
from `d×d` to `r·(d+d)` — and `W₀` never changes, so one frozen base can host many adapters,
each a small file you swap per task.

The frozen base doesn't solve the domain task on its own. Full fine-tuning drives the loss
down by moving every weight. LoRA gets *close* — at an adequate rank — while training a small
fraction of the parameters and leaving the base untouched. The gap between them narrows as you
raise the rank; the trade is quality against adapter size.

## Why this matters at real sizes

The toy layer is `4×6`. Real layers are thousands on a side, and there are hundreds of them:

```output
scale
```

That factor is the whole point. A `4096×4096` layer has ~16.8M weights to train in a full
fine-tune; a rank-8 LoRA adapter for it has ~65K — **256× fewer** — and there are hundreds of
such layers. LoRA is what turns a fine-tune from a GPU-cluster job into something you can run
on a single GPU, and it's why "parameter-efficient fine-tuning" (PEFT) is the default way teams
actually adapt models.

```check
Why can one organisation cheaply serve twenty different LoRA-fine-tuned variants of the same base model?
- Because LoRA models are smaller and each fits in less memory
- * Because every adapter shares one frozen copy of the base weights; each variant is just a small B·A adapter you load on top, so twenty variants cost one base plus twenty tiny adapters
- Because LoRA variants don't need a GPU to run
why: LoRA freezes the base, so all adapters share it. You store one base plus many small adapters and swap them per request — you are not storing twenty full models.
```

## The levers that decide a fine-tune

```output
rules
```

- **Data format and quality.** SFT data is `(prompt, ideal completion)` pairs. Consistency
  beats volume — a few hundred clean, consistent examples beat thousands of noisy ones, because
  the model learns exactly what you show it, contradictions included.
- **Rank (for LoRA).** Higher rank fits better and costs more parameters; low rank is cheaper
  and can underfit. It is the main dial, and you pick it on the eval, not by feel.
- **Overfitting is the risk.** Too many epochs on too little data and the model memorises the
  training set and gets *worse* on anything new. You catch this only with a **held-out eval
  set** (3.3): watch train loss keep falling while held-out quality plateaus then drops — that
  divergence is overfitting, and it's why the eval is not optional.
- **Behaviour, not facts.** Fine-tune for format, tone, domain style (10.1); for facts,
  retrieve (6.1). This is worth repeating because it is the most common way a fine-tune is
  wasted.

```check
During a LoRA fine-tune, training loss keeps dropping but held-out accuracy peaks at epoch 3 and declines after. What is happening, and what do you do?
- The learning rate is too low; train longer
- * Overfitting past epoch 3 — the model is memorising the training set. Stop at the best held-out checkpoint (early stopping), and/or reduce epochs, lower the rank, or get more data
- The held-out set is wrong; trust the training loss
why: Falling train loss with falling held-out accuracy is the textbook overfitting signature. The held-out set is exactly what catches it; you keep the checkpoint where held-out quality peaked, not where train loss is lowest.
```

## What a senior engineer should take from this

- **SFT is the 1.2 training loop on your `(prompt, completion)` pairs** — nothing more exotic.
- **LoRA freezes the base and trains a low-rank adapter**, cutting trainable parameters by
  orders of magnitude and giving you small, swappable artefacts over one shared base.
- **Data quality and consistency beat quantity**; rank is the LoRA dial; overfitting is the
  failure mode.
- **A held-out eval is mandatory** — it is the only thing that distinguishes a real improvement
  from a memorised training set.

## Model answers (sketch)

1. Loss falls as rank rises but with diminishing returns; past the point where the adapter can
   already represent the needed update, extra rank buys little and costs parameters. Pick the
   smallest rank that hits your eval bar.
2. Pairs come from logged real inputs plus verified ideal outputs (human-written or a strong
   model's, checked). Consistency: one schema, one style, contradictions removed. Hold out a
   random, representative slice you never train on.
3. Fine-tune on the 300 clean ones — consistency beats volume, and 8,000 noisy pairs teach the
   contradictions in them. Use the noisy set for coverage analysis or as candidates to clean and
   promote, not as training data as-is.
4. Full: `200 × 4096² ≈ 3.36B`. LoRA rank-16: `200 × 16 × (4096+4096) ≈ 26.2M`. Saving ≈ **128×**
   fewer trainable parameters (rank-16: `d²` vs `2·r·d`, i.e. `4096 / 32 = 128`).
