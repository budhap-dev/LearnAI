## The one idea

When the caller of your API is a model, three things are simultaneously true:

1. The arguments were **assembled by a next-token predictor** — plausible-looking is its
   speciality, correct is not guaranteed (Lesson 2.1).
2. The predictor may have been **steered by text an attacker wrote** — an email, a ticket, a
   web page it just read (Lesson 4.6). Tool calls are where injection stops being words and
   becomes actions.
3. The loop **retries** (5.1, 7.2) — so anything not idempotent can happen twice.

So the rule is: **validate as if the arguments came from the internet, because indirectly
they did.** No model, however good, changes this; the tool is the trust boundary.

Same attacks, none succeed — and look at *how* each dies. The over-refund becomes a
**proposal awaiting approval** (it is a legitimate request — the customer really is owed
consideration; the tool's job is to stage it, not judge it). The smuggled arithmetic dies at
the **type check** (the schema layer would have killed it earlier; the tool checks anyway —
defence in depth). The unknown order dies against **reality** (the orders table), the
negative amount against a **range rule**, and the retry is a **no-op** because proposals are
keyed.

## The checklist

```output
rules
```

Expanding the two that engineers most often skip:

**Propose, don't execute.** Split every consequential capability into a *propose* tool the
model can call and an *execute* path the model cannot reach — driven by your auth system and
a human (7.6) or a policy engine. The model's schema simply has no "execute" in it. This is
not distrust of a particular model; it is the same reason CI cannot push to prod directly.

**Validate against reality, not just shape.** `amount: number` is shape. "Amount ≤ what is
refundable on this order" is reality, and only your code can know it. Every tool should ask:
what does the *world* say the bounds are, and where do I check them?

```check
Your search tool takes a `query: string`. The model, mid-injection, calls it with a query containing another customer's email address. What is the defence?
- A firmer system prompt
- * The tool's own authorisation: it searches only records the current user may see, regardless of the query text
- Blocking the word "email" in queries
why: Tools carry the caller's real permissions, never the model's ambitions. Scoping data access in the tool makes the query text harmless.
```

```check
A tool deletes a draft by id. The loop retried after a timeout and the second call returned "not found", which the model reported as an error to the user. What is the fix?
- Tell the model to ignore not-found errors
- * Make delete idempotent: deleting an already-deleted draft returns success with a note — retries become safe by design
- Remove retries
why: Lesson 5.1's idempotency, applied to tools: the pair (operation, key) must be safe to repeat, because the loop will repeat it.
```

## Tool design quality is prompt quality

One more reason to write tight contracts: the model reads them. Names, descriptions and
enums are the only documentation it gets, and 5.3 showed descriptions are how it decides
*when* to call. Vague contracts produce vague calls; a tool named `do_billing` with
`data: object` will be called wrongly forever. The best tools look like the best internal
APIs: one job, few arguments, typed, enumerated, honestly described — plus the paranoia
above.

## What a senior engineer should take from this

- **Tool arguments are untrusted input**, with or without an attacker; the tool is the trust
  boundary.
- **Schema first, reality second, policy third** — three validation layers, none optional.
- **Read tools read; write tools propose; execution is gated** by identity the model does
  not have.
- **Idempotent by key; audited per call.** The loop retries and the trace must show
  everything.

## Exercises

1. Take one tool from a system you know (or the 5.3 calculator) and write its three
   validation layers explicitly. Which layer was missing?
2. The good tool keys proposals by `order_id:reason`. What duplicate slips past this key, and
   what key fixes it?
3. Design the contract for a `send_email` tool a support agent may call. Who can it address,
   what can it contain, what is proposed vs executed, and what is audited?
4. An MCP server (7.4) offers your agent a `run_query` tool. What do you verify before
   enabling it, and with which permissions does it run?

## Model answers (sketch)

1. Commonly missing: reality (checking the id exists / the amount is within bounds) — shape
   checks exist, policy is assumed, reality is skipped.
2. Same order, same reason, *different amount* is treated as a duplicate; key on
   `order_id:amount:reason` (or hash the whole proposal) if distinct amounts are legitimate.
3. Recipients: the ticket's requester only (looked up, not model-supplied); content: template
   + model-drafted body that passes checks (no other customers' data, no promises beyond
   policy); anything off-template → propose for human send; audit: full body + recipient +
   trigger.
4. Who wrote the server, what credentials it holds, what its tools can reach; run it with a
   scoped read-only role, never your service's admin identity — an MCP server is a tool
   supply chain (9.5).
