## The one idea

Every multi-step LLM system answers one design question: **who decides what happens next —
your code, or the model?** Everything else about "agents" is detail. The five patterns,
simplest first:

```diagram
pattern-gallery
```

| Pattern | Next step chosen by | Cost | Testability | Reach for it when |
|---|---|---|---|---|
| **Chain** | your code, fixed | N known calls | each step alone | the steps are known: extract → decide → draft |
| **Router** | your code, after one cheap classify | 1 + branch | per branch | different inputs need different handling |
| **Parallel** | your code, concurrently | N at once | per branch | independent pieces; latency matters |
| **Evaluator loop** | your code, judged retry | 2–2k calls | judge + generator separately | quality varies and a rubric can score it |
| **Agent** | **the model**, from tool results | unknown until it stops | trajectories, not units | the path genuinely depends on what is found |

The order is a discipline, not a hierarchy of sophistication. A chain that ships and evals
cleanly is better engineering than an agent that demos impressively; and a real agent task
forced into a chain becomes a thicket of special cases. **Match the pattern to how knowable
the path is.**

## The first four are just code

A chain is function composition where some functions are model calls — each with a schema, a
validator and its own golden set (Lessons 4.3, 8.2). A router is 5.6's model routing applied
to intent. Parallel is `asyncio.gather` / `Promise.all` with per-branch caps. The evaluator
loop is generate → judge → retry-with-feedback, capped at two or three rounds (a third retry
rarely helps and doubles cost — the same economics as 4.3's retry policy).

Their shared virtue: **the graph is visible in your code.** You can read it, log each edge,
test each node, and put a budget on each box. When something breaks, the question is "which
node", not "what did it decide to do this time".

```check
A feature must: pull the order, summarise the complaint, decide refund vs replace by policy, and draft a reply. Which pattern?
- Agent — it has four steps
- * Chain — the steps are known and fixed; only their contents need a model
- Evaluator loop
why: Step count does not make an agent. The path is fully known in advance, so code owns the graph and each step is separately testable.
```

## The agent row

Give the model tools and the loop (Lesson 7.2) when **the path cannot be written down in
advance**: diagnosing an incident, researching a question across sources, fixing a failing
test suite, filling a form that depends on what earlier lookups reveal. The signature is
branching that depends on *content discovered mid-task*.

That power has a price you must budget for, not hope away:

- **Unknown cost** until it stops — so budgets, in the loop (7.2, 7.7).
- **Unknown behaviour space** — so guardrails, least-privilege tools (7.3) and gates for
  side effects (7.6).
- **Testing becomes trajectory evaluation** — did *a* good path happen, not *the* path
  (Module 8's evals over rubrics rather than exact matches).

> **For the ADR.** Write one sentence: "The path cannot be known in advance because ___."
> If you cannot fill the blank with something discovered mid-task, choose a row higher. If
> you can, write the budgets and the gate into the same paragraph as the decision.

## Composition is the norm

Real systems mix rows. The 7.6 example is a router (supervisor) over two chains (workers)
with a gate; a coding agent is an agent whose inner steps are chains (edit → run tests →
read failures); RAG with an evaluator loop wraps retrieval in judged retries. The patterns
are vocabulary, not sects — the discipline is only ever *simplest row that fits, per
decision point*.

```check
Your agent works, but 80% of its runs follow the same three tool calls in the same order. What is the refactor?
- Nothing — it works
- * Promote the common path to a chain and keep the agent for the rest — cheaper, faster, testable
- Add more tools
why: A stable majority path is a workflow wearing an agent costume. Hoist it; let the loop handle the genuinely variable 20%.
```

## What a senior engineer should take from this

- **One question: who owns the next step.** Code where the path is knowable; the model where
  it is not.
- **Five patterns; start at the top.** Each row down trades predictability for flexibility.
- **Agents are budgeted, gated, trace-emitting loops** — never bare while-loops with tools.
- **Watch running systems for pattern demotion**: stable agent paths become chains; chains
  with content-dependent branches become agents. The boundary is empirical.

## Exercises

1. Classify five multi-step LLM features you know (or want to build) into rows. For any you
   marked "agent", fill in: "the path cannot be known in advance because ___".
2. Sketch the 7.6 supervisor/worker system entirely as a chain. What breaks first as
   requirements grow — and at which requirement would you re-introduce the router?
3. Your evaluator loop converges 92% of the time in ≤2 rounds, else never. Design the exit:
   what do you return, at which cap, and what do you log?
4. Take a real incident-diagnosis runbook from your team. Which steps are chain-able, and
   where is the first genuinely content-dependent branch?

## Model answers (sketch)

1. Typical: doc summariser → chain; support triage → router; contract analyser → parallel +
   merge; copy generator with brand rubric → evaluator; "find why the build broke" → agent
   (the failing step is discovered, not known).
2. The chain works until inputs diverge (multiple request types); the router returns at the
   second or third distinct handling path.
3. Cap at 2 retries; return best-scoring draft flagged `below_bar` with the judge's feedback
   attached; log rounds, scores and the rubric version (Lesson 4.4's registry).
4. Most runbooks are 80% chain (gather standard signals) with one branch point ("if the
   deploy correlates…") — which is exactly where 7.2's loop earns its budget.
