## The one idea

"Multi-agent" sounds exotic and is mostly not: it is **decomposition** — the oldest tool in
software — applied to model calls. One call with ten tools, five duties and a giant prompt
becomes several calls, each with one duty, a narrow contract, and its own golden set. The
supervisor/workers shape is simply a router (7.1) whose branches are model calls:

```diagram
supervisor-gate
```

Two properties make the shape governable, and both are code:

1. **Typed JSON at every seam** — each handoff is loggable, replayable, and evaluable alone;
2. **The gate** — consequential actions stop as *proposals* until an authenticated human (or
   a policy engine) approves. The model cannot reach the execute path at all.

## Gates: the engineering, not the sentiment

"Human in the loop" fails when it is a checkbox. A gate that works has:

- **A hard code boundary.** Propose and execute are different code paths; the execute path
  demands an identity from your auth system. No prompt output can traverse it — the model
  cannot approve its own proposal, and neither can an injection (4.6).
- **Blast-radius placement.** Gate what is irreversible or expensive: money, emails to
  customers, deletions, permission changes, production deploys. Do not gate reads and
  drafts — a gate on everything trains reviewers to click yes, which is no gate at all.
- **Reviewable proposals.** The reviewer sees the proposal, the evidence, and the trace —
  not "the AI wants to do something, OK?". 7.3's audit lines are what make review real.
- **Thresholds in code** (`amount > cap`), tuned by data, deaf to the prompt.
- **An owner for the queue.** Pending proposals are work; unowned queues rot into
  auto-approve.

```check
Your team gates every single agent action "to be safe". Three weeks later, reviewers approve in under two seconds each. What happened, and what is the fix?
- The agent became trustworthy
- * Alert fatigue: gate only by blast radius so approval stays a real decision, and auto-serve the harmless paths
- Add a second approval
why: Gates spend reviewer attention, which is finite. Spend it where reversal is impossible, and let grounded reads and drafts flow.
```

## When multi-agent pays — and when it is theatre

Decomposition pays when the pieces are *genuinely different jobs*: different tools,
different risk levels, different eval criteria — like billing (gated, exact) versus product
Q&A (grounded, auto-served). It is theatre when one model call with a clear prompt would do
and the "agents" exist for the diagram: every seam you add is latency, another prompt to
version (4.4), and another failure mode. The 7.1 discipline applies unchanged — simplest
shape that fits; and the supervisor itself should stay so small that *its* failure is only
ever a misroute, caught by the same evals as any classifier (3.3's confusion matrix, per
route).

```check
The billing worker starts also answering product questions "while it's there". Why is this a defect even when the answers are right?
- Workers may only do one thing, as a rule
- * Scope creep across seams destroys the properties you decomposed for: the product answers now bypass grounding, its evals, and the routing decision
- It costs more tokens
why: Each worker's guarantees (grounding, gating, golden set) are attached to its scope. Work that leaks across seams carries no guarantees.
```

## What a senior engineer should take from this

- **Multi-agent = decomposition with model calls.** Typed seams, narrow workers, small
  supervisor — each piece testable alone.
- **The gate is code + real identity between propose and execute.** Blast-radius placement;
  reviewable proposals; owned queues.
- **A gate on everything is a gate on nothing.** Spend reviewer attention where reversal is
  impossible.
- **Add seams only for genuinely different jobs.** Otherwise it is complexity theatre.

2. The supervisor misroutes 4% of emails. Design its eval (per-route precision/recall, 3.3)

3. Replace the scripted reviewer with a real flow: what is persisted, who is notified, what
   happens on timeout, and how does the customer experience the wait?
4. A colleague proposes agents that talk to each other in free prose "so they can
   collaborate". Argue for typed handoffs instead — what specifically becomes impossible
   with prose seams?

## Model answers (sketch)

1. `{account_id, effective_date, reason}`; gated (irreversible, revenue); evidence: the
   request text, account standing, retention offer eligibility.
2. Label a few hundred routed emails; confusion matrix per route; `other` → human triage,
   never a guess — misrouting money to auto-serve is the failure to minimise.
3. Persist proposal + trace; notify via the team's queue; timeout → escalate, never
   auto-approve; customer gets "we're reviewing" with the served (harmless) answers inline.
4. With prose seams you lose: schema validation (4.3), replayable logs, per-seam evals,
   idempotency keys, and gate enforcement — every guarantee in this module hangs off the
   seams being typed.
