## The one idea

Lesson 5.3's tools were functions you wrote, described to the model in your own request. That
scales badly across an organisation: every app that hosts a model re-integrates every system
it wants to touch — N apps × M systems, each pair bespoke.

**MCP (Model Context Protocol)** is the USB-of-tools answer: a standard way for a
model-hosting app (the **host**, via an MCP **client**) to connect to tool **servers** and
discover, at runtime, what they offer:


- **Tools** — callable functions with JSON-schema arguments (exactly 5.3's contract shape);
- **Resources** — readable content the host can pull into context (files, records, docs);
- **Prompts** — reusable, parameterised prompt templates a server ships alongside its tools.

One protocol, so an integration written once (a "tickets server", a "database server") works
in any MCP-speaking host — your assistant, an IDE, an agent runtime. N+M instead of N×M.

## What the protocol does not do

The protocol is plumbing. Everything Module 7 has taught remains your job, per server:

| Not in the protocol | Still yours | Lesson |
|---|---|---|
| Permissions | the identity and scopes each server runs with — least privilege per server, never your service's admin credentials | 7.3 |
| Trust of results | server output is **data**; a resource fetched from a wiki can carry an injection payload like any other document | 4.6 |
| Consequential actions | propose-vs-execute and human gates do not appear because a tool arrived by protocol | 7.6 |
| Quality | a server's tool descriptions are prompt material; vague ones produce wrong calls in any host | 5.3, 7.3 |
| Cost & budgets | tool calls still consume loop steps and tokens; caps still live in your loop | 7.2 |

The sharpest edge is **supply chain**: installing a third-party MCP server is installing
someone's code and granting it your credentials and your model's attention. Vet it like a
dependency (because it is one), pin its version, read what scopes it requests, and run it
sandboxed. A malicious or sloppy server can exfiltrate what it reads and inject what your
model consumes — this is 9.5's territory, arriving early.

```check
A third-party MCP server offers a convenient "browse any URL" tool for your research agent. What is the primary risk to assess first?
- Latency of the fetches
- * Everything it fetches is untrusted text entering your prompts, and the server itself sees whatever your agent sends it — injection surface and supply chain, before convenience
- Whether the protocol version matches
why: A URL-browsing tool is an injection firehose (4.6), and the server is a third party in your data path. Both are manageable — deliberately, not by default.
```

## Bespoke tool or protocol server?

| Choose bespoke (5.3-style) when | Choose MCP when |
|---|---|
| One app, a handful of tools you own | several hosts need the same tools |
| the tool wraps your own service, already authenticated | the integration is a product for others (or from others) |
| tight loop, latency-critical | discovery at runtime is worth a hop |
| you need non-standard behaviour (streaming results into context, custom auth flows) | the standard surface (tools/resources/prompts) covers it |

In practice teams converge on both: internal capabilities exposed once as MCP servers for
every host to share, plus a few bespoke tools inside a specific loop where the protocol hop
buys nothing. The decision is ordinary platform engineering — the same one you make about
"library vs service".

```check
Your team's agent, IDE assistant and support bot all need to search the product database. Today each has its own bespoke tool. What does moving to one MCP server change?
- The model gets better at SQL
- * One implementation, one permission review, one audit point — and every host inherits fixes; the searches themselves are unchanged
- Injection risk disappears
why: The protocol consolidates integration and governance. It does not change what the tool does or what its results should be trusted as.
```

## What a senior engineer should take from this

- **MCP standardises discovery and calling** — tools, resources, prompts — turning N×M
  integrations into N+M.
- **It standardises none of the safety.** Permissions, gates, result-trust and budgets stay
  exactly where Lessons 7.2–7.3 put them, per server.
- **Third-party servers are dependencies with credentials.** Vet, pin, scope, sandbox.
- **Bespoke vs protocol is library-vs-service**, decided by how many hosts share the need.

## Exercises

1. List the tools your team's assistants (or scripts) have built more than once. Which would
   an internal MCP server consolidate, and what single permission review would replace?
2. Write the security review checklist for adopting a third-party MCP server — five
   questions, each mapped to the lesson that motivates it.
3. A server ships a prompt template alongside its tools ("use this to summarise a ticket").
   What are the benefits and the risks of adopting the server's prompt into your host?
4. Design the identity model: three servers (files, tickets, database) used by one agent on
   behalf of user U. Whose credentials does each call carry, and where is that enforced?

## Model answers (sketch)

1. Search/lookup tools are the usual duplicates; one server means one place for the
   authorisation logic 7.3 requires.
2. Who maintains it (supply chain, 9.5)? What scopes does it need (7.3)? What does it log or
   phone home (9.6)? Are results treated as untrusted (4.6)? Can its actions be gated (7.6)?
3. Benefit: the server author knows their domain's good prompt. Risks: the template is
   third-party prompt material in your trust boundary, and it changes when they update —
   version-pin it like the prompt registry expects (4.4).
4. Each server runs with a service identity scoped to *its* backend, and receives U's
   authorisation context per call; enforcement lives in each server's backend, never in the
   model or the client.
