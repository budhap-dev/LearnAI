## The one idea

A single model call fails by being wrong. An **agent** adds failure modes that only exist
because there is a loop: it can repeat itself forever, spend without limit, do excellent
work on the wrong goal, and turn a 5% per-step error rate into a coin flip over twenty
steps. None of these is fixed by a better prompt. Each is fixed by a **guardrail in the
loop** — deterministic code watching the trace:

## Detectors, against real trace shapes

The example runs four abbreviated traces of the 7.2 diagnostic agent through four detectors.
Deterministic on purpose: the point is the detector, and a detector you cannot unit-test is
not a guardrail.

**Repeats** — the commonest failure. A model that did not get what it wanted often just asks
again, identically, forever:

```code

```

```output

```

Read the four verdicts:

- **healthy** passes everything — five steps, each new, ending in FINISH.
- **loop** trips two detectors at once (exact repeats *and* no-new-information) — real loops
  usually do, which is why you run every detector every step, not one.
- **wander** is the subtle one: the agent is busy and each call succeeds, but the recent
  window stopped touching goal-relevant tools — it is researching kubernetes tuning while
  checkout burns. Activity is not progress.
- **runaway** is caught by the budget — the guardrail of last resort from 7.2, still
  essential because novel failure shapes will slip the pattern detectors.

## Compounding: the arithmetic that makes agents different

```output
compounding
```

A 95%-reliable step is excellent for a single call and a coin flip at twenty steps — and
worse than it looks, because a wrong mid-trace "fact" poisons every later step (the model
conditions on its own history; Lesson 2.1). Two consequences:

1. **Shorter chains are a reliability feature**, not just a cost saving. 7.1's demotion rule
   (promote stable paths to chains) removes steps from the multiplication.
2. **Verification between steps resets the chain.** A schema check, a value check, a test
   run after each edit (11.1's coding agents live on this) — each verified step starts the
   multiplication over from 1.0. This is Module 4.3's discipline, applied per iteration.

```check
An agent's steps are each 98% reliable. The team plans a 30-step autonomous run with verification only at the end. Roughly what fraction of runs will have at least one bad step, and what changes the maths?
- ~2%; nothing needed
- * ~45%; verification between steps (schemas, tests, checks) resets the chain so errors are caught where they happen
- 100%; agents cannot work
why: 0.98³⁰ ≈ 0.55. End-only verification finds that something went wrong, not where; per-step checks turn a multiplication into independent small risks.
```

## Matching response to failure

```output
responses
```

The mapping matters as much as the detection — the wrong response converts one failure into
another:

| Detection | Right response | Wrong response (and what it causes) |
|---|---|---|
| repeat / stall | inject "already tried; result was X", or stop with partial | silently allow (burns budget) or raise temperature (adds noise, 2.7) |
| budget | stop; return best-so-far + trace; escalation is a *human* decision | auto-raise the cap (runaway with extra steps) |
| drift | re-state the goal; or supervisor/human check-in (7.6) | kill immediately (wastes salvageable work) |
| tool errors | data back to the model (5.3); repeated errors count as no-progress | exceptions up the stack (loses the trace and the partial) |

And every path — healthy or not — **returns the trace**. Agents are debuggable exactly to
the extent their traces are complete (5.7, 7.2); the trace is also what your evals score
(Module 8) and what the incident review reads (9.8).

```check
Your drift detector fires on 15% of healthy runs (the agent legitimately consults docs mid-diagnosis). What is the right adjustment?
- Delete the detector
- * Tune it like any classifier: widen the goal-tool set or window, measure false-positive rate on labelled traces, and prefer "nudge" over "kill" as its response
- Make it fire more often to be safe
why: Detectors are classifiers over traces — 3.3's precision/recall applies. A noisy detector with a destructive response is worse than none; a noisy detector that only nudges is cheap.
```

## What a senior engineer should take from this

- **Four classes: loops/stalls, runaway spend, drift, compounding error.** All detectable in
  the trace, none fixable by prompt alone.
- **Run every detector every step**; budgets remain the backstop for shapes you did not
  foresee.
- **Reliability multiplies; verification resets it.** Shorter chains and per-step checks are
  how long-running agents stay correct.
- **Responses are graded**: intervene, stop-with-partial, escalate. Auto-raising budgets is
  how bills happen.

## Model answers (sketch)

1. A two-cycle in the (tool, args) sequence — detect a repeating period-2 window; respond
   like repeat/stall (inject the combined results of A and B, ask for a decision).
2. Most teams find 2–3 steps carry the risk (the extraction and the action); a schema check
   after extraction and a dry-run before action reset the chain where it matters.
3. "Goal: find why checkout is slow. So far: payments latency doubled at 14:02. Docs research
   does not advance this — use get_deploys or conclude." Restating gives the model the
   context to self-correct; scolding adds tokens and no information.
4. Per failure class: fire rate, false-positive rate (sampled), budget p95 vs cap, top-3
   stop reasons, and five random full traces — the sample keeps the numbers honest (8.1).
