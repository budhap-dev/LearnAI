## The one idea

Lesson 5.3's loop ran until the model stopped calling tools. That was fine for two tools and
a scripted errand. An **agent** points the same loop at an open-ended goal — which means the
model now controls how long you loop and how much you spend. So the loop grows four organs:

```diagram
agent-loop-stops
```

1. an explicit **goal and method** in the system prompt;
2. a **budget** — steps *and* tokens, whichever trips first;
3. a **termination contract** — the model must either call a tool or finish in prose;
4. a **trace** — every step recorded, returned on every exit, healthy or not.

Read that trace like an engineer reads any trace. The model listed services, measured all
three, spotted the payments jump (121 → 262 ms), and concluded — correctly, citing numbers,
inside budget. Two honest observations from this recording:

- **It skipped the deploy check.** The method said "for any degraded service, get its
  deploys"; the model found the latency evidence sufficient and finished. Instructions steer,
  they do not enforce (Lesson 2.6) — if correlating with deploys is *required*, that is a
  chain step (7.1), not a prompt line.
- **The method prompt mattered.** An earlier recording of this exact example, with a vaguer
  system prompt ("investigate efficiently"), checked one healthy service and confidently
  blamed it. The loop was identical; the method text was the difference between a right and a
  wrong conclusion. Agents amplify prompt quality.

## Degrading, not hanging

The same loop with a hostile budget stops with a partial result and the trace — never an
infinite loop, never an unbounded bill:

```output
failure
```

The degraded exit is a designed outcome, not an error: return the best-so-far, say what was
spent, attach the trace, and route to a human or a bigger budget *by explicit decision*.
Lesson 7.7 adds detectors for the failure shapes a budget alone misses.

```check
Your agent loop has max_steps=8. A run hits the cap mid-investigation. What should the caller receive?
- An exception
- * The partial findings, the reason it stopped, and the full trace
- Nothing — retry automatically with max_steps=16
why: Budget exhaustion is a normal outcome to design for. Silently doubling the budget is how runaway spend happens; escalation is a decision, not a default.
```

## Rules that make loops production-grade

- **Bound everything the model influences**: steps, tokens, per-tool call counts, wall time.
- **Keep tools read-only until Module 7.6's gate exists.** A diagnostic agent's worst case
  is a wrong sentence; an acting agent's worst case is a wrong action.
- **The trace is the product** for debugging, evals and audits: persist it with the same
  care as 5.7's spans (it *is* 5.7's spans, plus tool results).
- **Termination is enforced by the loop, requested of the model.** The prompt says "reply in
  prose when done"; the budget guarantees an end regardless.
- **Do not stream trust into the loop**: each iteration re-validates tool arguments (7.3) —
  step 6 is as untrusted as step 1.

```check
The model in your loop calls the same tool with the same arguments three times in a row. The budget has room. What should happen?
- Let it continue — the budget will catch it eventually
- * Intervene: a repeat detector feeds back "already called; result was X" or ends the run — burning budget on repeats is waste, not progress
- Raise the temperature
why: Budgets bound damage; detectors (Lesson 7.7) recognise failure shapes early. Both belong in the loop.
```

## What a senior engineer should take from this

- **Agent = tool loop + goal + budgets + termination + trace.** All four organs, always.
- **Two budgets** (steps, tokens); degraded exits are designed outcomes that carry the trace.
- **Method prompts change outcomes** — and anything *required* belongs in code, not prose.
- **Read traces the way you read any trace.** If you cannot reconstruct a run from what you
  stored, you stored too little.

## Model answers (sketch)

1. Repeat/stall; feed back "call limit reached for get_latency; use what you have or finish".
2. Chain: fetch latencies for all services + deploys for degraded ones (plain code); agent
   (or single call): interpret the assembled evidence. The discovery part was never really
   open-ended — 7.1's demotion rule.
3. A tool that blocks for minutes burns wall time with zero steps/tokens; users and SLOs live
   in seconds, not tokens.
4. run_id, step, model+version, prompt hash, tool, args, result hash, tokens in/out,
   stop_reason, budget state, final answer, verdict (from evals). The 5.7 span plus tool I/O.
