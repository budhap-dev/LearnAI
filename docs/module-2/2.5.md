## The one idea

The **context window** is the maximum number of tokens the model can look at in one call —
input *and* output together. It is one fixed buffer, and four things compete for it:

```diagram
context-budget-bar
```

1. the **system prompt** — instructions, persona, rules, tool descriptions
2. the **conversation history** you re-send every turn (Lesson 2.4: there is no memory)
3. whatever you **retrieve** or attach — documents, search results, tool outputs
4. the **answer** the model has yet to write

Grow any of the first three and the fourth shrinks — or the request is rejected, or the API
truncates for you. None of those is a decision you want made implicitly.

The policy here — oldest turns first, then least-relevant documents, never the system prompt
or the answer reserve — is right for a support assistant that must answer from documents. A
coding agent might keep more history; a summariser might keep more document. **The point is
that it is a policy you chose, and it logs what it dropped.** When an answer is wrong because
context was cut, you can see that it was.

Common policies, in rough order of sophistication:

| Policy | Keeps | Loses | Use when |
|---|---|---|---|
| Truncate oldest history | recent turns | early decisions and facts | casual chat |
| Sliding window + pinned facts | recent turns and a small "facts" block | detail | most assistants |
| Summarise old history | a compressed recap | precision, tone | long sessions; the recap is itself an LLM call |
| Rank and drop retrieval | best documents | marginal ones | RAG — always, in some form |
| Reject and ask the user to narrow | everything | convenience | when wrong answers are expensive |

## Long context is a capacity, not a strategy

Windows have grown from a few thousand tokens to hundreds of thousands. That is a real
capability — whole codebases, long transcripts, many documents. It is not a reason to stop
budgeting, for three reasons the example makes plain:

```output
bigger-window
```

- **Cost is linear in tokens sent.** Filling a big window on every request multiplies the bill
  by the same factor. Prompt caching (Lesson 5.5) softens this for the parts that do not
  change; it does nothing for the parts that do.
- **Latency grows with input** — attention is quadratic in the worst case (Lesson 2.4), and
  even the linear parts add up. Time to first token on a 150k prompt is measured in seconds.
- **Quality does not scale with volume.** Models attend less reliably to the *middle* of a very
  long prompt — the "lost in the middle" effect — and more irrelevant text means more chances
  to answer from the wrong passage. Twenty precise chunks usually beat two hundred loose ones.
  Retrieval (Module 6) exists precisely so that you can send less.

> **For the ADR.** "We'll just use the big context window" is a legitimate first design for
> low-volume, high-value tasks (one long document, one careful answer). For anything with
> traffic, budget the window and retrieve. Write down the per-request token target and alert
> when p95 exceeds it.

## Practical notes

- **Count both directions.** Some providers state a total window; some separate input and
  output limits. Know which, and set `max_tokens` deliberately.
- **Tool schemas and few-shot examples are tokens too.** A dozen tools with verbose
  descriptions can eat thousands before the user says a word.
- **Put the important thing at the start or the end.** Instructions first, the question last,
  bulk material in between — that shape works with the attention pattern, not against it.
- **Log tokens per part, per request** (Lesson 5.7). "System 900 / history 3,400 / retrieved
  6,200 / output 700" tells you exactly what to trim when cost or latency drifts.

## What a senior engineer should take from this

- **The window is one budget.** Four claimants; the answer is the one that gets squeezed.
- **Measure, reserve, apply a policy, log.** Truncation you did not choose is a silent bug.
- **Long context is not memory** and not free. Send what matters; retrieve the rest.
- **Tokens per part per request** is a metric you want from day one.
