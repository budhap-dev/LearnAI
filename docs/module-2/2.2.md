## The one idea

Every time you send text to a language model, the very first thing that happens — before any
"intelligence" — is that your text is chopped into **tokens** and turned into integers. The
model is trained on those integers, predicts the next integer, and the tokeniser turns
integers back into text on the way out.

```diagram
token-pipeline
```

That means three practical things:

1. **You pay per token**, and the context window is measured in tokens — so you need to be
   able to *estimate* tokens for a workload before you build it.
2. **Tokens are not words and not letters.** They are fragments learned from data. Common
   English words are usually one token; rare words, other languages, code and numbers split
   into more.
3. A model reasons over tokens, not characters. Tasks that need character-level access —
   counting letters, reversing strings, spelling — are harder than they look, *by design*.

> **In one sentence:** a token is a learned fragment of text, and the tokeniser is a
> lookup that maps text ⇄ integers before and after the model.

## Try it first

Paste anything into the explorer — an English sentence, the same sentence in another
language, a JSON blob, a UUID — and watch the boundaries move.

```explorer

```

Notice: spaces are usually attached to the *start* of the next word (` the` is one token, so
is `the`, and they are different tokens), numbers fragment oddly, and non-English text costs
two to four times as many tokens for the same meaning.

## How tokens are learned — byte-pair encoding

Real tokenisers are trained, not designed. The most common algorithm, **byte-pair encoding
(BPE)**, is simple enough to write in a screen of code, and doing so removes all the mystery.
Here is the whole thing on a toy corpus, in Python and TypeScript.

Start with a tiny corpus and pre-split it into words, keeping the leading space attached:

```code
corpus
```

```code
pre-tokenise
```

Training is one loop: **count every adjacent pair of symbols across the corpus, merge the
most frequent one everywhere, repeat.** The ordered list of merges *is* the trained
tokeniser.

```code
train-bpe
```

```output
train
```

Read the merges top to bottom. The first rule glues a space to `t` (because ` t…` words are
common); by rule six the corpus has learned that ` token` is a unit; `ber` + `r` → `berr`
is on its way to `berry`. Nobody told it about words — frequency did.

```check
- Fewer tokens — Devanagari is compact
- * Noticeably more tokens — fewer merges were learned for it, so it fragments
why: Text unlike the training data splits into more, shorter tokens. Budget 1.5–4× for non-English input, and measure.
```

Three observations that carry straight over to production tokenisers with 100,000+ merges:

- `strawberry` is **5 tokens** here even though `berry` was learned — the model never saw
  `straw`. Real tokenisers have the same problem with rare and misspelled words.
- `tokenisation` (British spelling, not in the corpus) fragments into 8 tokens; the American
  `tokenization` would have too. **Spelling variants cost tokens.**
- The leading-space convention means `␣the` and `the` (at the start of a line) are different
  tokens. This is why prompt formatting sometimes matters more than it "should".

## Why the model can't count the r's

A famous failure: ask a model how many r's are in *strawberry* and it may say two. Look at
what it actually receives:

```output
letters
```

There is no token that contains all three r's, and there is no character-level view at all.
The model has to *know* the spelling of each token from training data, then add — a memory
task, not a perception task. Newer models are trained to handle this better, but the
mechanism is the reason, and it generalises: **anything that depends on characters
(reversing, spelling, exact string lengths, regex-like matching) is a weak spot. Give that
work to code, not to the model.**

```check
A feature must validate that a reference number is exactly 12 characters. Where should that logic live?
- In the system prompt, with an example
- * In your code — the model works in tokens, not characters
- In a few-shot prompt with correct and incorrect examples
why: Character-level work is a structural weak spot. Give exactness to code; give judgement over meaning to the model.
```

> **Production tip.** If a feature needs exact string manipulation, do it in your code and
> give the model the result. Models are for judgement over meaning; your code is for
> characters.

## Other languages, code and numbers cost more

Tokenisers are trained on a mix dominated by English (and, increasingly, code). Text that
looks unlike the training data fragments into smaller pieces:

```output
multilingual
```

The toy vocabulary exaggerates the effect, but real tokenisers show the same shape: the same
sentence in German, French, Hindi or Japanese commonly costs **1.5–4×** the tokens of the
English version. The same is true of:

| Input | Why it costs more |
|---|---|
| Non-English prose | fewer merges learned for it; more, shorter tokens |
| Numbers and IDs (`4829107`, UUIDs) | digits are usually split into 1–3 digit chunks |
| Code | punctuation-heavy; indentation whitespace is tokens too |
| Base64, hashes, minified JSON | close to one token per 2–3 characters |
| Unusual formatting (ALL CAPS, l33t) | breaks the common merges |

**Consequences for design:** a multilingual product costs more per request than the English
demo suggested; stuffing raw JSON or logs into a prompt burns budget fast; and a "4,000-word
document" is a very different number of tokens depending on what it contains.

## Estimating tokens and cost

Pricing is quoted per million tokens, separately for input and output. The arithmetic is
trivial; the skill is remembering to do it *before* you build.

```code
cost
```

```output
cost
```

Two rules of thumb for English prose with real tokenisers: **~4 characters per token** and
**~0.75 words per token** (so 1,000 words ≈ 1,300 tokens). For anything else, measure — use
the explorer above or your provider's token-counting endpoint.

> **Careful.** Prices are deliberately not printed in this lesson. They change, differ per
> model, and differ for input, output, cached input and batch. The
> [model reference](#/reference/models) is the one dated place we keep them.

## What a senior engineer should take from this

- **Budget in tokens, not characters or words.** Log tokens per request from day one
  (Lesson 5.7) and estimate before you build (Lesson 5.6).
- **Expect multilingual and structured input to cost 2–4× the English demo.**
- **Character-level work belongs in code**, not in the prompt.
- **Different models use different tokenisers.** Token counts — and therefore costs and
  context limits — are not comparable across vendors without measuring.
- **The context window is a token budget shared by everything** — system prompt, history,
  retrieved documents and the answer. Lesson 2.5 is about spending it well.

## Model answers (sketch)

1. Capitalising every word typically raises the count 30–80%: the merges were learned on
   lower-case running text, so `The`, `Model` are rarer units than ` the`, ` model`.
2. With more merges the corpus's own words merge fully (`strawberry` may become 1–2 tokens),
   but the German/French sentences barely improve — you cannot merge what you never saw.
   More merges = bigger vocabulary = better compression *of the training distribution only*.
3. English: (3,000 + 400) words × ~1.33 ≈ 4,500 tokens × 50,000 ≈ **225M input tokens/day**.
   With 40% at ~2× cost: 0.6 × 225M + 0.4 × 450M ≈ **315M/day**. The point is the second
   number, not the first.
4. Encode, slice the token array to the budget, decode. Decoding a partial multi-byte
   sequence must not produce garbage — a good library returns a replacement character or lets
   you decode "safe" prefixes; test with emoji and CJK text.
