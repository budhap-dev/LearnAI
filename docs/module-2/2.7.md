## The one idea

Every step of the loop from Lesson 2.1 ends with a distribution over the next token. Something
has to turn that into *one* token. That something is the **sampler**, and every knob you have
heard of — temperature, top-p, top-k, seed — belongs to it. **None of them changes what the
model computed. They change how a token is picked from it.**

## Try it first

```explorer

```

Drag temperature to 0 and sample: the same token every time. Drag it to 1.5 and the tail
comes alive — including tokens that make no sense here. Now set top-p to 0.8 at temperature
1.5 and watch the tail get cut off *before* sampling. That interaction — flatten, then cut —
is how most production settings work.

## From scores to probabilities: temperature

The model's last layer emits a raw score per token, called a **logit**. Softmax turns scores
into probabilities; temperature divides the scores first:

```code
softmax
```

```output
temperature
```

- **T → 0**: greedy. The top token gets everything. Repeatable, and prone to loops (Lesson 2.1).
- **T < 1**: sharper. The favourite gets more of the mass. Good for extraction, classification,
  code, anything with a "right answer".
- **T = 1**: the model's own distribution.
- **T > 1**: flatter. Rare tokens get real probability. More variety, more surprises, more
  nonsense. Brainstorming, fiction, generating diverse test cases.

Notice what temperature does *not* do: at T = 2, `purple` gets 3.5%, but the model has not
learned anything new about purple. **Temperature is not a creativity dial on the model's
mind; it is a noise dial on the pick.**

```check
Which setting is right for a JSON extraction pipeline?
- Temperature 1.2 so it explores the schema
- * Low temperature (0–0.3) — one right shape, minimise variance
- Temperature 2 with top-k 1
why: Tasks with a right answer want a sharp distribution. Save higher temperatures for when you want the tail.
```

## Cutting the tail: top-k and top-p

Flattening helps variety but lets junk through. Two truncation rules fix that:

```code
truncate
```

```output
truncation
```

- **top-k** keeps the *k* most likely tokens. Simple, but blind: on a step where the model is
  torn between 20 reasonable words, k = 3 is too tight; on a step where one word is obviously
  right, k = 3 lets in two wrong ones.
- **top-p (nucleus)** keeps the smallest set whose probabilities add up to *p*. It adapts: a
  confident step keeps one or two tokens, an open step keeps many. This is why most APIs
  expose temperature and top-p, and why "temperature 0.7, top-p 0.9" is such a common
  default.

Change one at a time. Temperature and top-p interact (temperature reshapes, top-p cuts what
was reshaped), and tuning both simultaneously turns a two-minute decision into an afternoon.

## Actually picking a token

```code
sample
```

Draw a random number, walk the cumulative distribution, stop when you pass it. That is the
whole of "sampling", and it is where randomness enters the system:

```output
samples
```

Same prompt, same model, twenty different picks at T = 0.7 — and a `this` and several `a`s
that a greedy run would never produce.

## Seeds, determinism, and what you can actually promise

```output
seed
```

A seed makes *this* sampler repeatable: same seed, same picks. Providers offer something
similar. It is useful for tests and demos, and it is **not** a guarantee of deterministic
output in production, because the numbers arriving at the sampler are not stable:

```check
Your extraction pipeline runs at temperature 0. Is one test run enough?
- Yes — T=0 is deterministic
- * No — batching, model versions and hardware still shift the logits, and near-ties flip; measure pass rates over several runs
- Yes, if the seed is fixed
why: T=0 removes the sampler's randomness, not the model's. Design and evaluate as if every call is a sample.
```

- the model version changes under you (silently, on hosted APIs, unless you pin);
- requests are batched with other people's, and floating-point results depend on batch shape;
- hardware and kernels differ across the fleet;
- at T = 0, near-ties flip on those tiny differences — and then the whole rest of the
  output diverges, because every later token conditions on the earlier one.

**Design as if every call is a sample from a distribution**, because it is. That means: evals
that run each case several times and look at rates, not single passes (Lesson 8.4); output
schemas and validators rather than string matching (Lesson 4.3); and retries that expect a
different answer the second time.

## Choosing settings — a starting table

| Task | Temperature | Top-p | Why |
|---|---|---|---|
| Extraction, classification, structured output | 0 – 0.3 | 0.9 – 1.0 | one right shape; minimise variance |
| Code generation | 0 – 0.5 | 0.9 – 0.95 | mostly one right answer; a little variety helps retries |
| Q&A over documents (RAG) | 0.2 – 0.5 | 0.9 | grounded, but natural phrasing |
| Chat / assistant | 0.6 – 0.9 | 0.9 – 0.95 | natural, varied, not chaotic |
| Brainstorming, names, test data | 1.0 – 1.3 | 0.95 – 1.0 | you *want* the tail |
| Generating *diverse* candidates to rank | 0.9 – 1.2 | 0.95 | then choose with an evaluator (Lesson 7.1) |

Treat these as starting points to be measured, not settings to be trusted. And check the
provider's semantics: some scale temperature 0–1, some 0–2; some ignore top-k; "reasoning"
models may fix the sampler entirely (Lesson 4.5).

## What a senior engineer should take from this

- **The sampler picks; the model proposes.** Temperature and top-p change variety, never
  knowledge.
- **Low temperature for tasks with a right answer; higher when you want the tail.** Change
  one knob at a time.
- **Nothing is deterministic in production.** Seeds help tests. Design, evaluate and retry as
  if every call is a sample.
- **T = 0 is not "the correct answer mode"** — it is "the mode most likely to repeat itself".

## Model answers (sketch)

1. e.g. T ≈ 1.2, top-p ≈ 0.95: after flattening, `every` is inside the nucleus and `purple`
   just outside; the cut removes it before any draw.
2. Frequencies converge to the distribution (law of large numbers); at T = 0 the frequency is
