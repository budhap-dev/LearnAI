## The one idea

Lesson 2.1 said the model turns "the text so far" into a next-token distribution. **Attention
is how each token gets to consult the text so far.** For every token, the model asks: *of the
tokens before me, which ones matter for predicting what comes next — and what should I take
from them?* It weights the earlier tokens, blends in what it took, and does that again in
every layer.

Everything the word "context" means in practice — the model using your system prompt, the
document you pasted, the earlier turn of the conversation, the variable name three hundred
lines up — is attention doing that.

## Try it first

```explorer
attention
```

Two things to notice, because they generalise:

1. In sentence 1, **“it” attends to “animal”**; change one word at the end (sentence 2) and
   **“it” attends to “street”**. Attention is computed fresh for every input. Nothing is
   stored; the *pattern* is a function of the whole prompt.
2. **“bank” next to “interest rate” and “bank” next to “river”** are the same token id
   going in, and different vectors coming out — because they attended to different
   neighbours. This is the answer to "how can one embedding handle two meanings?" from
   Lesson 2.3: in a transformer, every token's vector is rewritten in context.

## The mechanism, in words

Each token starts as a vector (its embedding, plus a marker for its position). Then, in each
layer:

- **Every token computes a *query*** — "what am I looking for?" — and every earlier token
  offers a ***key*** — "what do I have?" — and a ***value*** — "what you get if you pick me".
- The token scores its query against every key, turns the scores into weights that sum to
  one, and takes the **weighted blend of the values**. That blend is added to its own vector.
- This runs many times in parallel with different learned queries and keys — the **heads** —
  so one head might track "which noun does this pronoun refer to", another "what is the
  matching bracket", another "which earlier line defined this variable".

That is attention. Nothing more exotic than "look back, weight, blend". The maths (a matrix
multiply, a softmax, another matrix multiply) is in the optional fold below; you do not need
it to reason well about the system.

## The transformer, in one diagram

```diagram
transformer-block
```

A block is attention followed by a **feed-forward** layer that transforms each token on its
own — the part where most "stored knowledge" appears to live. Stack tens of blocks; the last
token's final vector becomes the next-token distribution. Two design facts explain a lot of
what you will see in production:

| Fact | Consequence you will feel |
|---|---|
| Attention looks at **all earlier tokens**, so work grows with the **square** of the input length | doubling the prompt costs more than double; long-context requests are slow and expensive; providers charge per token because compute really does scale with tokens |
| Everything happens **inside one forward pass over the prompt** | there is no state between calls — "memory" is your code re-sending history; the model cannot "remember" what you told it yesterday |
| Position is just another input | the model can weight tokens by where they are; the middle of a very long prompt is often attended to less than the start and end ("lost in the middle", Lesson 2.5) |
| Attention is **parallel across tokens** | prompts are processed fast (all at once), output tokens slowly (one per loop) — which is why *time to first token* and *tokens per second* are separate numbers (Lesson 9.3) |
| The **KV cache** — keys and values for the prompt can be kept for the next output token | this is what prompt caching (Lesson 5.5) sells you: skip recomputing the prompt if it has not changed |

```check
You double a prompt from 20k to 40k tokens. Roughly what happens to the attention work?
- It doubles
- * It roughly quadruples — attention compares every token with every earlier one
- It stays the same; only output tokens cost
why: Attention is quadratic in the worst case; the rest of the network is linear. Long context is a design decision with a bill and a latency.
```

## What "knows" versus "sees" means now

You can now separate two things people conflate:

- **Parametric knowledge** — what the model absorbed in training, baked into its weights.
  Broad, fixed at the cutoff, fuzzy on specifics, no source.
- **In-context knowledge** — what is in the prompt right now, reachable by attention. Exact,
  current, and *yours to supply*.

RAG (Module 6) is the discipline of moving the facts you care about from the first category
into the second. Fine-tuning (Module 10) tries to add to the first category. Prompt
engineering (Module 4) is largely about arranging the second so attention finds it.

## Optional — the maths, if you want it

For a token with query vector *q* and earlier tokens with keys *k₁…kₙ* and values *v₁…vₙ*:

```
weights = softmax(q · kᵢ / √d)     for i = 1…n
output  = Σ weightsᵢ · vᵢ
```

`q`, `k` and `v` are each the token's vector multiplied by a learned matrix; `d` is the
vector size and √d just keeps the scores well-scaled. Multi-head attention runs this with
several sets of matrices and concatenates. That is genuinely all of it.

## What a senior engineer should take from this

- **Attention = every token looks back, weights, blends.** Context works because of it.
- **No state between calls.** All "memory" is prompt content your code re-sends.
- **Cost is roughly quadratic in prompt length.** Long prompts are a design decision with a
  bill and a latency, not a free upgrade.
- **The same token means different things in different contexts** — the network rewrites it.
  This is why pasting the right context changes answers so much.
- **Knowledge in the weights vs. knowledge in the prompt** is the axis that RAG, fine-tuning
  and prompting all move along.

## Model answers (sketch)

1. "bank" attends to "interest/rate" (financial sense) vs "grassy/river" (landform); a static
   embedding is one vector per token id and cannot depend on neighbours.
2. Either the app stored the name and re-sent it in the prompt, or the model guessed. There is
   no cross-call state in the model.
3. Attention diluted across many tokens; positional bias against the middle. Move the key
   passage to the start or end, or retrieve just that passage instead of sending everything.
4. Attention ~ (32/4)² = 64× that part; the rest of the network is linear, so the whole is
   between 8× and 64×. Providers price linearly for simplicity and to keep the model of cost
   predictable — they absorb (and cap) the nonlinearity via context limits.
