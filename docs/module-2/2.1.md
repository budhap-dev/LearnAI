## The one idea

Strip away the chat interface, the tools, the marketing, and a large language model is this:

> **A function that takes the text so far and returns a probability for every possible next
> token.**

That is the entire contract. It does not "understand", "look up", "decide" or "know" in the
sense your code does; it produces a distribution over what token most plausibly comes next,
given everything it absorbed during training and everything currently in the prompt.
Generation is that function run in a loop:

```diagram
next-token-loop
```

Predict a distribution → pick one token → append it → run again. A 400-token answer is 400
trips round the loop. Every capability you have seen — code, essays, reasoning, tool calls —
is built out of this one operation, and so is every failure.

## Build the smallest one

The fastest way to make the idea concrete is to build a language model whose only "knowledge"
is a table of which word followed which. It is laughably small, but it has exactly the same
shape as the real thing:

```code
corpus
```

Training is counting. For every word, count what came after it:

```code
train
```

Ask it what comes after `the` and it gives you a **distribution**, not an answer:

```output
distribution
```

That is what a real model outputs at every step, only over ~100,000 tokens instead of a
dozen words, and computed by a neural network rather than a lookup. Now the loop:

```code
generate
```

```output
generate
```

Two things worth pausing on:

- **The loop repeats itself.** Greedy decoding — always take the most likely token — falls
  into cycles. This is why real systems *sample* instead (Lesson 2.7) and why "just set
  temperature to 0" is not the free lunch it looks like.
- **Nothing here is looked up.** `generate` never checks whether its output is true, complete
  or sensible. It continues. Feed it a prompt the corpus never contained:

```output
no-lookup
```

The model does not notice that "the prompt predicts" is nonsense. It finds the last word it
recognises and continues fluently. **This is hallucination, in miniature: not a bug, but the
mechanism working exactly as designed on an input it has no grounds for.**

```check
A model 'hallucinates' a policy that does not exist. Is that a bug in the model?
- Yes — the model malfunctioned and a firmer instruction will fix it
- * No — it produced the most plausible continuation without grounds; that is the mechanism working as designed
why: A language model is a next-token sampler, not a database. The fix is to put the facts in the prompt or verify the output in code — not to ask more firmly.
```

## Consequences you can now derive

Once you hold "next-token predictor in a loop", the standard list of LLM gotchas stops being
folklore. Each one follows.

| Behaviour | Why it follows |
|---|---|
| **Hallucination** | The most plausible continuation is produced whether or not there are grounds for it. A confident-sounding citation and a real one are equally "likely-looking" text. |
| **Same prompt, different answers** | Picking a token is sampling from a distribution (Lesson 2.7). Even at temperature 0, batching and hardware make the numbers upstream drift. |
| **Prompt sensitivity** | The prompt is the *only* input. Wording, order and formatting change the distribution — sometimes a lot. |
| **Struggles with letters and arithmetic** | It predicts tokens; digits and characters are not first-class (Lesson 2.2). |
| **"Sycophancy"** | Training rewards continuations people rate highly; agreeable text rates highly (Lesson 2.6). |
| **Runs out of context** | The function's input is finite; older text falls off (Lesson 2.5). |
| **Cannot say "I don't know" reliably** | Nothing in next-token prediction represents *the absence* of knowledge — refusal is itself a learned continuation. |

If you remember nothing else from Module 2, remember that table and how each row is derived.

## What is the model's job — and what is not

A useful engineering habit: for every capability in your system, ask *which box in the loop
diagram does this live in?*

- **The model** turns context into a distribution. Its "knowledge" is fixed at training time
  and it has no memory beyond the prompt.
- **The sampler** picks a token. Temperature, top-p, seeds — all here, none of them changing
  what the model knows. Try it:

```explorer
sampling
```

- **Your code** owns everything else: what goes into the prompt (retrieval, history, tools'
  results), when to stop, what to do with the output, whether to trust it. Every production
  pattern in Modules 4–9 is a way of putting the right thing in the prompt and checking what
  comes out.

```check
Which component decides that the answer will be 'the' rather than 'a' at a given step?
- The model
- * The sampler
- The tokeniser
- The retriever
why: The model outputs a distribution; the sampler picks from it. Temperature and top-p live there (Lesson 2.7) and change variety, not knowledge.
```

> **Production tip.** When something goes wrong, locate it in the loop before you reach for a
> fix. "It made up a policy" is a *prompt content* problem (the policy was not in the
> context) or a *verification* problem (nothing checked the answer) — not a "model is dumb"
> problem that a firmer instruction will cure.

## What a senior engineer should take from this

- **The definition is the mental model.** Next-token predictor, run in a loop. Everything else
  is consequence.
- **Fluency is not evidence.** The model's confidence is the same whether it is right, wrong or
  inventing.
- **Knowledge lives in the model; facts you care about must live in the prompt** — or be
  checked by code afterwards. That sentence is most of Module 6 and Module 8.
- **Separate the model, the sampler and your code** when diagnosing behaviour. Most fixes are
  in your code.

## Exercises

1. Explain to a colleague, in under a minute and without the word "understand", what an LLM
   does. Then explain hallucination using only that definition.
2. In the example, change `max_tokens` / `maxTokens` to 40. What happens to the greedy output?
   Now change the tie-break rule (alphabetical) to prefer the *first* seen. Does the loop still
   cycle? Why is repetition a structural risk of greedy decoding?
3. Add a third-order model (look at the previous *two* words). Does the "no-lookup" prompt still
   get a fluent continuation? What does that tell you about scaling up context vs. scaling up
   truthfulness?
4. Take three surprising LLM behaviours you have personally seen. Place each in the loop
   diagram: model, sampler, or your code? What would the fix be in each box?

## Model answers (sketch)

1. "It predicts the most plausible next word, over and over. When it lacks grounds it still
   predicts something plausible — that's a hallucination."
2. Longer output cycles longer; changing the tie-break changes *which* cycle, not whether
   there is one. Greedy decoding has no source of variety, so any repeated state repeats forever.
3. Yes — it just needs a two-word suffix it has seen. More context makes continuations more
   fluent and specific; it does nothing to make them true. Truth needs grounding (Module 6).
4. Typical: made-up API → model (fix: retrieval or a docs tool); different answers between
   runs → sampler (fix: lower temperature *and* evals that tolerate variance); truncated JSON →
   your code (fix: max-tokens, schema validation, retry).
