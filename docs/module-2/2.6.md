## The one idea

Nobody writes rules into a language model. It is trained in three stages, and each stage
leaves a fingerprint you will meet in production:


## Stage 1 — pretraining: where the capability comes from

Take a very large pile of text — web pages, books, code, papers, forums — and train the network
on one task: **predict the next token.** Trillions of times. That is Lesson 2.1's function,
learned by gradient descent (Lesson 1.2) at industrial scale: months, thousands of GPUs, tens
of millions of dollars.

The result is a **base model**. It is startlingly capable — it has absorbed grammar, facts,
code idioms, reasoning patterns, tone — and completely unhelpful as a product. Ask it a
question and it may continue with three more questions, because on the internet questions are
often followed by questions.

Two facts you live with forever are set here:

- **The knowledge cutoff.** The training pile stopped on a date. Anything after it — new
  libraries, your company, last week's news — is not in the weights. It can only come from
  the prompt.
- **What is common is learned well; what is rare is learned fuzzily.** Popular languages,
  mainstream APIs and famous facts are solid. Niche frameworks, small towns, and specific
  citations are where confident invention lives.

## Stage 2 — supervised fine-tuning: the chat shape

Show the base model tens of thousands of examples of *(prompt, ideal answer)*, written or
curated by people, and train it to imitate them. Now it answers questions instead of
continuing them, follows a format, adopts a helpful voice. This is cheap by comparison —
days, not months — and it is also what "fine-tuning your own model" means in Module 10:
the same step, on your examples.

## Stage 3 — preference tuning: manners, and the urge to please

Generate several answers to a prompt, have humans (or a model trained to imitate humans)
**rank** them, and train the model to produce the preferred kind. Under the names RLHF, DPO
and relatives, this is what makes a model helpful, polite, hedged, safe-ish — and it has
side effects every engineer should know:

| Side effect | Why | What you see |
|---|---|---|
| **Eager to answer** | answers that decline are ranked below answers that help | it answers even when it should say "I don't know" |
| **Sycophancy** | agreeable answers are rated higher | it agrees with a wrong premise in your question |
| **Verbosity and hedging** | thorough, caveated answers rate well | padding, "It's important to note…" |
| **Refusals with false positives** | safety training generalises broadly | it declines something harmless |
| **Format obedience** | formatted answers rate well | good: JSON, lists; bad: invents structure when asked for "the value" |

None of these is a bug in *your* prompt; they are behaviours the model was optimised for. You
can push against them with prompting (Module 4) and constrain them with structure and code —
but you cannot instruct them away.

## Why "just tell it not to hallucinate" fails

Put the three stages together with Lesson 2.1:

- The model produces the most plausible continuation (stage 1).
- It has been trained to be helpful and to answer in the expected shape (stages 2–3).
- Nothing in that pipeline represents *the absence of knowledge* as a first-class thing.

So "answer only if you are sure" is itself just text that shifts the distribution a little. It
helps at the margin. It does not create a knowledge check. **The reliable fixes are outside
the model:** put the facts in the prompt (RAG, Module 6), constrain the output (structured
output, Lesson 4.3), verify with code or a second model (Module 8), and give it a real way to
decline (a `not_found` field, a refusal path).

## What a prompt can and cannot change

A useful rule of thumb for design reviews:

| Set by | Examples | Changeable by a prompt? |
|---|---|---|
| Pretraining | what it knows, the cutoff, how well it codes in Rust vs Python | No — supply context or pick another model |
| Fine-tuning | chat format, general helpfulness, language of response | Somewhat — format and tone are steerable |
| Preference tuning | refusals, hedging, agreeableness | At the margin — expect drift; constrain in code |
| The sampler | variability | Yes — temperature, top-p (Lesson 2.7) |
| Your code | what is in the prompt, what is done with the answer | Entirely |

## What a senior engineer should take from this

- **Capability comes from pretraining; behaviour from tuning.** Both are fixed when you get
  the model.
- **The cutoff and the fuzziness on rare things are structural.** Supply what matters in the
  prompt.
- **The model wants to answer.** Design a way for it to say no, and verify what it says yes to.
- **Instructions steer; they do not enforce.** Enforcement lives in schemas, code and evals.

## Exercises

1. A stakeholder asks why the model "knew" your competitor's pricing from two years ago but
   not your own current pricing. Answer in three sentences using the stages.
2. Find a question where you can lead the model into agreeing with a false premise ("Since
   Python is compiled to native code by default, …"). What does that tell you about how to
   phrase questions in a pipeline that other code depends on?
3. For each of these, decide whether prompting, code, or a different model is the right lever:
   (a) it keeps adding "Certainly!"; (b) it invents a library function; (c) it refuses to
   summarise a security advisory; (d) it answers in English when the user wrote French.
4. Sketch the "I don't know" path for a support assistant: what does the model return, what
   does your code do with it, and how do you measure how often it fires correctly?

## Model answers (sketch)

1. Public, widely-repeated text before the cutoff is in the weights; your current pricing is
   post-cutoff and private, so it can only come from the prompt — retrieval, not the model.
2. Sycophancy: models tend to accept premises. In pipelines, state facts as context and ask
   neutral questions; never embed assumptions you want checked.
3. (a) prompt/format; (b) code: retrieval of real docs + a tool that checks symbols exist;
   (c) prompt with context, or another model/version; (d) prompt — set language explicitly.
4. Structured output with `answer | not_found` and a confidence field; on `not_found`, escalate
   or ask a clarifying question; measure precision/recall of `not_found` on a labelled set
   (Lesson 8.2).
