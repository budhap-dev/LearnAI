## The one idea

An **embedding** is a list of numbers — a vector, typically 256 to 3,072 long — that stands for
a piece of text. It is produced by a model trained so that texts with similar *meaning* get
vectors that point in similar *directions*. Once text is geometry, "how related are these
two things?" becomes arithmetic:

```diagram
vector-space
```

The arithmetic is **cosine similarity**: the cosine of the angle between two vectors. 1.0 is
"same direction", 0.0 is "unrelated", and in practice useful values live between roughly 0.3
and 0.9. That single number is the primitive under semantic search, retrieval-augmented
generation, clustering, near-duplicate detection and cheap classification.

> **In one sentence:** embed everything once, then compare vectors instead of text.

## Try it first

```explorer
embeddings
```

Notice that "street food in Bangkok" sits *between* the food and travel groups, and "a horse
race at Ascot" between animals and sport. Meaning is a position, not a label — a text can be
partly about several things, and the vector says how much of each.

### Cosine similarity

```code
cosine
```

Dot product over the product of lengths. Length is deliberately ignored: a word that appears
twice as often should not look "more similar" to everything, and a long document should not
outrank a short one just for being long.

Score the query against every candidate, take the top *k*. That is semantic search. Real
systems replace the linear scan with an approximate index once there are millions of vectors
(Lesson 6.4), and they embed passages of a few hundred tokens rather than single words — but
the question asked is exactly this one.

## What embeddings are for

| Use | How it works | Where it appears |
|---|---|---|
| **Semantic search** | embed the query, find nearest documents | anywhere keyword search misses paraphrases |
| **RAG** | search first, then put the hits in the prompt | Module 6 — the main use in LLM systems |
| **Clustering / topic discovery** | group nearby vectors | support-ticket themes, log triage |
| **Near-duplicate detection** | very high similarity → probably the same thing | dedup, cache hits for similar prompts |
| **Cheap classification** | nearest labelled example wins | routing, intent detection without an LLM call |

Embedding a query costs a fraction of a generation call and takes milliseconds. A surprising
share of "AI features" are an embedding plus a nearest-neighbour lookup and no LLM at all.

## What similarity does *not* mean

```output
limits
```

`chased` is as close to `cat` as `dog` is. Cosine similarity says "these appear in similar
contexts", which is often meaning, sometimes just topic, sometimes just grammar. Two hard
rules follow:

```check
You switch embedding models but keep the stored vectors and the 0.75 threshold. What breaks?
- Nothing — cosine is model-independent
- * Everything — new queries live in a different geometry from the old vectors, and the threshold no longer means anything
- Only long documents
why: Same model, same version on both sides. Changing the model means re-embedding everything and re-measuring thresholds.
```

1. **A similarity score is a ranking signal, not a truth signal.** "The nearest document
   scored 0.82" tells you it is the best of what you have. It does not tell you it answers
   the question, or that any document does. RAG systems that skip this thought return
   confident answers from irrelevant context (Lesson 6.6).
2. **Scores are not comparable across models, and thresholds are not portable.** Each
   embedding model has its own geometry: 0.8 from one may be 0.5 from another. Choose
   thresholds by measuring on your own data (Lesson 6.7), and re-measure when you change the
   model.

Two further limits engineers trip over:

- **Negation and specifics wash out.** "Reset password" and "cannot reset password" embed
  close together; so do "flight to Lisbon on the 3rd" and "on the 13th". Embeddings capture
  the gist. Exact constraints belong in a filter or a keyword match, alongside the vector
  search — that is why hybrid search exists (Lesson 6.4).
- **A vector has no idea what it did not see.** New product names, internal jargon and
  post-cutoff terms embed poorly. Domain adaptation (Lesson 10.5) or keyword fallbacks fix it.

## Practical notes for building

- **Same model on both sides.** Query and documents must be embedded by the *same* model and
  version, or the geometry does not line up. Store the model name with the vectors.
- **Chunk before embedding.** A 30-page document as one vector is an average of everything in
  it. Embed passages (Lesson 6.3).
- **Normalise once.** Most providers return unit-length vectors; if not, normalise at write
  time so cosine becomes a plain dot product.
- **Dimensions are a cost knob.** More dimensions ≈ slightly better ranking, more storage,
  slower search. Many models let you truncate; measure before you pay for the full width.
- **Embeddings leak content.** A vector can be inverted to approximate the text. Treat vector
  stores with the same access controls as the documents.

## What a senior engineer should take from this

- **Embedding + nearest neighbour is the cheapest, most reliable "AI" primitive you have.**
  Reach for it before a generation call.
- **Cosine similarity ranks; it never proves.** Every downstream step must remember that.
- **Same model both sides, chunk first, measure thresholds on your data.**
- **Gist in, gist out.** Exact constraints go in filters and keyword search, not vectors.

## Model answers (sketch)

1. Anything with two strong dimensions — e.g. "a horse race at Ascot" (animals + sport) —
   whose neighbours split across groups; the vector is a blend and the plot is a projection.
2. One vector for two meanings — a blur of both. Sentence/passage embeddings are computed *in
   context* so each occurrence gets its own vector; that is why real systems embed passages.
3. Thresholds are model-specific; scores rank rather than verify; negation/specifics wash out;
   FAQ coverage gaps mean "best match" ≠ "a match". Measure precision/recall of the rule on a
   labelled set of real questions (Lesson 6.7).
4. Vector, model name + version, source id, chunk offset, text, metadata for filters, updated
   time. If the model changes, every vector must be regenerated or queries will not line up.
