## The one idea

Everything in Module 2 so far converges on one design question: **for this task, where would
the model's answer come from — and can I tell?**

```diagram
knows-vs-guesses
```

The four columns sound identical. A model has no reliable internal signal for which one it is
in, and neither do you from reading the answer. So reliability has to be *designed*: put what
matters in the prompt, verify what comes out, and keep the model to the jobs it is
structurally good at.

## What LLMs are reliably good at

These are the capabilities you can build on with ordinary engineering care — good prompts,
structured output, evals:

| Capability | Why it works | Typical uses |
|---|---|---|
| **Transforming text** — summarise, rewrite, translate, change tone, change format | the answer is fully determined by the input in the prompt | summaries, drafts, localisation, style |
| **Extracting structure from text** | again, the facts are in the prompt | tickets → fields, contracts → clauses, logs → incidents (Lesson 4.3) |
| **Classifying and routing** | pattern recognition over meaning | intent, sentiment, triage, moderation |
| **Answering from provided context** | attention over the passage (Lesson 2.4) | RAG (Module 6) — the workhorse |
| **Writing and reviewing code in mainstream languages** | vast training data; tests can verify | assistants, migrations, review (Lesson 11.1) |
| **Following a multi-step procedure with tools** | plan-in-text plus function calls | agents (Module 7) — with guardrails |
| **Reading images and documents** (multimodal models) | same next-token machinery over image tokens | OCR-ish tasks, screenshots, charts, forms (Lesson 5.4) |
| **Reasoning through a problem in writing** | "thinking" tokens let it work incrementally | maths, planning, analysis — with limits below (Lesson 4.5) |

The common thread: **the model has what it needs in front of it, and the output can be
checked** — by a schema, a test, a source passage, or a person.

## Where they fail — and why

| Failure | Mechanism (which lesson) | Design response |
|---|---|---|
| **Fabricated facts, citations, APIs** | plausible continuation without grounds (2.1, 2.6) | supply sources; require citations; verify symbols exist |
| **Confident about post-cutoff or private things** | not in the weights (2.6) | retrieval; tell it the date; refuse without context |
| **Character-level tasks** — counting letters, exact lengths, reversing | tokens, not characters (2.2) | do it in code |
| **Arithmetic and exact logic at scale** | next-token, not a calculator | tools: calculator, code execution, database |
| **Very long inputs: middle gets lost** | attention dilution and position (2.4, 2.5) | retrieve, chunk, put key facts at the edges |
| **Different answer each run** | sampling (2.7) | schemas, retries, evals on rates |
| **Agrees with a false premise** | preference tuning (2.6) | neutral phrasing; verify premises in code |
| **Injection: follows instructions inside data** | it cannot tell your prompt from a pasted email (4.6, 9.5) | trust boundaries, least privilege for tools |
| **Miscalibrated confidence** | no first-class "I don't know" (2.6) | explicit `not_found` outputs; measure precision of refusals |

Two of these deserve a closer look because engineers most often misjudge them.

### Calibration: the tone is flat

A model's phrasing does not track its reliability. A hedged answer can be right; a crisp one
can be invented. Some models expose token-level probabilities, and low probability on key
tokens is a *weak* signal — but the practical stance is: **treat all outputs as unverified
until something other than the model checks them.** Where the cost of error is real, that
"something" is a source passage, a test suite, a schema, a second model with a rubric, or a
human (Module 8).

### "Reasoning" helps, and has edges

Models that write out intermediate steps (and the "thinking" budgets exposed by newer APIs)
genuinely improve results on maths, planning and multi-constraint tasks. They are still
next-token predictors: reasoning is text that conditions later text. It fails on problems that
need exact search over many possibilities, it can rationalise a wrong answer fluently, and it
costs tokens and latency. Use it where the task is genuinely multi-step; measure whether it
pays; and still verify (Lesson 4.5).

## The rule for dividing the work

If one rule survives this lesson, make it this:

> **Judgement over meaning → the model. Exactness, facts and side effects → code.**

- The model decides *what a customer is asking*; code looks up the order.
- The model drafts the SQL; code runs it read-only and checks the row count.
- The model extracts the date from an email; code validates it is a date and in range.
- The model proposes a refund; code checks policy and a human approves over a threshold.

Every reliable LLM feature you will build has that shape. Every incident you will read about
is a case where the model was left holding the second half.

## Choosing a model — the questions that matter

Capabilities differ across models and versions, and change monthly; the
[model reference](#/reference/models) is the dated place for specifics. The questions are
stable:

1. **Does it do the task well on *my* data?** — run a small eval (Lesson 8.2) before believing
   a leaderboard.
2. **Context length, modality, tool calling, structured output** — features you need, not
   features it has.
3. **Latency and cost at my volume** — time to first token, tokens/second, price per million
   in and out (Lesson 9.3, 9.4).
4. **Hosting, data handling, region** — where does the prompt go (Lesson 9.6).
5. **Version pinning and deprecation policy** — can it change under you (Lesson 9.8).

Smaller and cheaper models are usually enough for classification, extraction and routing;
save the large ones for judgement-heavy work — and route between them (Lesson 5.6).

## What a senior engineer should take from this

- **Provenance decides trust; tone tells you nothing.** Design so the answer's source is the
  prompt or is verified afterwards.
- **Reliable: transform, extract, classify, answer from context, code with tests.
  Structural weak spots: facts from memory, characters, arithmetic, exact search, huge
  inputs, side effects.**
- **Judgement to the model, exactness and side effects to code.**
- **Evaluate on your data; the model is a component, not an oracle.**

## Exercises

1. Take five features your team has discussed adding "with AI". Sort each into the capability
   table or the failure table, and write the one-line design response.
2. Write down the "I don't know" contract for one of them: what the model returns, what code
   does with it, and how you would measure false negatives and false positives.
3. Find a question that a model answers confidently and wrongly (a niche API, a small-town
   fact, a paper title). Then rewrite the interaction so the wrong answer is impossible to
   return without being caught. What did you add?
4. Draft the model-selection section of an ADR for a document-extraction feature: which of the
   five questions matter most here, and what eval would you run before choosing?

## Model answers (sketch)

1. Typical: "summarise tickets" → transform (reliable); "answer billing questions" → answer
   from context (RAG + citations); "detect duplicate bugs" → embeddings, not generation;
   "compute refunds" → code with model-drafted reasoning; "auto-reply to security reports" →
   route to a human.
2. Structured `{status: found|not_found, answer, sources}`; on `not_found` escalate; measure
   against a labelled set where you know which questions are answerable.
3. Retrieval of the real source and a citation requirement; or a tool that checks the API
   symbol / paper exists; or a schema field the code validates. You added *ground truth from
   outside the model*.
4. Task quality on your documents (run 50 real ones through two or three models with a
   schema), structured-output support, cost at volume, data-handling. Leaderboards last.
