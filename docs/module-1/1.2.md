## The one idea

Nobody programs a model's behaviour. A model is **a function with numbers in it** — the
*parameters* — and training is the process of choosing those numbers so the function's
outputs match known examples. That is all "learning" means here:

```diagram
train-vs-infer
```

The left side runs once (or occasionally) and is expensive. The right side runs on every
request and is comparatively cheap. **An API call to a model is always the right-hand
path** — no learning happens when you call it, whatever the marketing implies.

### Loss: how wrong are we?

Training needs a single number that says how bad the current parameters are on the known
examples. That number is the **loss**. Here, mean squared error — the average squared gap
between prediction and truth:

```code
loss
```

For an LLM the loss is "how much probability did you put on the actual next token" over
trillions of tokens (Lesson 2.6). Different formula, same job: one number to make small.

### Gradient: which way is less wrong?

```code
gradient
```

The gradient says how the loss changes if each parameter nudges up. Move *against* it and the
loss goes down. For two parameters you can write the calculus by hand; deep learning
frameworks compute the same thing automatically for billions of parameters — that automation
(back-propagation) is most of what a framework *is*.

Watch the loss fall: 459 → 74 → 28 → … → 0.09. That column going down is what "training" looks

```check
A model has been trained and deployed. A user's request comes in. What does the model do with it?
- Learns from it and updates its parameters
- * Evaluates its frozen function on the input and returns the output
- Compares it against the training set and returns the closest example
why: Inference does no learning. Parameters are frozen at deployment; every request just runs the function. Anything that looks like "remembering" is your code re-sending context.
```

## Inference: calling the function

```output
after
```

Once trained, `predict` is just a function. It does not learn from being called. It also
happily answers for inputs it never saw — `predict(12)` extrapolates a line past the data —
which is either exactly what you want (generalisation) or a confident guess with no grounds
(Lesson 2.8). The model cannot tell you which; the data can.

## The learning rate, and hyperparameters generally

```output
learning-rate
```

The learning rate is not learned — it is chosen. Too small and training crawls; too big and it
overshoots and blows up. Settings like this are **hyperparameters**: knobs set by trying,
measuring and keeping what works. Model size, training length, batch size, temperature at
inference (Lesson 2.7) — all hyperparameters. When an ML colleague says "we swept the
learning rate", this is what they mean.

```check
Training loss stopped improving after step 500 in the example. What has happened?
- The model has memorised the data
- * The parameters are near the bottom of the loss surface — further steps change little
- The learning rate was too high
why: The characteristic curve — fast improvement, then a long flat tail — means the optimiser has found the valley. Whether that fit generalises is a separate question answered on held-out data (Lesson 3.3).
```

## Scaling the picture up

Everything below is the same loop, bigger:

| | This example | A gradient-boosted tree | An LLM |
|---|---|---|---|
| Parameters | 2 | thousands (tree splits) | billions to trillions |
| Known examples | 8 pairs | rows of a table | trillions of tokens of text |
| Loss | mean squared error | log-loss / squared error | next-token cross-entropy |
| Training cost | microseconds | seconds to hours on a CPU | months on thousands of GPUs |
| Inference cost | nanoseconds | microseconds | milliseconds to seconds per token |
| Who trains it | you, in a script | you, in a notebook | a lab; you fine-tune at most (Module 10) |

The economics fall out of the last three rows: **training is rare and enormous, inference is
constant and metered.** That is why "can we teach it our data at runtime?" is the wrong
question (you supply context at inference — Module 6), why model versions change under you
(someone retrained), and why fine-tuning is a project, not a config change.

## What a senior engineer should take from this

- **A model is a function with numbers in it; training chooses the numbers.** Loss measures
  wrongness; the gradient says which way; the loop repeats.
- **Training and inference are different operations with different costs and owners.** API
  calls are inference. Nothing learns from your requests.
- **The loss curve shape is universal**: fast, then flat. "Done training" means "the curve is
  flat", not "the model is right".
- **Hyperparameters are chosen by measuring**, not derived. Expect that habit everywhere in
  this course.

## Model answers (sketch)

1. The line tilts toward the outlier — squared error punishes big misses hard. A different
   loss (absolute error) or outlier removal would resist it. The loss encodes what "wrong"
   means; choose it deliberately.
2. Around 0.02–0.03; the *b* direction is shallow because the data's x-values are small, so
   b's gradient is small — hence per-parameter step sizes in real optimisers.
3. (a) No — inference only; a correction only helps if you log it and someone retrains or you
   feed it back as context. (b) Yes, at the next weekly training run, if corrections enter the
   training data. (c) Not the model; but the corrected document can be indexed immediately, so
   the *system* improves.
4. Training changes the parameters (rare, expensive, someone else's process); giving documents
   means putting them in the prompt at inference (Module 6) — the model reads them each time
   and forgets them after.
