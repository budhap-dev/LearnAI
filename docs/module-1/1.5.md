## The one idea

It helps to see the whole stack once, if only to know which parts are not your job:

```diagram
ai-stack
```

Most product engineering happens in the top two layers. You *buy* the model layer (via an API
or by downloading weights), you *rent* the hardware (through the API's price or a cloud GPU),
and you almost never touch training and data except to fine-tune (Module 10). But each lower
layer leaks into your work in a specific way, and that is what this lesson is for.

> Names change monthly. This lesson describes *kinds* of things; the
> [model reference](#/reference/models) is the dated place for who currently offers what.

## The layers, and how each one reaches you

**Hardware.** GPUs and other accelerators, their memory, and the networking between them.
You never see it — but it is why inference is metered per token, why long prompts cost
latency, why capacity is rationed with rate limits, and why "just self-host it" is a capacity
plan and a bill, not a download.

**Training & data.** Pretraining corpora, instruction datasets, human preference data
(Lesson 2.6). Reaches you as: the knowledge cutoff, the model's strengths and blind spots, and
its licence terms. When a vendor ships a new version, this layer changed — and your evals
should notice (Module 8).

**Models.** Four kinds you will choose between:

| Kind | What it is | Fits when |
|---|---|---|
| **Frontier hosted** | the largest closed models, API only | hardest judgement tasks, agents, code; you can accept a hosted dependency |
| **Open-weight** | weights you can download and run (licences vary — read them) | data must stay in-house, cost at scale, customisation, no vendor lock |
| **Small / specialised** | 1–10B-parameter models, often fine-tuned for a task | classification, extraction, routing, on-device; latency and cost matter |
| **Embedding models** | text → vector (Lesson 2.3) | search, RAG, clustering, dedup — usually alongside one of the above |

"Open" needs care: *open weights* means you can run it; the training data and recipe may
still be closed, and the licence may restrict commercial use. Check before you build on it.

**Model APIs & serving.** How you reach a model: a vendor's own API, the same models resold
through cloud platforms (with regional hosting and enterprise contracts), or an inference
server you run on GPUs you rent. This layer sets latency, throughput, rate limits, data
handling, region and price — Module 9's concerns.

**Orchestration & tooling.** Retrieval and vector stores, tool/function calling and MCP,
gateways, caching, evals, tracing, guardrails, and the frameworks that bundle them. This is
where most engineering effort goes and where the choices are yours (Modules 4–9; Lesson 11.4
on frameworks).

**Applications & agents.** Your product. Assistants, copilots, extraction pipelines, agents
with tools. Everything above supports this.

```check
A team says "we'll self-host an open model to avoid vendor costs". Which layer did they just take ownership of, and what does it involve?
- Only the model layer — download the weights and call them
- * The serving and hardware layers too — GPUs, capacity planning, an inference server, scaling, upgrades and on-call
- Nothing extra — open models run on ordinary web servers
why: Self-hosting moves you down the stack. It can be right for privacy, scale economics or control, but it is an operations commitment, not a download.
```

## Hosted or self-hosted — the paragraph

Hosted APIs give you the strongest models, elastic capacity, no GPU operations, and fast
access to new versions — at a per-token price, with a data-handling and dependency question
to answer, and versions that change under you. Self-hosting an open-weight model gives you
control over data, version and cost at high volume — in exchange for GPU capacity, serving
infrastructure, on-call, and usually a weaker model. Most teams start hosted, put a gateway
in front (Lesson 9.2) so the choice is reversible, and self-host only a specific workload
where privacy or unit economics force it. That is the ADR in one paragraph; Lesson 9.6 and
10.4 fill in the detail.

## Who the players are — as kinds, not names

- **Frontier labs** train the largest models and sell API access; they set the capability
  ceiling and change it several times a year.
- **Cloud platforms** resell those models (and their own) with enterprise wrapping — regions,
  contracts, identity, billing you already have.
- **Open-weight publishers** release models you can run — some labs, some companies, some
  communities.
- **Inference providers** host open-weight models behind APIs cheaply and fast.
- **Tooling vendors** sell the orchestration layer: vector stores, eval platforms,
  observability, gateways, agent frameworks.
- **You** — the application layer, and the integrator of all of the above.

```check
Your compliance team requires that customer text never leaves your cloud region. Which options survive?
- Only self-hosting
- * Self-hosting, or a hosted model offered through a cloud platform with in-region processing and a suitable data agreement
- Any vendor API — prompts are not stored
why: Region and data handling are properties of the serving layer. Cloud-platform offerings often satisfy them without self-hosting; check the contract, not the marketing.
```

## What a senior engineer should take from this

- **You build in the top two layers and buy the rest** — but each lower layer reaches you as
  cost, latency, limits, cutoffs, licences or version changes.
- **Four kinds of model**: frontier hosted, open-weight, small/specialised, embedding. Most
  systems use two or three.
- **Hosted first, gateway in front, self-host by exception.** Write the ADR.
- **Read the licence and the data terms**, not the launch post.

## Exercises

1. For a product you know, list which layer each of its AI dependencies sits in and whether
   it is built, bought or rented.
2. Write the hosted-vs-self-hosted paragraph for your own context: what would force you down
   the stack?
3. Pick a small task (classify support tickets into 6 categories). Argue for a small model
   over a frontier one, then argue the reverse. Which argument needs data to settle?

## Model answers (sketch)

1. Typical: vector DB (tooling, bought), embedding model (model, rented via API), frontier
   chat model (rented), gateway (tooling, built), eval harness (tooling, built).
2. Usually data residency, volume × price crossing a threshold, or the need to pin a version
   forever. Absent those, hosted wins on capability and operations.
3. Small: cheaper, faster, can be fine-tuned, on-prem. Frontier: better zero-shot, no training
   needed, handles the long tail. Settle with an eval on real tickets (Lesson 8.2).
