## The one idea

"AI" is not one thing. It is a nested family of approaches to making software do tasks that
look like they need judgement, and the rings matter because **each ring changes what you can
promise, how you test it, and what goes wrong**:

```diagram

```

- **Artificial intelligence** — the outer term. Includes things with no learning at all: rule
  engines, search, planners, expert systems. A chess program from 1997 is AI.
- **Machine learning** — behaviour learned from data instead of written by hand. Regression,
  decision trees, gradient boosting, clustering. Most "AI in production" for the last decade
  has been this: fraud scores, recommendations, demand forecasts.
- **Deep learning** — machine learning using neural networks with many layers. Won because it
  scales with data and compute: vision, speech, embeddings, and everything below.
- **Generative AI** — deep learning models that *produce* content: text, code, images, audio.
  Large language models sit here, and so does most of this course.

The rings are subsets. Everything an LLM does is deep learning, is machine learning, is AI —
but a rule-based fraud check is AI without being any of the inner rings.

## Rules you write versus behaviour a model learns

The single most useful distinction, because it decides how you build and test:

| | **Rules** (classic software) | **Learned behaviour** (ML, LLMs) |
|---|---|---|
| Where the logic comes from | you wrote it | a training process found it in data |
| Behaviour on a new input | exactly what the code says | whatever the learned function outputs — plausible, not guaranteed |
| Testing | assert exact outputs | measure rates on a set of examples |
| Explaining a decision | read the code | partial at best; the "reason" is a pattern in weights |
| Changing behaviour | edit the code | change data, retrain/fine-tune, or change the prompt |
| Failure looks like | a bug, reproducible | a wrong answer that sounds right, often not reproducible |

Both are legitimate. The mistake is applying the habits of one to the other: unit-testing a
model with exact string matches, or hand-writing rules for a problem with a thousand
exceptions that a model would learn in an afternoon.

```check
A vendor says their product "uses AI" to route support tickets. What have you learned about how it works?
- It uses a large language model
- It uses machine learning trained on past tickets
- * Almost nothing — "AI" spans hand-written rules to LLMs; ask which ring and what data
why: The term is a family name. The useful questions are: is the behaviour written or learned, from what data, and how is it evaluated?
```

## The questions to ask when someone says "let's use AI"

For an engineer, "use AI" is a category, not a design. Turn it into one with five questions:

1. **Is this even a learning problem?** If the rule can be written and the exceptions are few,
   write the rule. It will be faster, cheaper, testable and explainable.
2. **Which ring?** A gradient-boosted tree on tabular data and an LLM over free text are as
   different as a SQL query and a message queue. Lesson 3.1 is the decision.
3. **What data do we have — and what does "correct" mean?** ML needs examples; LLM features
   need context and evaluation sets. If nobody can say what a right answer looks like, nobody
   can measure whether the feature works (Module 8).
4. **What happens when it is wrong?** Every learned component is wrong sometimes. Where does
   the wrong answer go — a human, a validator, a customer? (Lesson 1.6.)
5. **What does it cost per call and per month?** Rules cost nothing per call. Models cost
   tokens, GPUs or both, every time (Lesson 2.2, 9.4).

```check
A team wants "AI" to check that uploaded invoices have a VAT number in a valid format. What is the right first answer?
- Fine-tune a small model on invoices
- Use an LLM with a careful prompt
- * A regular expression — the rule is known and the exceptions are few
why: Not every judgement-shaped task needs learning. When the logic can be written, write it: cheaper, faster, testable, explainable.
```

## Why this course is mostly about LLMs — and not only

Generative AI is the ring where the recent capability jump happened and where most new
software features are being built, so Modules 2 and 4–9 focus on LLMs. But the outer rings
did not go away: Module 3 covers the classic ML you will meet in any data-heavy product, and
Lesson 3.1 argues that a surprising number of "AI features" should be a regression, a
classifier or a nearest-neighbour lookup rather than a generation call.

## What a senior engineer should take from this

- **"AI" is a family name.** Ask which ring, whether behaviour is written or learned, and from
  what data.
- **Written rules and learned behaviour need different testing, explanation and change
  processes.** Do not mix the habits.
- **Not every judgement-shaped task needs learning.** If you can write the rule, write it.
- **The five questions** — learning problem? which ring? what data / what is "correct"? what
  happens when wrong? what does it cost? — turn "use AI" into a design.

## Exercises

1. Take three "AI" features from products you use. Place each in a ring and say what
   evidence you used.
2. Rewrite the table above from memory, then add a row for "how you roll back a bad change".
3. For a feature you are considering, answer the five questions in writing. Which one was
   hardest? That is where the design risk is.
