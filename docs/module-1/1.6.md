## The one idea

The failure stories are always told as "the AI did X". Useful engineering starts by asking
**where X came from**:

```diagram
failure-taxonomy
```

- **From the model** — structural properties of how it works. You design *around* these; no
  prompt removes them.
- **From the input** — what you gave it, or what an attacker gave it. Engineered away with
  retrieval, budgets, trust boundaries.
- **From the system** — cost, latency, truncation, versions, missing evals. Operated: metrics,
  budgets, gates.
- **From the organisation** — no owner, no eval, over-trusted demos, no rollback. Process.

Most incidents are blamed on the first column and caused by the other three.

## From the model — one sentence each

| Failure | One sentence | Design around it |
|---|---|---|
| **Hallucination / fabrication** | the model produces the most plausible continuation whether or not it has grounds (Lesson 2.1) | put facts in the prompt; require citations; verify in code; give it a way to say "not found" |
| **Knowledge cutoff** | anything after training, or private, is not in the weights (Lesson 2.6) | retrieval; tell it the date; refuse without context |
| **Bias** | it reproduces patterns — including unfair ones — in its training data and its labels | evaluate across groups; keep humans on consequential decisions; document known gaps |
| **Character & arithmetic weakness** | it predicts tokens, not letters or numbers (Lesson 2.2) | code and tools for exactness |
| **Non-determinism** | outputs are samples; even at temperature 0 they drift (Lesson 2.7) | schemas, retries, evals on rates |
| **Miscalibrated confidence** | tone does not track correctness (Lesson 2.8) | verification, not vibes |

```check
A model states a plausible but false product spec in a customer chat. Which column, and what is the fix?
- Model — switch to a bigger model
- * Model behaviour, but the fix is input and checks: retrieve the real spec into the prompt, require the answer to cite it, refuse otherwise
- Organisation — train the support team to apologise
why: Fabrication is structural; you cannot instruct it away. You design around it by controlling what the model sees and checking what it says.
```

## From the input

| Failure | One sentence | Fix |
|---|---|---|
| **Prompt injection** | the model cannot tell your instructions from instructions hidden in data it reads — an email, a web page, a document (Lesson 4.6, 9.5) | treat all model-read content as untrusted; least-privilege tools; approval gates for side effects |
| **Missing context** | it was never told the thing you needed it to know | retrieval; look-ups in code; better prompt assembly |
| **Ambiguous asks** | garbage question, plausible answer | clarify before acting; structured intake |
| **Stale or wrong retrieval** | the right-looking chunk from the wrong document (Lesson 6.6) | retrieval evals; citations; freshness |
| **Too much context** | the middle gets lost, cost climbs (Lesson 2.5) | budget; retrieve less, better |

Prompt injection deserves emphasis because it is *new*: your code has never before had a
component that reads data and might obey it. Any system that lets a model read untrusted
content **and** take actions has an injection surface. Module 9 treats it as the security
problem it is.

## From the system

| Failure | One sentence | Fix |
|---|---|---|
| **Cost blow-up** | tokens × traffic × a loop nobody bounded | budgets per request and per day; caching; routing (Lesson 5.6, 9.4) |
| **Latency & timeouts** | tokens in and out both take time; chains multiply it | streaming; smaller prompts; parallel calls; timeouts with fallbacks (Lesson 9.3) |
| **Silent truncation** | something dropped part of the prompt or the answer and nobody logged it | explicit budgets and `finish_reason` in logs (Lesson 2.5) |
| **Model changed under you** | the vendor shipped a new version; behaviour shifted | pin versions; run evals on upgrade; canary (Lesson 9.8) |
| **No evals** | you cannot tell a fix from a regression | a golden set from day one (Module 8) |

```check
Your monthly bill tripled with no traffic increase. Most likely cause?
- The model got more expensive overnight
- * Something in your system now sends more tokens per request — longer history, more retrieval, a retry loop, or an agent that stopped terminating
- Users are typing longer messages
why: Cost is tokens × calls. Sudden multiples are almost always a system change: unbounded history, a retry storm, a loop. Log tokens per part per request and alert on p95.
```

## From the organisation

These are not technical, and they cause the most expensive failures:

- **No owner for the prompt.** It lives in a string, edited by whoever, with no version and
  no test. (Lesson 4.4.)
- **No eval before launch.** The demo looked great on five examples; production sees five
  thousand. (Lesson 8.1.)
- **Over-trusting demos.** Fluency is persuasive; the confidence in the room is not evidence.
- **Privacy and compliance gaps.** Prompts contain customer data; where does it go, how long
  is it kept, who can see the logs? (Lesson 9.6.)
- **No rollback plan.** Prompt, model and retrieval index are all versions; can you revert
  each?

## The one thing to write down before you build

Every AI feature should have a sentence in its design doc that starts **"When the model is
wrong, …"** — and finishes with a specific path: a validator rejects it, a human reviews it,
the user sees a hedge with a source, the action is not taken. If nobody can complete the
sentence, the feature is not designed yet. Lesson 11.2 turns this into the one-page design
doc; everything between here and there is how to make each answer true.

## What a senior engineer should take from this

- **Sort the failure by source; the source tells you where the fix lives.** Most fixes are
  input, system or process, not the model.
- **Model failures are structural — design around them.** Retrieval, verification, code for
  exactness, a way to say no.
- **Prompt injection is a new attack surface.** Any read-and-act system has it.
- **Cost, truncation and version drift are operations problems.** Log tokens, pin versions,
  run evals.
- **"When the model is wrong, …"** — finish the sentence before you build.

## Exercises

1. Take three AI incidents you have read about. Sort each into a column and name the fix that
   would have prevented it.
2. For a feature you own or plan, complete "When the model is wrong, …" for each of its
   three shapes (transform / extract / act) if applicable.
3. Draft the five log fields you would want on every model call to diagnose failures in all
   four columns.

## Model answers (sketch)

1. Common pattern: a fabricated fact in customer-facing text (model → input+checks); an
   assistant that followed instructions in an email (input → trust boundary); a runaway bill
   (system → budgets); a launch with no eval (org → process).
2. Transform: a validator checks length/format and falls back to showing the source. Extract:
   schema + value validation; below confidence, ask the user. Act: code applies policy; over a
   threshold, a human approves.
3. Prompt/model version, tokens per part + finish reason, retrieved sources, tool calls with
   arguments, validation outcome. Together they cover model, input, system and process.
