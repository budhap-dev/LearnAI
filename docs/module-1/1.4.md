## The one idea

Most of an "AI feature" is not AI. It is a request handler, a lookup, some retrieval, a call,
validation, and an action — ordinary software with **one probabilistic step** in the middle:

```diagram
ai-as-component
```

Everything outside the highlighted box is deterministic and testable the way you already test
things. The box is different in kind: it samples from a distribution (Lesson 2.1, 2.7), it can
be wrong while sounding right, and it cannot be unit-tested with an exact expected string. The
skill is to **keep the box small, feed it well, and check what comes out.**

## What changes when a component is probabilistic

| Concern | Deterministic code | The model step |
|---|---|---|
| Correctness | pass/fail per input | a *rate* over a set of inputs |
| Testing | assert outputs | evaluate on a golden set; look at distributions (Module 8) |
| Reproducibility | same input, same output | same input, similar output — sometimes not |
| Failure | exception, bug | plausible wrong answer, silently |
| Debugging | read the code, step through | inspect the prompt and context, compare runs |
| Change management | diff, review, deploy | prompt/model versions *plus* eval results |
| Cost | ~free per call | metered per token / per call |
| Latency | µs–ms | hundreds of ms to seconds; scales with tokens |

None of this makes the model unusable. It means the box needs a different contract than a
function call — one that says *"here is a distribution of behaviour, measured like this, with
these checks around it"* — and that the code around it carries more of the weight than usual.

```check
Your integration test asserts that the model's summary of a fixed document equals a saved string. What will happen?
- It will pass reliably at temperature 0
- * It will be flaky — outputs vary between runs and model versions; test properties and rates instead
- It will fail only if the prompt changes
why: A model step is a sample from a distribution. Test structure (schema), properties (contains the three key facts), and pass rates over a set — not exact strings.
```

## The standard shape, and who owns what

Read the diagram left to right and give each side a job:

**Before the model — your code decides what it sees.**
- Authenticate, authorise, rate-limit — the model must never be the thing that decides who
  may do what.
- Look things up: the order, the account, the policy. Facts you *have* should be fetched by
  code, not recalled by the model.
- Retrieve relevant documents (Module 6), format tool results, assemble the prompt within a
  budget (Lesson 2.5).

**The model — judgement over meaning.**
- Interpret an ambiguous request. Draft. Summarise. Classify. Extract into a structure. Decide
  *which* tool to call and with what arguments (Module 7).

**After the model — your code decides what happens.**
- Validate the shape (schema), the values (ranges, allowed enums), the claims (against the
  source).
- Perform side effects — send, refund, write, delete — from code, under policy, with the
  model's output as *input to a decision*, not the decision.
- Escalate to a human when confidence, value or risk demands it.

> **The rule:** judgement over meaning → the model. Exactness, facts and side effects → code.

## Three shapes you will build repeatedly

- **Transform** — text in, text out, no side effects: summarise, rewrite, translate. Lowest
  risk; validate length/format, evaluate quality on samples.
- **Extract / classify** — text in, structure out: fields, categories, routing decisions.
  Medium risk; enforce a schema, validate values, measure precision/recall (Lesson 3.3, 4.3).
- **Act** — the model proposes an action with side effects. Highest risk; the action runs from
  code, under policy, with approval gates where the blast radius warrants (Lesson 7.6).

Every feature is one of these or a chain of them. Naming the shape early tells you which
checks you owe.

```check
A model drafts a refund and your code issues it directly from the model's JSON. Where is the design flaw?
- Using JSON instead of prose
- * A side effect runs on the model's word alone — code should apply policy (limits, eligibility) and gate high-value cases to a human
- Refunds cannot be automated
why: The model proposes; code decides and acts under policy. Side effects are the code's responsibility because the model can be confidently wrong.
```

## Where reliability actually comes from

New engineers reach for the model to fix model problems: a longer prompt, a firmer
instruction, a bigger model. Those help at the margin. The reliable levers are on either side
of the box:

- **Better input** — the right context, retrieved and formatted, within budget. Most "the
  model is dumb" complaints are "the model was not told".
- **Better checks** — schemas, validators, source-grounding, a second model as judge, a human
  for the tail. Most incidents are "nothing checked".
- **Measurement** — a golden set and an eval that runs on every change (Module 8). Without it
  you cannot tell a fix from a regression.

This is why Modules 4–9 are mostly about the code around the model.

## What a senior engineer should take from this

- **The model is a component.** Keep the box small; the system is yours.
- **A probabilistic step needs a different contract**: rates, evals, versions with results,
  checks on the way out.
- **Judgement to the model; exactness, facts and side effects to code.** Say it in design
  reviews.
- **Reliability comes from input, checks and measurement**, not from asking the model more
  nicely.

## Exercises

1. Draw the diagram for a feature you know (or want): label every box with what it does and
   whether it is deterministic. Where are the side effects? Who checks the model's output?
2. Take the "extract" shape: write the schema for extracting a meeting request from an
   email, and list three validations code should do before creating a calendar event.
3. Your on-call runbook says "if the assistant gives wrong answers, restart the service".
   Rewrite the runbook entry using this lesson.

## Model answers (sketch)

1. Look for any arrow from the model straight to a side effect or a customer with no code in
   between — that is the gap.
2. `{title, start, end, attendees[], location?, confidence}`; validate start < end, times in a
   plausible window, attendees resolve to known contacts; below a confidence threshold ask the
   user rather than create.
3. Check the prompt/model version deployed; run the eval set to see if a regression is
   measurable; inspect recent traces for missing context or truncated prompts; roll back the
   prompt/model version if the eval confirms it. Restarting changes nothing about a
   distribution.
