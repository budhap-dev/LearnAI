## The one idea

A coding assistant is a **very fast junior who has read everything and remembers nothing about
your system.** It amplifies a clear intent into a draft in seconds — and it will just as
confidently produce plausible, wrong code. So the value is not "it writes the code"; the value
is **the loop**, and your judgement is the part that does not automate:

```diagram
review-loop
```

The spec is yours, the review is yours, and the accountability never moves. What changed is
throughput: you spend less time typing and more time specifying and reviewing — which is the
higher-leverage work anyway.

## Spec-first, not autocomplete-first

The difference between an engineer who gets value from these tools and one who gets burned is
**where they start.** Autocomplete-first — accept the grey text, keep going — is how subtle bugs
and quietly-wrong architecture get committed. Spec-first is the discipline:

- **Say what "correct" means before you generate** — the inputs, the outputs, the edge cases,
  the constraints. A precise prompt is a precise spec; a vague one gets vague code.
- **Generate in reviewable units** — a function, a test, a small module — not a thousand-line
  sprawl you cannot actually read.
- **Read every line as if it were a junior's PR**, because it is. The bar is not "does it look
  right"; it is "do I understand exactly what it does and why."

```check
A teammate accepts a 300-line AI-generated module because "the tests pass and it looks clean." What is the flaw in that reasoning?
- Nothing — passing tests is sufficient evidence
- * The tests may themselves be AI-generated and test the wrong thing, and "looks clean" is not "is correct." AI code needs the same line-by-line review as any PR — passing tests written alongside the code do not establish correctness
- They should have generated it in a different language
why: Passing tests only show the code agrees with the tests; if both came from the same model with the same misunderstanding, they agree on the wrong behaviour. "Looks clean" is aesthetic, not correctness. The review is the control, and it is not optional because a machine wrote the code.
```

## The characteristic failure modes

AI-generated code fails in recognisable ways, and knowing them makes review faster:

- **Confident plausibility** — code that reads well and is subtly wrong: an off-by-one, a
  swapped condition, a mishandled null. It looks like working code because it was optimised to
  *look like* working code.
- **Invented APIs** — methods, flags, and packages that do not exist, or exist with different
  semantics. The model pattern-matched a plausible name.
- **Stale patterns** — the average of its training data, which may be an outdated idiom, a
  deprecated call, or a known-insecure snippet.
- **Silent scope drift** — it "helpfully" changes something you did not ask about, or drops a
  case you did.
- **Security by omission** — no input validation, secrets in code, an over-broad permission —
  because the happy path was the prompt and safety was not.

None of these are exotic; they are exactly what you already look for in a review. The assistant
just produces them faster, so your review has to be as fast and as sharp.

## What to never delegate

The loop delegates *drafting*. It does not delegate the decisions a senior engineer is paid
for:

- **Architecture and security decisions** — the shape of the system, trust boundaries, what runs
  with what privilege (9.5). A model has no stake in the consequences.
- **What "correct" means** — the spec, the acceptance criteria, the definition of done. If you
  cannot state it, the assistant certainly cannot.
- **The final review** — the human sign-off before it merges. Accountability requires a person.
- **Anything you could not debug at 3am if it broke.** If you would not be able to own the
  incident, you cannot own the merge.

```check
Where is the line for delegating to a coding agent that can edit files and run commands autonomously?
- Let it do anything as long as a human reads the final diff
- * Give it reversible, well-scoped, verifiable work (a refactor with tests, a migration behind review) with least privilege and no access to secrets or production — and keep architecture, security, and the merge decision with a human
- Never use autonomous agents; they are unsafe
why: Autonomous agents are useful on scoped, reversible, verifiable tasks under least privilege (7.3) — that is a real productivity gain. What stays human is the irreversible and the judgement-laden: architecture, security, secrets, production access, and the accountable sign-off. "Reads the final diff" alone is too weak if the agent had broad privileges along the way.
```

## What a senior engineer should take from this

- **The value is the loop, not the generation** — spec, generate, review, integrate — and your
  judgement is the part that does not automate.
- **Spec-first beats autocomplete-first**: state what correct means, generate reviewable units,
  read every line like a junior's PR.
- **AI code fails in known ways** — confident plausibility, invented APIs, stale/insecure
  patterns, scope drift — which is exactly what your review already catches.
- **Never delegate architecture, security, the meaning of correct, the final review, or
  anything you could not own at 3am.**

## Exercises

1. Take a real task and write the spec you would give an assistant — inputs, outputs, edge
   cases, constraints — before generating anything. What did writing it clarify?
2. Generate a function two ways: from a vague prompt and from your precise spec. Diff the
   quality of what you have to review. What does that tell you about where to spend effort?
3. List the last three bugs you found in AI-generated (or your own) code and map each to a
   failure mode above. Which would a sharper review have caught?
4. Define, for your team, the delegation policy for an autonomous coding agent: what it may do,
   what privileges it gets, and what always requires a human.

## Model answers (sketch)

1. Writing the spec forces the edge cases and the definition of done into the open — usually you
   discover the ambiguity that would have produced the wrong code.
2. The precise-spec output is smaller to review and closer to correct; the vague one needs
   rework you could have avoided. Effort spent specifying pays back in review.
3. Most real bugs are "confident plausibility" (subtle logic) and "security by omission" — both
   caught by reading for what the code *does*, not how it looks.
4. Reversible, verifiable, least-privilege tasks delegated; secrets, production, architecture,
   security, and the merge sign-off reserved for a human — written down so it is enforced, not
   assumed.
