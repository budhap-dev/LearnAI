## The one idea

A framework is a **composition layer**, not magic. LangChain, LlamaIndex, Semantic Kernel, DSPy
and the rest package the plumbing you'd otherwise write — prompt templating, call-retry-parse,
tool orchestration, memory, tracing — behind named abstractions like chains, agents, and
retrievers. That packaging is genuinely useful. It is also **thin**: everything in it is a few
lines of the primitives you built up across Modules 4–9.

To see exactly how thin, here is a "framework" in a dozen lines — a `Chain` of named steps — and
the same task done with raw primitives, to identical output.

```code
framework
```

The `Chain` composes four steps and gives you tracing for free. Now the same task with no
framework at all — the four steps inline:

```code
primitives
```

Run both:

```output
framework
```

```output
raw
```

Same output. The framework version is more concise and hands you tracing; the raw version has
zero indirection and nothing to learn or upgrade. **The `Chain` compiles down to the raw
version** — which is the whole point: a framework is a convenience over primitives, not a
different kind of thing.

## When a framework helps — and when it gets in the way

```output
choose
```

The honest trade:

- **It helps** at the start (a fast path to a working prototype), for standard patterns, and for
  integrations you'd otherwise build and maintain — dozens of vector stores, loaders, model
  providers behind one interface.
- **It hurts** when it becomes a **leaky abstraction over the thing you most need to debug.**
  When production breaks, you need to see the exact prompt, the exact tokens, and the exact
  control flow — and a framework that hides those behind three layers of indirection turns a
  ten-minute fix into an afternoon spelunking its source. Add version churn, hidden prompts you
  didn't write, hidden costs from extra calls, and a ceiling when your case isn't the one it was
  designed for.

The test is concrete: **can you see and control the exact prompt, tokens, and control flow?**
If the framework hides those, you will fight it where it matters most.

```check
A team's LangChain-based feature works in the demo but is hard to debug in production: they can't easily see the exact prompt sent to the model or why the agent took a particular step. What does this indicate, and what's the fix?
- The framework is buggy; file an issue and wait
- * A leaky abstraction over exactly what you must observe. Either configure full prompt/trace visibility, or drop below the framework for the hot path — call the model through your own adapter so the prompt and control flow are yours — keeping the framework only where its convenience outweighs the opacity
- Rewrite everything without any abstraction
why: The problem is that the abstraction hides the prompt and control flow — the things you need when debugging a probabilistic system. The fix isn't "never use frameworks" or "wait"; it's to regain visibility (tracing) or drop to raw primitives on the critical path, which you can do precisely because the framework sits on top of primitives you own.
```

## How to leave one — so you always can

```output
leave
```

You don't have to predict whether you'll outgrow a framework; you just have to build so that
leaving is cheap. The rules are ordinary good architecture:

- **Keep domain logic framework-free.** Your product's core should not `import` the framework —
  the framework calls your code, not the reverse.
- **Wrap model access behind your own adapter seam** (the `llm` module this course has used
  throughout). Providers and libraries are swapped *there*, in one place, not scattered through
  the codebase.
- **Depend on interfaces you own** at your module boundaries, not the framework's types — so a
  migration is an adapter change, not a rewrite.
- The goal: **the framework is a dependency you could delete in a day**, not the shape of your
  system.

This is exactly why the course was built on a small `complete`/`stream`/`embed` adapter and
never on a framework: the primitives are yours, and any framework is a layer you can add or
remove above them.

```check
Why did this course build its examples on a small custom llm adapter (complete, stream, embed) rather than on a framework?
- Because frameworks don't support Python and TypeScript
- * So the primitives are owned and visible — every example shows the exact call, tokens, and control flow — and any framework becomes an optional layer on top rather than the shape of the system, which is the same seam that lets a real system swap providers or leave a framework
- Because custom code is always better than libraries
why: The adapter seam keeps the primitives visible and owned, which is both good pedagogy (you see exactly what happens) and good architecture (providers and frameworks are swappable at one boundary). It's not that libraries are bad — it's that the seam is what keeps you in control of the parts that matter.
```

## What a senior engineer should take from this

- **A framework is a thin composition layer** over primitives you already have — useful, not
  magical.
- **It helps** for a fast start, standard patterns, and integrations; **it hurts** when it hides
  the prompt, tokens, or control flow you must debug in production.
- **The test**: can you see and control the exact prompt, tokens, and flow? If not, drop below
  it on the hot path.
- **Build to leave**: domain logic framework-free, model access behind your own adapter seam,
  dependencies on interfaces you own — so the framework is deletable in a day.

## Model answers (sketch)

1. Both are a few lines; the framework's version is tidier but the retry logic and the prompt it
   re-sends are now behind the abstraction — cheaper to write, harder to see when it misbehaves.
2. Often several layers (chain → agent → LLM wrapper → provider); in an incident that indirection
   is exactly what slows you down, which is the argument for tracing or a raw hot path.
3. The seam should be a single module all model calls go through; if domain logic imports the
   framework directly, that's the coupling to remove first.
4. Framework for a fast standard start; raw for an unusual case or a performance/observability-
   critical path. Keep the option by wrapping model access in your own seam either way, so the
   choice is reversible.
