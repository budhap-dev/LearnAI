## The one idea

A traditional service has an owner and a runbook. An AI feature adds concerns that don't map
cleanly onto existing roles — **prompts, evals, cost, guardrails, serving** — and each will
quietly degrade if no single person is accountable for it. The most common organisational
failure is not a bad model; it's that **the evals belonged to everyone, so no one kept them
current**, and quality drifted with nobody watching.

The fix is boring and it works: one **Accountable** owner per concern.


The point of the matrix is not the letters; it's that **every row has exactly one A.** Consulted
and Informed can be many; Accountable is one. When the golden set goes stale or the cost line
spikes, there is a name.

## The new artefacts a team maintains

AI work introduces living artefacts that are as much a part of the system as the code, and each
needs an owner who keeps it current:

- **The golden set** (8.4) — the evaluation data that defines "good." It is a version-controlled
  asset that grows as you find new failure cases; a stale golden set is a broken speedometer.
- **The prompt registry** (4.1) — prompts are versioned, reviewed code, not strings pasted in a
  dashboard. Changes go through review and re-run the evals.
- **The cost & latency dashboard** (5.5, 9.3) — tokens, spend, and p95 per feature, watched like
  any other SLO, with alerts and a budget.
- **The guardrail / red-team suite** (9.7, 8.6) — the safety checks and the attacks they must
  withstand, run in CI so a regression fails the build.
- **The incident playbook** (9.8) — what to do when the model, the provider, or a guardrail
  fails, including the model-deprecation runbook.

If you can't say who owns each of these, that is the gap to close — it's where quality will
erode first.

```check
Six months after launch, an AI feature's answer quality has quietly declined and no one noticed until users complained. What organisational cause is most likely, and what prevents it?
- The model was silently downgraded by the vendor
- * No one owned the evals, so the golden set was never run against changes or updated as the input distribution drifted. Assign an accountable owner and gate every change on the eval suite, run continuously — not just at launch
- The team should have used a bigger model from the start
why: Undetected quality decline is almost always an ownership-and-process gap: evals that no one runs and no one keeps current. The fix is a named owner plus continuous evaluation gating changes, so drift is caught by the suite, not by users. (A vendor change is possible, but that too is caught by continuous evals.)
```

## Running the project: a loop, not a launch

A deterministic feature is "done" at launch. An AI feature is never done, because its quality
depends on inputs that drift and models that change. So you run it as a **continuous loop**, the
same shape as the eval-driven development of Module 8:

1. **Change** a prompt, a model, a retrieval setting, a guardrail.
2. **Evaluate** against the golden set — the change ships only if it clears the bar (8.4).
3. **Roll out** progressively — shadow, canary, on (9.8) — watching cost and quality.
4. **Observe** production: log traces, sample outputs, watch the dashboards.
5. **Feed back**: every real failure becomes a new golden-set case, so the suite gets stronger.

The roles map onto this loop: engineers own the changes and guardrails, DS/ML owns the evals and
the golden set, the PM owns the cost line and the priorities, SRE owns serving and the SLOs. The
work is a team sport precisely because no one role spans prompts, evals, cost, and serving.

```check
A PM proposes shipping prompt changes directly to production to "move faster," bypassing the eval suite. How should the team respond?
- Agree — evals slow down iteration and the PM owns priorities
- * Push back: prompt changes are code changes and must pass the eval gate, because an unevaluated prompt can silently regress quality or open a safety hole. "Faster" that ships regressions is slower; keep the loop, and speed it up by making the eval suite fast, not by skipping it
- Ship it but only on Fridays
why: Bypassing the eval gate trades a real safety net for apparent speed; an unevaluated prompt change can regress quality or reopen an injection hole with no signal until users hit it. The right move is to keep the gate and invest in making evals fast, so the loop is quick without being unsafe.
```

## What a senior engineer should take from this

- **One accountable owner per concern** — prompts, evals, cost, guardrails, serving — or it
  falls between roles and degrades.
- **AI teams maintain living artefacts** — the golden set, prompt registry, cost dashboard,
  red-team suite, incident playbook — each with an owner who keeps it current.
- **Run it as a loop, not a launch**: change → evaluate → roll out → observe → feed failures
  back into the golden set.
- **It's a team sport** because no single role spans the concerns — the RACI is what stops
  "everyone and no one" ownership.

## Exercises

1. Draw the RACI for an AI feature you know. Which row has no clear A today? That's the gap.
2. Inventory the living artefacts above for that feature. Which exist, which are stale, and who
   would you make accountable for each?
3. You have engineers, one DS, a PM, and shared SRE. Assign the five concerns and justify each
   Accountable choice.
4. Design the feedback step: how a production failure becomes a golden-set case, who triages it,
   and how it re-enters the eval suite.

## Model answers (sketch)

1. Usually evals or cost has no clear owner — assign one accountable person, not a committee.
2. The golden set and prompt registry are the ones most often missing or stale; make DS/ML
   accountable for the golden set and engineering for the prompt registry.
3. Eng → prompts + guardrails; DS → evals + golden set; PM → cost + priorities; SRE → serving +
   SLOs. Each A goes to whoever bears the consequence and can act on it.
4. On-call captures the failing case and its expected output, triages severity, adds it to the
   golden set via review, and the suite re-runs on the next change — so the same failure can't
   silently return.
