## The one idea

The demo is the trap. A probabilistic feature looks brilliant in the three cases you tried and
fails in the fourth you didn't — so **"it looked good" is not a design, and a demo is not a
plan.** The antidote is cheap: one page, seven sections, written *before* you build, that forces
the decisions a demo lets you skip.

The order matters. Most teams write the approach first and bolt on evaluation later, once the
demo has already sold the idea. Flip it: the **eval plan** and the **failure modes** are the
sections that make this engineering rather than a science fair, so they come before you commit
to a solution.

## The seven sections

1. **Problem & user.** The job to be done and who has it — in one paragraph, no solution. If you
   can't state the problem without naming "AI," you're solving for the tool, not the user.
2. **Why AI (or not).** What makes this genuinely probabilistic — open-ended language, judgement,
   unstructured input — and what the deterministic alternative is. Half of good AI design is
   noticing the cases that are just software (1.3). If a `switch` statement does it, write the
   `switch`.
3. **Approach.** Prompt, RAG, fine-tune, classic ML — and *why*, in one line each, referencing
   the decision (6.1, 10.1). Name the model and the fallback.
4. **Eval plan.** The golden set, the metrics, and the bar to ship — decided *now* (8.4). "How
   will we know it works, on data it hasn't seen?" If you can't answer, you can't ship.
5. **Failure modes & guardrails.** What goes wrong — wrong answers, injection, PII, cost blowups
   — and the checks *in code* that contain each (9.5, 9.7). Assume the model will fail; design
   for it.
6. **Cost & latency budget.** Tokens × traffic = the bill (5.5); the p95 latency target (9.3).
   A number, not "should be fine."
7. **Rollout & ownership.** Shadow → canary → on (9.8), and who owns the prompts, the evals, and
   the cost line once it's live (11.3).

```check
A team's design doc has a detailed approach and architecture but the "eval plan" section says "we'll evaluate after the MVP is working." What is the risk, and what should the doc do instead?
- No risk — evaluating after the MVP is the efficient order
- * Without an up-front eval plan you can't tell whether the MVP is good enough or just demos well, and the bar becomes whatever the demo happened to show. Decide the golden set, metrics, and ship bar before building, so "working" has a definition
- The doc should drop the eval section; it slows delivery
why: If the eval plan comes after the MVP, the MVP's demo sets the bar retroactively — you evaluate against what you already built rather than against what the user needs. Deciding the golden set and the ship bar first makes "good enough" an objective call and catches the cases the demo missed (8.4).
```

## The doc's real job: surface the riskiest unknown

A one-pager is not bureaucracy — it is a **risk-finding tool.** The section you *can't* fill in
is the most valuable thing the exercise produces, because it is the risk that would otherwise
have surfaced in production. Can't describe the eval? You don't yet know what good looks like.
Can't budget the cost? You don't know if it's viable. Can't name the failure modes? You haven't
thought about how it breaks.

So write the doc, find the empty box, and **resolve the riskiest unknown first** — with a spike,
a prototype eval, a cost estimate — before you invest in building the rest. This is the same
"reduce the biggest risk first" instinct as any hard engineering project; AI just adds a few
risk categories (does it work on unseen data, does it fail safely, does it cost too much) that
deterministic software doesn't have.

```check
You can fill in every section of the design doc except the cost & latency budget, which you can only guess at. What does the doc tell you to do next?
- Proceed to build; you can measure cost once it's running
- * That the biggest unknown is viability — spike it first: estimate tokens per request against real inputs, multiply by traffic, and check the p95 latency of the approach, before committing to build the rest
- Remove the budget section since you can't fill it
why: The section you can't fill is the risk to resolve first. An unknown cost/latency profile can make an otherwise-good feature non-viable, and that's cheapest to discover with a quick estimate or spike — not after you've built everything and the bill or the latency kills it.
```

## What a senior engineer should take from this

- **Design the feature before you demo it** — one page, seven sections, written up front.
- **Eval plan and failure modes come first**: deciding how you'll know it works and how it fails
  is what makes it engineering.
- **"Why AI (or not)" is a real section** — notice the parts that are just deterministic
  software and build those as software.
- **The empty box is the point**: the section you can't fill is the riskiest unknown — resolve
  it first, before building the rest.

## Exercises

1. Write the one-page doc for a feature you're considering. Which section was hardest to fill,
   and what does that tell you about where the risk is?
2. For that feature, write the "why AI (or not)" section honestly. Is any part of it actually
   deterministic? Carve that part out.
3. Draft just the eval plan: the golden set's source and size, the metrics, and the exact bar to
   ship. Could someone else run it and get the same verdict?
4. List the failure modes and, for each, the guardrail in code that contains it (9.7). Which
   failure mode has no guardrail yet?

## Model answers (sketch)

1. Usually the eval plan or the cost budget — and that's exactly the unknown worth resolving with
   a spike before building.
2. Often the input classification or routing is deterministic; only the open-ended generation
   needs a model. Building the deterministic part as software is cheaper and more reliable.
3. Source: real logged inputs with verified expected outputs; size: representative per case
   type; bar: a metric threshold on a held-out split that another engineer can reproduce.
4. Wrong answer → grounding + citations (6.6); injection → input guards (9.7); PII → output
   guard; cost blowup → budget cap and alert. The one with no guardrail is the next thing to
   build.
