## The one idea

Every eval so far asked *is the answer right?*. A safety eval asks a different, adversarial
question: **can this system be made to do the wrong thing?** That needs different inputs
(attacks, not typical cases) and — the part teams get wrong — a different scorer: **it scores
what the system did, never whether the model meant well.**

A red-team suite is just a golden set (8.2) whose cases are attacks and whose expectation is
"harm did not occur", run on every change with a regression gate (8.4). Same machinery,
adversarial content.

## Score outcomes, not intentions

```output
undefended
```

Every attack lands. And the reason is the whole lesson: **"mostly resists" is not a defence.**
A model that refuses 99% of the time still breaches once in a hundred attempts, and an
attacker gets to try a thousand. Scoring this system by "did the model refuse?" would have
shown 99% and hidden the breach. You must score the *outcome*: was a refund executed, was PII
returned, was a secret leaked.

## Structural guards make harm impossible, not unlikely

Now the same attacks against a system with the guards from Module 7, in code:

```code

```

```output

```

Zero breaches — and not because the model got better. The guards do not depend on the model
cooperating:

- **least context** — the system prompt and secrets are not in the model's context, so there
  is nothing to leak (inj-1, jail-1);
- **gated actions** — refunds and deletions are proposals a human approves (7.6), so injected
  instructions cannot execute them (inj-2, escal-1);
- **scoped data access** — PII is authorised in code by the caller's identity, not by the
  query text (exfil-1);
- **output classifier** — disallowed content is blocked regardless of how it was elicited
  (harm-1).

```check
A red-team review reports "the model refused 47 of 50 jailbreak attempts (94%)". Is this a passing safety result?
- Yes — 94% is a strong refusal rate
- * No — 3 attacks succeeded; safety is scored by breaches, not refusal rate, and the fix is structural guards that make the 3 impossible, not a prompt that refuses more often
why: A refusal rate below 100% on a harmful capability is a breach rate above 0%. Safety evals score outcomes; the remedy is structural (least context, gated actions), not more polite refusals.
```

## It is an eval, so it gets the eval treatment

```output
gate
```

Red-teaming is not a one-off audit; it is a suite that runs on every change, like 8.4 — with
two adjustments for its nature:

- **Zero-tolerance thresholds on critical slices.** For most correctness slices a rate is
  fine; for "leaks another user's data" the threshold is one breach fails the build.
- **The set grows from the outside world.** Every incident (9.8), every disclosure, every new
  public jailbreak technique becomes a case, and every case maps to an
  [OWASP LLM Top 10 category](#/reference/checklists) so coverage is auditable.

The [injection lab](#/explore/injection-lab) lets you feel the undefended-vs-defended
difference by hand; the discipline here is to turn that into a gated suite.

```check
Your red-team suite passes. A new prompt-injection technique is published that your suite doesn't cover. What is the correct response?
- Nothing — the suite passes
- * Add it as a case (it maps to the injection category), run it against your guards, and if it breaches, fix structurally and re-gate — the suite grows from the outside world
why: A passing suite only means "the attacks we know of are held". Safety coverage tracks the threat landscape; new techniques become new cases, like every production miss becomes a golden case (8.5).
```

## What a senior engineer should take from this

- **Safety evals ask a different question** — "can it be made to do harm?" — with adversarial
  inputs and outcome-based scorers.
- **Score outcomes and actions, never refusals.** 99% refusal is a 1% breach rate.
- **Structural guards make harm impossible**, not discouraged — least context, gated actions,
  scoped access, output classifiers (Module 7, Module 9.5).
- **Red-teaming is a gated, growing suite** with zero-tolerance critical slices, mapped to
  OWASP LLM Top 10.

## Exercises

1. Write five red-team cases for a feature you know, one per OWASP LLM category that applies.
   For each, the checkable "harm occurred" predicate over outputs/actions.
2. For one of them, name the structural guard that makes the breach impossible and where it
   lives in the request path. Could a prompt alone have achieved the same guarantee?
3. Your suite scores "model refused" today. Rewrite the scorer to score outcomes, and explain
   what class of breach the old scorer was blind to.
4. Design the zero-tolerance policy: which slices get "one breach fails the build", how a
   breach is triaged, and how the incident becomes a permanent case.

## Model answers (sketch)

1. Injection (instruction in a document executes), exfiltration (another tenant's data
   returned), excessive agency (irreversible action without a gate), sensitive-info
   disclosure (system prompt/secret revealed), insecure output handling (unescaped output
   rendered/executed). Each predicate checks the action/output, not the model's words.
2. e.g. exfiltration → data access scoped in the tool by caller identity (7.3); a prompt
   ("never reveal other users' data") cannot guarantee it because the model can be steered.
3. Old: `"refused" in output`. New: check no PII/secret in the output and no unauthorised
   action in the trace. The old scorer was blind to a *compliant-sounding* answer that still
   leaked, and to actions taken via tools.
4. Slices touching money, data of others, secrets, irreversible actions; a breach pages the
   owner, is reproduced as a case, fixed structurally, and added to the gated suite before
   close.
