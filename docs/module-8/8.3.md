## The one idea

The golden set (8.2) says what a good outcome looks like; a **scorer** decides whether an
answer matched. There is a ladder of them, and the rule is simple: **use the cheapest rung
that can honestly measure the expectation.**

```diagram

```

## The three cheap rungs, and where strings run out

Three candidate answers to one refund question — two correct (one terse, one verbose), one
confidently wrong — scored by all the cheap scorers:

```code
cheap-scorers
```

```output
cheap
```

Read that table carefully, because it is the whole argument for the fourth rung:

- **Exact match fails the terse-correct answer** — it says "14-day window", not the literal
  "14 days". This is Lesson 4.4's brittle checker: string scorers measure *phrasing*.
- **Normalised match fixes hyphens and case but still measures phrasing** — and here the
  normaliser has a bug (it does not fold "days"→"day"), so it *also* fails the correct
  answers. Normalisers are code; test them like code.
- **Only the code check `no_wrong_deadline` catches the wrong answer for the right reason** —
  it looks for an invented deadline (a *property*), not a phrase. A wrong answer that happened
  to quote "14 days" would sail past both string scorers.

The lesson: **strings measure phrasing; code checks measure properties.** Citations present?
Numbers consistent with the source? Schema valid? Length sane? Each is a line of code that
catches a whole failure class, and each is deterministic and free.

## The fourth rung: LLM-as-judge

For things only meaning can settle — is the answer *correct*, is every claim *grounded*, is
the *tone* right — you need a model to grade a model. It works, with guardrails: a narrow
rubric, the source material in the prompt (the judge must not rely on its own memory), a
schema, low temperature.

```code
judge
```

```output
judge
```

The recorded judge got the **booleans** right — it flagged only the wrong answer as not
correct and not grounded. But look at the **1–5 score**: both correct answers got 1/5. The
scalar is noise. This is the practical rule: **ask judges narrow yes/no questions; scalar
scores are meaningless until calibrated against human labels.**

## A judge is a model, so probe its biases

Every failing of Module 2 applies to the judge itself. The best-known is position bias — ask
"which of these two answers is better" and the answer can depend on the *order*:

```code
order-bias
```

```output
order-bias
```

The verdict **flipped** with the order: "A first" said B wins, "B first" said A wins. This
judge cannot rank this pair — its preference is for *position*, not quality. The minimum bar
for a pairwise judge is agreement across both orders; count a win only when they agree, and
call the rest ties.

```diagram
judge-bias
```

Position is one of several; each has a one-time test and a build-in mitigation. Verbosity
bias (longer reads as better — test by padding a wrong answer), self/style bias (prefers its
own phrasings — test with a cross-model judge), sycophancy (agrees with the prompt's premise
— test by asserting something false). **Calibrate the judge against human labels on ~50
cases before trusting it, and re-calibrate when the judge model changes** — its biases are
not stable across versions any more than its answers are (Lesson 2.7).

## What a senior engineer should take from this

- **Cheapest honest scorer wins.** Exact for labels, normalised for phrases (test the
  normaliser), code for properties, judge only for meaning.
- **Strings measure phrasing; code measures properties.** Most "did it do the right thing"
  checks are code, not judges.
- **Judges are useful and biased.** Narrow yes/no rubrics, source in the prompt, schema, low
  temperature; scalar scores need calibration.
- **Probe every judge bias once** (order, verbosity, self, sycophancy) and re-calibrate on
  model change.

## Exercises

1. Take three expectations from your golden set and assign each the lowest scorer rung that
   honestly measures it. Which forced you up to a judge, and could a code check have done it?
2. The normaliser in the example missed "days"→"day". Write two more normalisation bugs that
   would silently pass or fail correct answers, and the test that catches each.
3. Design the order-bias test for your own pairwise judge as an automated check that fails CI
   if the flip rate exceeds a threshold. What threshold, and why?
4. You calibrate a judge at 92% agreement with humans, then the vendor updates the judge
   model. What is your policy before trusting the new version's scores?

## Model answers (sketch)

1. "cites a source" → code (`[id]` present); "states the 14-day rule" → normalised phrase or
   code check for the number; "is empathetic" → judge. The first two never need a model.
2. Folding "e.g."/"eg" or stripping punctuation that changes meaning ("can't" → "cant" vs a
   list membership); test with a fixture of known-equivalent and known-different strings.
3. Run every pairwise case both ways in CI; fail if > ~5% flip, because above that the
   pairwise number is measuring position, not quality.
4. Re-run the calibration set against the new judge; adopt only if agreement holds; the
   number is not comparable to the old judge's until you do (8.2's version discipline).
