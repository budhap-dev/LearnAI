## The one idea

A golden set is Lesson 3.3's held-out set, for a feature whose output is language: real
cases, each with a known-good outcome, run on every change. Three disciplines make it worth
trusting — and none of them is "collect a lot of examples".


## Sample from reality, and floor the rare

The set must mirror what production actually asks, or its number answers a question nobody
asked. Start from real traffic:

```code
traffic
```

The obvious move — take the most frequent questions — quietly discards exactly the cases
that matter most:

```code
sample
```

```output
naive
```

Billing dominates the traffic, so the top-N is all billing and how-to. **Bug, product and
security vanish** — including the highest-stakes category and every case that should escalate
or refuse. Frequency is not risk. The fix is stratified sampling with a floor: mirror the
mix, but guarantee every slice a seat:

```output
stratified
```

Now security survives, because you decided it must, not because it was common.

```check
Your product handles 10,000 billing questions and 5 legal-compliance questions a month. Proportional sampling of 100 cases gives compliance ~0.05 cases. What do you do?
- Accept it — sample proportionally to traffic
- * Floor the compliance slice: guarantee it several cases regardless of frequency, because its cost-of-error dwarfs its rate
- Drop compliance from the set
why: The golden set must protect against your worst outcomes, not just your commonest ones. Stratify with a per-slice floor sized by risk, not frequency.
```

## Label with checkable expectations and provenance

A label is not a transcript of the perfect answer (there are many good answers; Lesson 2.7).
It is what a correct outcome *must be true of* — checkable by a scorer (Lesson 8.3) — plus
the bookkeeping that makes it auditable:

```code
label
```

```output
labelled
```

Every case records **where it came from** (a real ticket) and **who or what labelled it** (a
person, or a documented rule — never "the model graded itself", which would make the eval
circular). And the set includes the cases that should *refuse* or *escalate*, not just the
happy path — those are where features fail dangerously.

## Version it like code

```code
version
```

```output
versioned
```

The content hash is the point: **numbers from different set versions are different numbers.**
"We added a few cases and the score went up" is meaningless unless you know the score is over
the same set — the hash makes the comparison honest and the drift impossible to hide. Grow
the set deliberately: every production miss (8.5) and every incident (9.8) becomes a new
case, with a note saying why.

## Sizing

Start around 50 cases and grow to hundreds as the feature matters more. Below ~30, a single
flaky case moves the rate by 3+ points and the number is too noisy to gate on (Lesson 8.4
runs each case several times for the same reason). Size is a means, not the goal:

- a 40-case set that mirrors traffic and includes the refusal cases beats a 400-case set of
  variations on the happy path;
- more cases buy tighter confidence intervals and finer slices, at labelling cost;
- the set is never "done" — it tracks the product, and a static golden set slowly stops
  describing live traffic (a cousin of drift, Lesson 3.5).

```check
A teammate proposes generating 500 golden cases by asking a model to paraphrase 20 real questions. What is wrong with this?
- Nothing — more cases are better
- * The 500 share the distribution and blind spots of the 20, and were labelled by the thing under test; you get false confidence, not coverage
- Paraphrasing is fine but 500 is too many
why: Coverage comes from real, diverse traffic and independent labels. Model-generated cases graded by a model make the eval circular and hide exactly the cases you did not think of.
```

## What a senior engineer should take from this

- **Sample from real traffic, stratified, with a floor for rare-but-critical slices.**
  Frequency is not risk.
- **Labels are checkable expectations with provenance**, and include refuse/escalate cases.
- **Version and hash the set**; never compare numbers across versions silently.
- **~50 to start, grow from incidents and misses**; a representative small set beats a
  bloated happy-path one.

## Exercises

1. For a feature you know, list its slices and assign each a floor sized by cost-of-error,
   not frequency. Which slice would proportional sampling have erased?
2. Write three golden cases including one that should refuse and one that should escalate.
   For each, write the *checkable* expectation (what a scorer will test), not the ideal answer.
3. Your golden set is at v4. Someone reports the score jumped from 81% to 89% "after
   improvements". What do you check before believing it?
4. Design the pipeline that turns a production incident into a golden case automatically —
   what is captured, who labels it, and how is the set version bumped?

## Model answers (sketch)

1. Typical: a "regulated advice" or "account deletion" slice that is rare and catastrophic;
   proportional sampling gives it ~0 cases.
2. Refuse: "medical advice?" → expects `NOT_COVERED`. Escalate: "I'm being charged after
   cancelling and I'm furious" → expects routing to a human, not an auto-reply. Answer:
   "refund window?" → expects the phrase "14 days" and a citation.
3. Same set version both times? If v4→v5, the numbers are not comparable — re-run the old
   prompt on v5, or the new on v4, to compare like with like.
4. Capture the input, the (wrong) output, and the trace; a human writes the correct
   expectation; append with a note referencing the incident id; bump the set version and
   re-baseline.
