## The one idea

Once you have a golden set (8.2) and scorers (8.3), evaluation becomes a **test suite that
runs on every change** — to the prompt, the model, the retrieval index, the scorer, or the
set itself. It differs from a normal test suite in exactly one way, and the whole lesson is
that difference: **the system under test is non-deterministic (Lesson 2.7), so one run is a
coin flip, not a measurement.**

## The gate, and what aggregates hide

Thresholds are written down *in advance* — in peacetime, before a specific change makes you
want to move them:

```code
gate
```

```output

```

The aggregate gate passes: both versions score 9/12, the overall floor holds, the refusal
slice is now perfect. And yet:

```output
caught
```

The candidate **fixed the refusal case (g4) and silently broke a covered one (g3)** — told
to answer "only from the policy", the model started over-refusing a question the policy does
cover. One failure was swapped for another, the totals balanced, and the aggregate gate waved
it through. Only a **per-case no-collapse rule** catches it:

```code
gate
```

This is the central lesson of eval gates: **aggregate numbers hide compensating changes.** A
gate that only checks the overall rate will ship regressions as long as something else
improved by the same amount. Gate on per-slice minimums *and* per-case collapse, not just the
headline.

```check
Your eval gate checks only "overall pass rate ≥ 85%". A change takes the rate from 88% to 88% — but the security slice went from 100% to 60% while billing improved. What ships?
- Nothing — the rate is unchanged so it's safe
- * A dangerous regression: the aggregate hid a security collapse behind a billing gain; gate on per-slice minimums and per-case collapse, not just the total
why: Compensating changes keep the aggregate flat while a critical behaviour breaks. This is why the example gate adds slice minimums and a per-case no-collapse rule.
```

## Flakiness is not a rerun ticket

```output
flakiness
```

A case at `[+-+]` is **flaky** — the behaviour sits at the edge of the distribution (Lesson
2.7). The wrong response is to rerun until it is green; that is p-hacking your own test
suite. The right responses: tighten the prompt for that case, lower the temperature for that
step, or *accept the rate knowingly* and set the threshold below it. A case that went
`[+++]`→`[---]` is a **regression**, not flakiness — the change broke it. The per-case marks
are what let you tell these apart; the totals cannot.

## When it runs, and citing the set

The gate runs on every change to the prompt, the model or its version, the retrieval index,
the scorer, or the golden set. Two operational notes carry through the course:

- **Vendor model bumps run the same gate before adoption** (Lesson 9.8) — a new model version
  is a change like any other, and "it's the same model, just newer" is exactly the assumption
  that ships a regression.
- **Every eval number cites the golden-set version** it was measured on (8.2). A report that
  says "89%" without a set version and hash is not a measurement you can act on.

```check
An eval case flakes at [+-+-+] on your gate. A teammate reruns the CI job three times until it goes green, then merges. What went wrong?
- Nothing — CI is green now
- * They p-hacked the gate: the behaviour is genuinely ~50% reliable; rerunning until green ships a coin-flip. Fix the prompt for that case or set the threshold honestly below its true rate
why: Rerunning a non-deterministic suite until it passes selects for luck. The flaky rate is real information (2.7) — act on it, don't launder it.
```

## What a senior engineer should take from this

- **A prompt change is a deploy; gate it.** Every change to prompt, model, index, scorer or
  set runs the eval.
- **Measure rates over several runs**, per case and per slice — one pass measures luck.
- **Aggregates hide compensating regressions.** Gate on slice minimums and per-case
  collapse, not just the headline rate.
- **Flaky ≠ regression, and rerun-until-green is p-hacking.** The per-case marks tell them
  apart; act on the flaky rate honestly.

## Exercises

1. Design your gate's thresholds for a support assistant: overall floor, max drop vs
   baseline, per-slice minimums, per-case rule. Justify each number.
2. The example swapped g4 for g3. Write the follow-up prompt change that fixes g4 *without*
   breaking g3, and say how the gate would confirm it.
3. How many runs per case do you need to distinguish a true 70% case from a true 90% case
   with reasonable confidence? Reason about it qualitatively, then pick N for your suite.
4. Your CI eval takes 20 minutes because it calls the model 300 times. Give three ways to
   speed it without weakening the gate.

## Model answers (sketch)

1. e.g. overall ≥ 88%, max drop 3 points, security/refusal slices at 100%, no case
   `[+++]`→`[---]`; the slice minimums are set by cost-of-error, the overall by the baseline.
2. Change "answer only from the policy" to "answer from the policy; if it does not cover the
   question, reply NOT_COVERED" *and* re-test — the gate must show g3 back to `[+++]` and g4
   still fixed before it merges.
3. Distinguishing 70% from 90% needs enough runs that the confidence intervals separate —
   qualitatively, single digits are too few; ~5–10 per case is a common practical floor,
   more for cases near a threshold.
4. Cache prompt prefixes (5.5); run cheap code/string scorers first and only judge the
   survivors; run the full set nightly and a fast subset per PR.
