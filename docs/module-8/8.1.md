## The one idea

You changed a prompt, ran it once, the answer looked great, you shipped. Three things make
that a mistake, and each is something earlier modules already proved:

1. **The output is a sample** (Lesson 2.7). One run measures luck. The same prompt gives a
   different answer next time — your "it works" was a single draw from a distribution you did
   not characterise.
2. **Your test input is not representative.** You tried the case you were thinking about.
   Production asks things you were not (Lesson 8.2), in a mix you did not pick.
3. **Fluency is not correctness** (Lesson 2.8). "Looks good" measures how confident the text
   *sounds*, which is exactly the signal that does not track whether it is *right*.

Evaluation is the discipline that replaces the anecdote with a number: **a pass rate over a
representative, labelled set, measured the same way every time.** It is Lesson 3.3's
held-out set and metrics, applied to a component whose output is language instead of a class
label — and it is the difference between "I think the new prompt is better" and "the new
prompt is 12 points better on grounded-answer rate and 3 worse on refusal precision, here is
the run."

## Two places evaluation lives

| | **Offline** | **Online** |
|---|---|---|
| When | before shipping, in CI | after shipping, in production |
| Against | a golden set (8.2) | real traffic |
| Catches | regressions, known failure cases, the change you just made | what the golden set did not contain; real-world distribution shifts |
| Speed / cost | fast, cheap, run on every PR | slow, real users exposed, measured over days |
| Lesson | 8.2–8.4, 8.6 | 8.5 |

They are complements, not alternatives. Offline evals are a gate — nothing ships that
regresses the cases you already know about. Online evals are a watch — production reveals
the cases you did not know to put in the set, and every one of those becomes a new offline
case (the loop in the diagram). A team with only offline evals ships confidently into
surprises; a team with only online evals learns every lesson in front of users.

```check
A colleague says "we don't need offline evals — we watch production dashboards closely." What is the gap?
- Dashboards are enough if they're real-time
- * Online-only means every regression is discovered in front of users; offline evals catch known failures before they ship, and turn each production surprise into a permanent test
- Offline evals are only for training models
why: The two are complements. Online watching cannot prevent a regression you could have caught in CI against cases you already knew about.
```

## The mindset, stated plainly

Everything in this module is downstream of one habit: **treat a change to a prompt, model,
retrieval index or tool as a deploy, and gate it on a measurement.** Concretely:

- No prompt change merges without the eval running (8.4).
- The measurement is a *rate over several runs*, per slice, never a single pass (2.7, 3.3).
- The set is *representative and versioned* (8.2); numbers cite the set version they came from.
- "Better" and "worse" are numbers with a threshold decided in advance, not a feeling after
  reading three outputs.
- You *read a sample of failures* — the number tells you something moved; the failures tell
  you what (8.1's own discipline, carried through 8.3).

None of this is exotic. It is the testing discipline you already apply to code, adapted for
a component that is probabilistic and whose correctness is a matter of judgement rather than
an assertion. The rest of Module 8 is the how: build the set (8.2), score it (8.3), gate on
it (8.4), watch online (8.5), and attack it (8.6).

```check
Your new prompt scored 84% on the golden set; the old one scored 82%. Is the new one better?
- Yes — 84 beats 82
- * Not yet: run each several times (outputs are sampled), check no critical slice or case regressed, and confirm 2 points is outside the noise before deciding
- No — 2 points is always noise
why: The mindset is measure-compare-then-decide, with confidence scaled to the evidence. A 2-point move on a small set run once can be pure sampling noise (Lessons 2.7, 8.4).
```

## What a senior engineer should take from this

- **A demo is an anecdote from a random process.** Replace it with a rate over a
  representative set, measured identically each time.
- **Offline gates; online watches; the loop connects them** — every production miss becomes
  an offline case.
- **A change is not done until a number says it did not make things worse.** That habit,
  applied per change, is the whole module.
- **Read the failures, not just the number.** The rate says something moved; the sample says
  what.

## Exercises

1. Take an LLM feature you have shipped or seen shipped. How was "it works" decided? Rewrite
   that decision as an offline + online eval plan in five lines.
2. For that feature, name one failure that offline evals would catch and one that only online
   evaluation would surface. Why can neither catch the other's?
3. A stakeholder wants to ship a prompt change today because "the demo was flawless".
   Write the two-sentence reply that reframes the demo as evidence, without blocking pointlessly.
4. Write your team's one-line definition of done for a prompt change. What number, what set,
   what threshold?

## Model answers (sketch)

1. Usually: decided by a demo. Plan: golden set of N real cases with expectations; gate in CI
   on pass rate + per-slice minimums; canary in prod watching a quality signal and cost.
2. Offline catches a regression on a known case (a refund question it used to answer);
   online catches a new question type users started asking after a marketing campaign.
   Offline cannot contain what it has never seen; online cannot prevent what it only observes.
3. "The demo shows it *can* work on that case; it doesn't show the rate across the cases users
   actually send. Give me a day to run it against the golden set and I'll tell you if it's
   better or worse — with a number."
4. e.g. "≥ 90% on support-golden@N, no slice below 85%, no case collapsed, vs the shipped
   baseline, run 3×."
