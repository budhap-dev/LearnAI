## The one idea

Offline evals (8.2–8.4) protect against the failures you *thought of*. Production is where
the failures you did not think of live — the question type users started asking this week,
the document format the retriever never saw, the phrasing that trips the prompt. Online
evaluation is how you meet those safely: **not a launch, but a ladder of increasing exposure,
each rung entered on evidence and exited on a metric.**

## The rungs

| Rung | Exposure | Catches | Rollback |
|---|---|---|---|
| **Offline gate** | 0% traffic | known regressions (8.4) | don't merge |
| **Shadow** | 0% served | real-traffic failures, at zero user risk — run the new version alongside the old, compare, serve neither | turn it off |
| **Canary** | 1–5% | problems that only appear at real scale / real users | route back to control |
| **A/B** | ~50%, measured | whether it is actually better on the metric that matters | ship control |
| **Full** | 100%, rollback ready | — | one config change |

**Shadow is the underused rung.** It runs the candidate on real production inputs, logs what
it *would* have answered, and serves the old version — so you get real-traffic evidence with
zero user impact. It is where you discover that the input distribution is not what your golden
set assumed, before a single user sees the new behaviour. Everything a shadow run flags
becomes an offline case.

```check
A change passes the offline gate at 94%. What is the safest next rung, and why not go straight to 100%?
- Straight to 100% — 94% is a strong offline score
- * Shadow (then canary): the offline set only contains cases you thought of; shadow reveals real-traffic behaviour at zero user risk before any exposure
why: A high offline score bounds known risk, not unknown risk. The ladder exists because production always contains inputs the golden set does not (8.1's loop).
```

## Measuring online, without labels

Offline you have ground truth (the golden label). Online you usually do not — nobody labels
live traffic in real time. So online evaluation leans on **proxy signals**, each imperfect,
triangulated together:

- **Implicit behaviour** — did the user retry, rephrase, escalate to a human, abandon? A spike
  in "talk to a human" after a change is a quality signal even with no labels.
- **Explicit feedback** — thumbs up/down, ratings. Sparse and biased (angry users click more),
  but cheap and directional.
- **Automated online scorers** — the code and judge scorers from 8.3 run on a *sample* of live
  traffic, giving a continuous quality estimate (with the judge's biases, so calibrate).
- **Guardrail and cost metrics** — refusal rate, validation-failure rate, tokens and latency
  per request (Lesson 5.7). A change that improves answers but doubles cost or refusals is not
  obviously better.

The A/B rung turns these into a decision: run candidate against control on split traffic,
and compare the proxy metrics with enough traffic to clear the noise (the same
sampling-variance discipline as 8.4, now over users instead of runs).

```check
After shipping a new prompt, thumbs-down feedback is flat but "escalate to human" clicks rose 30% and refusals rose 20%. What does this tell you?
- It's fine — explicit feedback didn't get worse
- * A regression the explicit signal missed: users are routing around the assistant. Triangulate implicit signals (escalation, retries) and guardrail metrics, not just thumbs
why: Explicit feedback is sparse and biased. Implicit behaviour and guardrail metrics often reveal a quality drop first — which is why online eval triangulates several proxies.
```

## Closing the loop

Every rung feeds the offline set. A shadow disagreement, a canary complaint, an A/B loss, a
thumbs-down with a transcript — each is a candidate golden case (8.2), labelled and versioned,
so the same failure is caught in CI next time and never ships again. This is the loop from
Lesson 8.1 made concrete: **offline gates, online watches, and production teaches the gate.**
A team whose golden set is not growing from production is not really doing online evaluation —
it is just watching dashboards.

## What a senior engineer should take from this

- **Roll out on a ladder** — offline gate → shadow → canary → A/B → full — exposure matched
  to evidence, rollback always one step down.
- **Shadow is the free rung**: real-traffic evidence at zero user risk. Use it.
- **Online you measure proxies** — implicit behaviour, explicit feedback, sampled scorers,
  guardrail and cost metrics — triangulated, never one signal.
- **Every production miss becomes an offline case.** That feedback is the point of the loop.

## Exercises

1. Design the rollout ladder for a change to your highest-stakes LLM feature: the entry
   evidence and exit metric for each rung, and the rollback mechanism.
2. Your feature has no thumbs up/down. List three implicit signals you already log (or could)
   that would reveal a quality regression, and their failure modes as proxies.
3. A canary at 5% shows the new prompt 8% better on an automated judge score but 15% more
   expensive. Who decides, on what basis, and what would you measure before deciding?
4. Write the pipeline that turns an A/B "loss" (a case where candidate underperformed
   control) into a golden case. What is captured, who labels it, how is the set versioned?

## Model answers (sketch)

1. e.g. offline ≥ threshold → shadow (exit: distribution matches assumptions, no new failure
   class) → canary 5% (exit: guardrail + cost metrics flat, no escalation spike) → A/B (exit:
   win on the primary metric, clear of noise) → full, rollback = flip the routing config.
2. Escalation rate, retry/rephrase rate, session abandonment; each is confounded (escalation
   also rises with hard questions), so read them as directional and together.
3. Product + eng owner decide on value-per-dollar: measure the quality gain on the golden set
   too (is the judge's 8% real?), and the cost at full traffic, before committing.
4. Log input, both outputs, the metric that lost, and traces; a human writes the correct
   expectation; append to the set with an A/B-id note; bump and re-baseline (8.2).
