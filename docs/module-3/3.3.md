## The one idea

A model gives every row a score. Evaluation answers two questions people keep merging:

1. **Does the score rank things well?** — independent of any threshold (AUC).
2. **At the threshold we will deploy, what happens?** — the confusion matrix and its
   metrics.

And both are only meaningful on **held-out** rows the model never trained on. Training-set
numbers flatter every model; the point of a model is behaviour on rows it has not seen.

want — usually recall on the rare class at an acceptable precision.

## The four counts, and the metrics on top

```code
confusion
```

- **Precision** — of what we flagged, how much was real? Low precision = false alarms,
  wasted reviewer time, annoyed users.
- **Recall** — of the real cases, how many did we catch? Low recall = misses.
- **F1** — their harmonic mean; a single number when you must have one, and it hides which
  side is weak.
- **Accuracy** — right answers over all; misleading whenever classes are imbalanced.

```output
threshold-sweep
```

The same scores; five thresholds; five products. Nothing in the model picks the row —
**the cost of each error type does**, and that is a conversation with whoever bears the cost.

```check
A fraud model at threshold 0.5 has precision 0.56 and recall 0.83. Reviewers complain about false alarms. What is the honest trade you can offer?
- Retrain until both are high
- * Raise the threshold: fewer false alarms (higher precision), and some fraud will slip through (lower recall) — decide together where that line sits
- Lower the threshold to catch everything
why: At a fixed model, precision and recall trade against each other via the threshold. A better model shifts the whole curve; the threshold picks the point on it.
```

## Ranking quality: AUC

```code
auc
```

```output
auc
```

AUC is the probability a random positive outranks a random negative — threshold-free, so it
is what you compare *models* on before anyone chooses a threshold. When positives are rare,
prefer the area under the precision–recall curve, which is not flattered by the ocean of
easy negatives.

## Held-out, and the many faces of leakage

```output
leakage
```

The single most common evaluation bug is **information from the test rows reaching the
training process**, which makes every number a lie:

| Leakage | Looks like | Fix |
|---|---|---|
| Testing on training rows | 99% accuracy in the notebook, 70% in production | split first, always |
| Fitting the scaler / vocabulary on all data | small but real inflation | fit statistics on the training split only (Lesson 3.2) |
| Duplicates or near-duplicates across the split | the model "remembers" | dedup before splitting |
| A feature that encodes the label | e.g. `refund_issued` when predicting fraud | ask "would this be known at prediction time?" for every feature |
| Random split of time-ordered data | the model peeks at the future | split by time: train on the past, test on what came after |

The time-split row deserves emphasis: for anything with a date, evaluate the way production
will experience it — trained on before, tested on after.

```check
Your churn model scores 0.94 AUC on a random 80/20 split of three years of data. Production performance is far worse. Most likely cause?
- The model needs more trees
- * The random split let the model train on the future — split by time so the test set is later than the training set
- The threshold is wrong
why: Behaviour drifts over time and features can encode later events. A time-based split evaluates the model as production will use it: past → future.
```

## Beyond one number

Before shipping, look at:

- **Slices** — performance by segment (region, plan, device, language). Averages hide the group
  the model fails for; this is where bias shows up (Lesson 1.6).
- **Calibration** — when the model says 0.8, is it right about 80% of the time? Matters if
  the score is shown to a person or used in a cost calculation.
- **A confusion sample** — read twenty false positives and twenty false negatives. Metrics
  tell you *how much*; the sample tells you *why*.

## The same habits, for LLM features

Everything above is the vocabulary of Module 8. An LLM classifier or extractor is evaluated
exactly like this: a held-out set of real cases, a confusion matrix per label, precision and
recall per field, slices, and a sample you read. The models differ; the discipline does not.

## What a senior engineer should take from this

- **Split first; test on what was held out; split by time when there is time.**
- **Beat the baseline** on a metric that reflects the rare class.
- **AUC to compare models; precision/recall at the deployed threshold to describe the
  product; costs to choose the threshold.**
- **Leakage inflates everything.** Ask "would we know this at prediction time?" for every
  feature.
- **Slices and a read sample**, not one number.
