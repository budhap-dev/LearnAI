## The one idea

Since large language models arrived, "AI" in product conversations has come to mean "call an
LLM". Most of the AI that has quietly run businesses for fifteen years is nothing of the sort:
fraud scores, churn predictions, demand forecasts, ranking, spam filters. Those are **classic
machine learning** — models over rows and columns — and they are usually faster, cheaper,
more measurable and more explainable than a generation call. Three questions decide:

```diagram
classic-vs-llm
```

1. **Can you write the rule?** If the logic is known and exceptions are few, write it. Free per
   call, exact, testable, explainable. (Lesson 1.1.)
2. **Do you have tabular data with labels?** Rows with an outcome — did they churn, was it
   fraud, how long did it take. That is classic ML's home: regression, trees, boosting.
   Milliseconds, fractions of a cent, measurable with a confusion matrix.
3. **Is the input free-form language and the task judgement over meaning?** Then an LLM —
   accepting seconds of latency, metered cost, and the need to verify the output.

And a fourth option that is neither: **embeddings + nearest neighbour** (Lesson 2.3) for
search, similarity, dedup and cheap classification — no generation call at all.

## What each option costs

| | Rules | Classic ML | Embeddings + kNN | LLM |
|---|---|---|---|---|
| Latency | µs | ms | ms | hundreds of ms – seconds |
| Cost per call | ~0 | ~0 | tiny (one embedding) | metered per token |
| Needs | someone who knows the rule | labelled rows | text + a labelled or curated set | context in the prompt; evals |
| Explaining a decision | read the code | feature importances, per-row contributions | "these were the nearest" | weak — the model's stated reason may not be the real one |
| Testing | assert | metrics on a held-out set (Lesson 3.3) | retrieval metrics | evals on rates (Module 8) |
| Failure shape | bug | miscalibrated score, drift | wrong neighbour | plausible wrong text |
| Best at | known logic | patterns in structured data | similarity | language, judgement, unstructured input |

The row that surprises engineers new to this: **classic ML is explainable enough for
regulated decisions** (credit, insurance, hiring screens) in a way LLM outputs are not. If
someone will ask "why was this declined?", that alone often decides.

```check
Predict which support tickets will breach SLA, from ticket metadata: queue, priority, hour, customer tier, age. Best first choice?
- An LLM reading the ticket text
- * A classic classifier on the metadata columns — labelled rows, tabular, needs to be fast and explainable
- A rule: priority = high → breach
why: The inputs are columns and the label (breached / not) is in history. That is a boosted-tree problem: milliseconds, cheap, measurable. The text can be added later as a feature if metadata is not enough.
```

## The composite that wins most often

Real features are rarely one box. The pattern that recurs:

> **LLM to turn language into structure → classic ML or rules on the structure.**

- The LLM reads a free-text ticket and extracts `{product, issue_type, sentiment, urgency}`
  (Lesson 4.3). A boosted tree, trained on months of labelled tickets, predicts breach risk from
  those fields plus metadata. Rules route the top 5% to a senior queue.
- The LLM summarises a claim; a classic model scores it for review; a rule blocks amounts over
  a threshold pending a human.

Each part does what it is good at: language → LLM; patterns in structured history → classic ML;
policy → rules. And each part is testable in its own way.

```check
Your team wants "AI" to answer free-text billing questions from customers. Which techniques, in which order?
- One LLM call, end to end
- * Embeddings to retrieve the relevant policy passages, an LLM to answer from them with citations, rules/code for anything with a side effect (refunds, changes)
- A classifier that picks one of 20 canned answers
why: Free-form language → LLM, but grounded by retrieval (Module 6) and never allowed to act alone (Lesson 1.4). The canned-answer classifier can be a cheap first tier for the common questions.
```

## When neither ML nor an LLM is the answer

Two more honest outcomes of the flow:

- **You have no data and no way to define "correct".** Not a learning problem yet. Ship the
  rule, log everything, and revisit when you have labelled outcomes (Lesson 1.3).
- **The cost of being wrong is high and unverifiable.** If no code, source or human can check
  the output before it matters, do not automate the decision — automate the *preparation* for
  a human decision.

## What a senior engineer should take from this

- **Three questions**: can you write the rule? tabular + labels? free-form language + judgement?
- **Classic ML is the default for structured data**: fast, cheap, measurable, explainable.
- **The composite** — LLM for language → structure, classic ML/rules on the structure — is the
  usual right answer.
- **No data, no definition of correct → not a learning problem yet.**

## Exercises

1. Take five features on your roadmap. Run each through the flow and write one line per

2. For one "LLM-only" proposal you have seen, redesign it as the composite. What became
   cheaper, faster, or more testable?
3. Name a decision in your product that would need explaining to a customer or regulator.
   Which options survive that requirement?

## Model answers (sketch)

1. Look for the tell-tales: "predict X from Y columns" → classic; "read this and…" → LLM;
   "find similar" → embeddings; "if amount > …" → rules.
2. Typically the LLM shrinks to extraction; a classifier handles the prediction; rules gate
   actions. Latency drops from seconds to ms for the common path; the parts get separate evals.
3. Rules and classic ML (with feature contributions). An LLM's explanation is text it
   generated, not the mechanism — usable as a draft for a human, not as the reason of record.
