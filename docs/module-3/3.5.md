## The one idea

A trained model is a file of numbers. Turning it into something a product can depend on
takes four things, and none of them is machine learning:

```diagram
ml-lifecycle
```

1. **A pipeline** — the same feature preparation at training time and at request time.
2. **An artefact** — the fitted numbers, serialised with a version, so serving loads exactly
   what was evaluated.
3. **Serving** — load once, predict per request, log what you predicted and with which
   version.
4. **Monitoring** — notice when incoming data stops looking like the training data.

That is a release loop. If you have shipped services, you already know most of it.

## The pipeline: one function, both places

```code
data
```

```code
pipeline
```

Two design rules do most of the work:

- **Feature engineering lives in one function** (`raw_features`) that both training and
  serving import. The classic production bug — "training/serving skew" — is two
  implementations that drift apart: the notebook log-transformed the amount, the service
  forgot to.
- **Statistics are fitted on training data and frozen.** The `Scaler` learns means and
  standard deviations once; serving *applies* them. Refitting on request data would make
  every request look average.

```check
The data scientist's notebook computes `log10(amount + 1)`; the serving code, written later by another team, passes `amount` straight in. The model was validated at AUC 0.9. What happens in production?
- Nothing — the model adapts
- * Every prediction is silently wrong: the model sees numbers on a different scale from what it was trained on, and no error is raised
- The service crashes on the first request
why: Training/serving skew fails silently. One shared feature function, called from both places, is the fix — and a test that runs a known row through both paths.
```

## The artefact: numbers plus a version, nothing else

```code
train
```

```output
artefact
```

Training returns **plain data**: feature names, scaler statistics, weights, threshold, and a
version string. Serialise it as JSON (or a proper model format), store it in a registry
alongside its evaluation metrics, and you can answer "which model made this decision, and
how good was it when we shipped it?" forever. Avoid artefacts that are pickled code objects
— they tie serving to a training environment and hide what is inside.

## Serving: load once, predict per request, log

```code
serve
```

```output
serve
```

Every prediction is logged with the artefact version. That single habit makes incidents
tractable — a bad decision traces to an exact artefact, and the artefact can be rolled back
like any deploy by serving the previous version.

Latency for a model like this is microseconds; boosted trees are milliseconds; the
expensive part is usually fetching features (a database call for "minutes since last
payment"). Two patterns:

- **Online** — compute features and predict per request. Freshest; needs the feature
  fetch to be fast.
- **Batch** — score everyone nightly, store the scores, look them up at request time.
  Cheapest and simplest when freshness of hours is fine (churn risk, marketing segments).

## Monitoring: is today still the world we trained on?

```code
drift
```

```output
drift
```

**Drift** is the input distribution moving away from the training data. It does not say the
model is wrong; it says you can no longer assume it is right — the model has not seen this
world. Alert on it, then check outcomes.

| Signal | What it catches | How |
|---|---|---|
| Input drift | features' distributions moved | mean shift in training SDs, or a distribution distance, per feature |
| Prediction drift | the model's score distribution moved | same, on the scores |
| Outcome quality | the model is actually worse | recompute metrics as labels arrive (often delayed by days or weeks) |
| Data quality | nulls, out-of-range, schema changes | validate every request's features |

When drift is real: retrain on recent data, re-evaluate on fresh held-out labels (3.3),
redeploy a new version — the same loop as any release.

```check
Input drift alerts fire, but you have no fresh labels yet. What can you conclude?
- The model is wrong; roll it back
- * Only that the inputs no longer look like the training data — treat it as an alert to investigate and to prepare a retrain, not as proof of failure
- Nothing — ignore drift until labels arrive
why: Drift is a leading indicator; outcome metrics are the lagging truth. Investigate what changed, tighten human review if the stakes are high, and line up labels for re-evaluation.
```

## The same shape, later in the course

## What a senior engineer should take from this

- **One feature function, both places; statistics fitted on training data only.**
- **The artefact is data with a version**, stored with its metrics; serving loads it and logs
  the version with every prediction.
- **Online vs batch** is a freshness/cost decision, not an ML one.
- **Drift is a leading indicator; outcomes are the truth.** Alert on the first, act on the
  second, retrain in a loop.

## Model answers (sketch)

1. Run a fixed row through `raw_features` at "training" and again through the loaded `Model`;
   assert the transformed features and score are identical; keep a golden file of expected
   scores per artefact version.
2. Log it, exclude it from automatic decisions or route to review — the model has no grounds
   there (Lesson 2.8, again).
3. Batch: nightly scores in a table are enough for a weekly campaign. Live dashboard →
   online, or batch with a freshness label; the choice is about how stale is acceptable.
4. Confirm via prediction logs which version misbehaves; point serving at the previous
   artefact; verify with the golden rows; then diagnose (drift? bad training data? skew?)
   before retraining.
