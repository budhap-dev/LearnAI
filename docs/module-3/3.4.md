## The one idea

Lesson 1.3 said unsupervised learning finds structure in inputs alone. Two questions cover
most of what engineers need from it:

- **What groups are in here?** → clustering. Customer segments, ticket themes, kinds of host,
  types of session.
- **Which rows do not belong?** → anomaly detection. The weird transaction, the misbehaving
  host, the metric that just changed shape.

Both are everyday tools in ordinary systems, and both are usually solved without any LLM.

## k-means, from scratch

Per-host metrics with no labels — but three kinds of host, and one impostor, are hiding:

```code
data
```

```code
kmeans
```

Assign every point to its nearest centre; move each centre to the mean of its points;
repeat. That is the whole algorithm.

```output
kmeans
```

Three things to hold on to:

- **k is your choice.** The algorithm will split three kinds into two or four without
  complaint. Try a few values, plot the groups, and pick the k whose clusters a person can
  *name* — "idle / busy / saturated". If nobody can name them, the clustering is not useful
  yet.
- **The start matters.** Different initial centres can give different groupings; real
  implementations run several starts and keep the best. The example uses a fixed start so
  the output is reproducible.
- **Look at the result.** Clustering has no labels to score against. Its test is whether the
  groups mean something to the people who will act on them.

```check
You ran k-means with k = 5 on customer behaviour and got five clusters. How do you know whether it "worked"?
- The algorithm converged, so it worked
- * A person can name each group and would act differently on them — clustering is judged by usefulness, not by a metric
- The clusters are equal in size
why: There are no labels; convergence and tidy sizes prove nothing. Try other k values, plot, and ask whether the segments drive different decisions.
```

## Anomaly detection, from a z-score

```code
anomaly
```

```output
anomaly
```

How many standard deviations from the mean is each value? Beyond about 3 is the classic "this
is not normal" line. It is crude and it assumes a roughly bell-shaped baseline — but it is
explainable in one sentence, needs no training, and is often exactly enough for a first alert.
When it is not: use robust statistics (median and MAD) for heavy-tailed data, isolation
forests or density methods for multi-dimensional anomalies, and a learned model when "normal"
is itself complex (seasonality, multiple regimes).

## Scale decides what "close" means

```output
scale
```

k-means — and every distance-based method, including the nearest-neighbour search under
embeddings (Lesson 2.3) — measures distance in whatever units you hand it. Latency in
milliseconds spans hundreds; CPU in percent spans tens; so unscaled, distance *is* latency.
Scaled to 0–1, both count. Neither is "right": the scaling encodes what you mean by similar,
so choose it deliberately (Lesson 3.2) and re-check the groups after changing it.

```check
After adding a "monthly spend in cents" feature to a customer clustering, all clusters became spend bands. Why?
- Spend is the most important feature
- * Cents span a huge range, so distance became almost entirely spend — scale the features before clustering
- k was too small
why: Distance-based methods weight features by their numeric range unless you scale. Standardise or normalise first, then decide on purpose which features should dominate.
```

## Where you will actually use these

| Need | Technique | Note |
|---|---|---|
| Discover the themes in ten thousand support tickets | embed the text (2.3), then k-means; name the clusters; later, train a classifier (3.2) | the classic labels-from-nothing bootstrap (Lesson 1.3) |
| Segment users by behaviour | k-means on scaled behavioural features | validate that segments drive different actions |
| Flag odd transactions / logins / hosts | z-scores → isolation forest as it matures | pair with a human review queue; alert on rate changes too |
| Detect a metric changing shape | rolling z-score or seasonal baseline | the anomaly may be the *distribution*, not one point (Lesson 3.5, drift) |
| Find near-duplicate documents | embeddings + high-similarity threshold | no clustering needed |

Notice how many of these are the *cheap first tier* in front of anything expensive: cluster
tickets before deciding what to build; flag anomalies before a person looks; dedup before an
LLM summarises.

## What a senior engineer should take from this

- **k-means: assign, move, repeat.** k is yours; the result is judged by whether people can
  name and act on the groups.
- **z-scores are a fine first anomaly detector**, and their assumptions tell you when to move
  on.
- **Scale before any distance-based method** — the scaling defines "similar".
- **These are the cheap first tier** before labels, models or LLM calls.
