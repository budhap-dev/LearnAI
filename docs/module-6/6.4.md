## The one idea

Lesson 2.3 was honest about embeddings: they capture *gist*, and specifics wash out — an error
code, a product name, a ticket id, a rare acronym. Keyword search is the opposite: it nails
exact tokens and has no idea that "money back" means "refund". Real questions contain both
kinds of signal, so production retrieval runs both and fuses the results:

## Keywords: BM25

```code
tokenise
```

```code
bm25
```

BM25 is what Lucene, Elasticsearch and OpenSearch rank with by default, and it is four
lines of maths: for each query term in a document, multiply a **rarity weight** (idf — terms
in few documents count more) by a **saturating term frequency** (the second mention helps
less than the first), normalised for document length. Stop-word removal matters — without it,
"what does a … mean" outscores the one rare token that matters — and real engines add
stemming so *refund* matches *refunds*.

## Meaning: cosine over embeddings

The same `embed` + cosine from Lesson 6.2. Its superpower is paraphrase; its blind spots are
exact tokens and jargon the embedding model rarely saw.

## Fuse: reciprocal rank fusion

```code
rrf
```

BM25 scores and cosine scores live on different scales, so you cannot add them. RRF ignores
scores and adds **1/(k + rank)** from each list — a document that is first in one list and
absent from the other still ranks well; one that is mid-list in both ranks well too. One
constant (*k*, usually 60), robust, and what most hybrid setups actually do.

```output
ranks
```

Read the four queries:

- **"what does HTTP 429 mean"** — the exact token `429` wins for keywords; vectors agree
  because "HTTP 429" is common enough in training data; fusion keeps api-limits first.
- **"how do I get my money back for the yearly subscription"** — no shared words with the
  refund article ("refund", "annual"), so BM25 misses it; vectors put it first; **fusion
  recovers it** from the vector list.
- **"does SCIM work for deprovisioning leavers"** — jargon: keywords find `scim` in the SSO
  article; the embedding model reads "deprovisioning leavers" as *deletion* and ranks
  retention first; fusion keeps SSO on top.
- **"reverse-charge VAT invoice for our EU entity"** — both agree.

Fusion rarely beats the better list on its own query; its value is **never being the worse
one**, across a traffic mix you cannot predict.

```check
Your vector-only search misses questions that contain ticket ids like "INC-48213". The fix is…
- A bigger embedding model
- * Add keyword (BM25) search and fuse with RRF — exact tokens are what keywords are for
- Lower the similarity threshold
why: Embeddings wash out specifics by design. Exact identifiers, codes and jargon come from keyword search; fusion combines both without comparing scores.
```

## Where the vectors live

```output
scale
```

| Scale | Store | Notes |
|---|---|---|
| up to ~100k vectors | **a list and a loop** (what this course does), or any database with a vector column | brute force is milliseconds; do not add a system |
| up to low millions | **pgvector** (Postgres) with an HNSW or IVF index | the default start: your existing database, transactions, filters, backups |
| tens of millions+, or vectors are the product | a **dedicated vector database** | tuned ANN, sharding, but one more system to run |
| keyword precision, filters, facets alongside vectors | a **search engine** (OpenSearch/Elasticsearch, etc.) | hybrid natively; heavier |

Two ideas matter whichever you pick. **ANN indexes** (HNSW, IVF) trade a little recall for
speed: instead of comparing against every vector they walk a graph or a set of clusters; you
tune the recall/latency knob and measure hit@k (Lesson 6.7). **Filter first**: most queries
have structure — this tenant, this product, this date range — and a metadata filter before the
vector search is cheaper and more precise than anything after it.

```check
You have 400,000 chunks in Postgres already. The fastest sensible route to vector search is…
- * pgvector with an HNSW index in that Postgres; filter by tenant in the same query
- Stand up a dedicated vector database and sync to it
- Load everything into memory in the application
why: Scale, operations and the filters you already have all point at the database you run. Add a system when the numbers say so.
```

## Operational rules

- **Same embedding model both sides; store the model name and version with the vectors.** A
  model change is a full re-index.
- **Store metadata** (tenant, document, section, updated-at) and **filter first**.
- **Version the index**; build the new one alongside, evaluate, switch, keep the old one until
  the evals pass.
- **Access control applies to vectors.** A vector can be inverted to approximate its text;
  treat the store like the documents (Lesson 2.3).

## What a senior engineer should take from this

- **Keywords for exact tokens, vectors for meaning, fuse with RRF.** Hybrid is the default, not
  the upgrade.
- **Put vectors where your data already is** until scale forces a dedicated store.
- **ANN is a recall/latency knob** — measure it. **Filter first.**
- **Same model both sides; version the index; protect the vectors.**
