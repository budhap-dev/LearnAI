## The one idea

RAG is two paths that meet at an index:

```diagram
rag-pipeline
```

The **ingest path** runs when documents change: chunk, embed, store. The **query path** runs
per request: embed the question with the same model, retrieve the nearest passages, put them
in the prompt with ids, ask the model to answer only from them and cite. That is the entire
architecture. Everything in Lessons 6.3–6.7 is an improvement to one box in this picture —
which is why the boxes must stay separate.

## Ingest once

```code
ingest
```

Load, embed, keep the vectors next to the text. The "vector store" at this scale is two
parallel lists; at production scale it is a table with an index (Lesson 6.4) — but note what is
stored either way: **id, title, text, vector**. The text comes back with the hit; the id is what
the answer will cite.

```output
ingest
```

We embed `title + text` rather than bare text: the title carries context the passage alone
may lack (Lesson 6.3 makes this a rule).

## Retrieve per request

```code
retrieve
```

Embed the question **with the same model** — a vector from a different model lives in a
different geometry and compares to nothing (Lesson 2.3). Score against every stored vector,
keep the top *k*. The per-request embedding cost is one short string.

```check
Your ingest job used embedding model A; six months later someone switches the query path to newer model B "because it scores better". What happens?
- Retrieval improves
- * Retrieval breaks — query vectors and stored vectors are in different spaces; re-embed the corpus with B first
- Nothing, embeddings are interchangeable
why: Same model both sides, always. Store the model name and version with the vectors and treat a model change as a full re-index.
```

## Assemble a grounded prompt

```code
assemble
```

Three things in this prompt do the work: the **ids** in square brackets (so the model can cite
and your code can check — Lesson 6.6), the **"ONLY the provided articles"** rule, and the
**explicit refusal token** `NOT_COVERED`. Without the last, the model will answer anything
(Lesson 2.6); with it, "we don't have that" becomes a normal, checkable outcome.

Scores are low and flat, the three "best" articles are unrelated, and the model said
`NOT_COVERED`. That is the single most important behaviour in the whole pipeline: **the
system can say no.** Lesson 6.6 makes it checkable; Lesson 6.7 measures how often it is right.

```check
In the third question the retrieved articles were seats, refunds and plans — none relevant — yet the scores were 0.52, 0.46, 0.46. What does that tell you?
- Retrieval failed and should be fixed
- * Top-k always returns k things; low, flat scores mean "nothing fits" — which is why the answer step needs a refusal rule, not a better ranker
- The corpus is too small
why: Nearest-neighbour search never returns nothing. The model's refusal rule (and, in production, a score threshold or a judge) is what turns "least bad" into "not covered".
```

## The shape to keep

```output
shape
```

Each stage has one job and one metric (Lesson 6.7). When answer quality is poor, the first
question is *which stage*: was the right passage retrieved (hit@k)? was it used (faithfulness)?
was the prompt clear? — never "the model is bad". The model only sees what retrieval put in
front of it; **retrieval quality is the ceiling on answer quality.**

## What a senior engineer should take from this

- **Two paths, one index.** Ingest on change; retrieve, assemble, answer per request.
- **Same embedding model both sides**; store id + text + vector + model version.
- **Ids in the prompt, "only from the articles", and an explicit refusal token** — the three
  lines that make answers checkable.
- **Keep the stages separate** so each can be measured and swapped.

## Exercises

1. Change `k` from 3 to 1 and to 8 (replay works for the retrieval part; the answer needs a
   recording). What changes in the retrieved list, and what would change in the prompt size?
2. Add a score threshold: if the best score is below 0.55, skip the model call and return
   NOT_COVERED directly. What does that save, and what does it risk?
3. Sketch the ingest path for a real corpus: what triggers re-embedding, how do you version
   the index, and how do you roll back a bad ingest?
4. Your retrieved passages are correct but the model's answer contradicts them. Which stage
   is at fault, and what would you look at first?

## Model answers (sketch)

1. k=1 loses multi-article answers (g7, g9 need two); k=8 sends ~3× the tokens and more
   distractors. k is a budget decision (Lesson 2.5), tuned on the golden set.
2. Saves a model call on clearly-off-topic questions and blocks answers from nothing; risks
   refusing paraphrased questions with low scores — set the threshold from the golden set.
3. Document change events → re-chunk/re-embed that document; index version stored with each
   vector; blue/green index switch; keep the previous index until evals pass.
4. Generation: grounding prompt/faithfulness. Check the prompt the model actually received
   (Lesson 5.7) and run the faithfulness judge (6.7).
