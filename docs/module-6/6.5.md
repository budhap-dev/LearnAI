## The one idea

Retrieval so far has been *bi-encoder* search: the query and each chunk are embedded
separately and compared by cosine. That is what makes it fast — the chunks were embedded
ahead of time — and it is also why it is approximate: the model never sees the query and the
chunk *together*. A **reranker** does exactly that, for a handful of candidates, and orders
them far more precisely. Too expensive to run over millions; cheap over twenty.

And before either stage: the user's message is often a poor search query. **Rewriting** it is
the cheapest precision win of all.

## Rewrite the question first


```output

```

A cheerful paragraph with the question buried at the end became a six-word search query with
the two concepts that matter. The same trick handles multi-part questions (split into two
queries), pronouns that refer to earlier turns (resolve them from history), and vocabulary
mismatch (the user says "money back", the docs say "refund"). **HyDE** is the same idea
inverted: ask the model to write a plausible answer and search with *that*, because an answer
looks more like the documents than a question does.

## First stage: recall


```output

```

Top-5 by cosine: the right article first, then four neighbours of decreasing relevance. On a
small corpus the first stage is already good; on a large one, the top twenty will contain the
right passage *somewhere* and the order will be rough.

## Second stage: precision

```output
rerank
```

The reranker read the query and each passage together and scored them 0–3: the refund article
3, billing 1, the rest 0. Now the prompt gets the two that matter and not the three that do
not — fewer tokens, less distraction, better grounding (Lesson 6.6).

The example uses an LLM judge with a structured schema because it needs no setup; it is also
slow and costs a generation call. In production the same job is done by a **cross-encoder
reranker** — a small model trained specifically to score (query, passage) pairs — which is
faster, cheaper and usually better. The shape is identical: first stage top-*N*, rerank, keep
top-*k*.

```check
Your reranker takes 400 ms and you run it over the top 200 first-stage results. Users complain about latency. The fix is…
- Remove the reranker
- * Rerank fewer candidates (top 20–30) and measure hit@k — the reranker's value is in ordering a short list, not a long one
- Rerank the whole corpus offline
why: Two stages exist precisely so the expensive step runs over a handful. Tune N with the golden set; recall rarely needs more than a few dozen candidates.
```

## When each step pays — and when it does not

```output
when
```

Both steps add a model call of latency and cost. The rule is the rule of the whole module:
**measure hit@k before and after on the golden set (Lesson 6.7), and keep the step only where
it moves the number.** Typical findings: rewriting helps chatty user input a lot and
well-formed search bars not at all; reranking helps large or noisy corpora and is invisible
on a small clean one.

```check
When does query rewriting most clearly pay for itself?
- For short keyword searches typed into a search box
- * For chatty, multi-part or pronoun-laden messages, and when users' words differ from the documents' words
- Never — the embedding model handles it
why: Rewriting turns messages into search queries. Well-formed queries gain nothing; conversational input gains a lot.
```

## Parent–child, briefly

A pattern that belongs here because it lives between retrieval and assembly: embed **small**
chunks (precise retrieval), but return the **enclosing section** to the model (enough context
to answer). Retrieve by child, de-duplicate by parent, send parents. It is the usual answer
to "fact lookups want small chunks and explanations want large ones" from Lesson 6.3.

## What a senior engineer should take from this

- **Two stages: cheap recall over everything, expensive precision over a few.**
- **Rewrite chatty input into a search query** before retrieval; resolve pronouns from
  history.
- **LLM rerankers are the zero-setup version; cross-encoders are the production one.**
- **Each step is latency and cost — keep it only where it moves hit@k.**
