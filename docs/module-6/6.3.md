## The one idea

An embedding is one vector for one piece of text. If the piece is a whole 40-page document,
the vector is an average of everything in it and no specific fact stands out; if the piece is
half a sentence, it has lost the context that made it mean anything. **Chunking is choosing the
pieces** — and it affects retrieval quality more than the choice of embedding model does.

## Three strategies, one file

```code
fixed
```

Fixed windows of *N* words with *M* words of overlap. Dumb, predictable, never misses text,
and often good enough. The overlap exists so a fact that straddles a boundary appears whole in
at least one chunk.

```code
sentence
```

Sentence boundaries packed up to a size. Chunks end where thoughts end, so a fact is rarely cut
in half; sizes vary a little, which is fine.

```code
sections
```

Headings. Real documents have structure; when they do, it is the best chunker you will find,
because the author already decided where topics start and stop.

Read the table as two questions. *Did we find it?* — every strategy except headings gets hit@1
on all nine answerable questions, and all get hit@3. *What came with it?* — whole-document
chunks send **~1,000 words** to the model per question; sentence chunks send **~160** for the
same hit rate. That is 6× the tokens, 6× the latency of prompt processing, and 6× the
irrelevant text the model must ignore (Lesson 2.5: the middle gets lost). The headings strategy
lost one hit@1 — a question whose answer spans two sections — which is exactly the kind of
thing only a measurement would tell you.


## The rules that fall out

```output
rules
```

1. **Natural boundaries first** — headings, then sentences; fixed windows when there is no
   structure. A little overlap (10–20%) for the windowed case.
2. **Prepend the document title / section path** to every chunk before embedding. A chunk that
   says "Seat reductions take effect at renewal" retrieves badly; "Billing guide › Seats and user
   management: Seat reductions…" retrieves well. The example does this in `measure`.
3. **Size by the question shape.** Fact lookups ("how long do refunds take") want small chunks;
   "explain our retention policy" wants a section. If you serve both, keep small chunks for
   retrieval and return the enclosing section to the model (**parent–child**, Lesson 6.5).
4. **Store chunk metadata** — document id, section path, position, last-updated — so results
   can be filtered and cited (Lesson 6.4).
5. **Measure on a golden set before and after every chunking change** (Lesson 6.7). Chunking is
   cheap to change and expensive to get wrong silently.

```check
Your corpus is 20,000 support tickets: short, unstructured, one topic each. Which chunker?
- Fixed 60-word windows with overlap
- * Whole-ticket chunks with the subject prepended — they are already short and single-topic
- Sentences, always
why: Chunking adapts to the material. Short single-topic items are their own chunks; the rules (carry context, measure) still apply.
```

## What a senior engineer should take from this

- **Chunking decides what retrieval can find** — it matters more than the embedding model.
- **Natural boundaries, a little overlap, title prepended.**
- **Measure hit@k and words-sent together** on your own corpus; taste does not count.
- **Parent–child** when fact lookups and explanations share a corpus.

## Model answers (sketch)

1. Between sections and sentences: section-sized where sections are short, sentence-packed
   where they are long — usually the best default for structured documents.
2. Hits drop for questions whose answer sentences do not mention the topic noun; the title
   carried it.
3. Hundreds of questions sampled from real traffic, labelled with relevant chunk ids, and a
   pass/fail threshold (Lesson 8.2).
4. Embed small child chunks with their parent id; store parent text separately; retrieve by
   child, de-duplicate by parent, send the parent section.
