## The one idea

Every lesson in this module ended with "measure it". This is the measurement. A RAG system has
two places to fail — **the right passage was not retrieved**, or **it was retrieved and the
model did not use it well** — and one number cannot tell those apart. So the scorecard has two
halves:

```diagram
rag-eval-triad
```

Lesson 3.3's discipline applies unchanged: a held-out set of real questions with known-good
answers, numbers computed on that set, and the set re-run on every change. The only new thing
is that some of the scorers are themselves model calls.

## The golden set

The fixture's ten questions each carry the **relevant article ids** (for retrieval) and an
**expected substring** (for correctness); one is deliberately uncovered (for refusal). Real
golden sets are hundreds of questions sampled from traffic and labelled by people who know the
domain (Lesson 8.2); ten is a smoke test, which is what the example says it is.

## Four scorers

```code
judge
```

- **hit@k** (retrieval, code): is any relevant id in the top *k*? No model call; the ceiling on
  everything else.
- **correctness** (code): does the answer contain the expected substring? Crude, fast, and —
  as the run below shows — brittle in exactly the way Lesson 4.4 warned about.
- **faithfulness** (model judge): given the passages and the answer, is every claim supported?
  A model grading a model. Useful, and biased: judges favour long, confident, well-formatted
  answers, and their own phrasing (Lesson 8.3). Keep the rubric narrow, use a structured
  schema, and spot-check a sample by hand.
- **refusal precision** (code): did it say `NOT_COVERED` exactly when the question was
  uncovered — and never when it was covered?

eval doing its job: the number is wrong about the system and right about the checker. In a
real suite you would normalise hyphens and whitespace (or check the number and the unit

## Reading the scorecard

```output
reading
```

| Pattern | Stage | First things to try |
|---|---|---|
| hit@k low | retrieval | chunking (6.3), hybrid (6.4), rewrite/rerank (6.5), larger *k* with reranking |
| hit ok, correctness low | generation / checker | read the failures: checker too brittle? prompt unclear? passage formatting? model too small? |
| faithfulness low | grounding | tighter prompt, citation checks in code (6.6), fewer/more relevant passages |
| refuses covered questions | threshold / prompt | lower the score threshold; soften the rule; check hit@k for those questions |
| answers uncovered questions | grounding | refusal rule, citation verification, a judge on "is this supported" |

And the habit that makes it work: **run the scorecard on every change** — chunking, index,
prompt version, model version — and block the change when a number regresses past a
threshold you wrote down in advance (Lesson 8.4).

```check
Your faithfulness judge says 100% supported for a month. Then you read ten answers by hand and find two with invented numbers. What went wrong?
- Nothing — two in ten is fine
- * The judge has a blind spot (judges are biased and can be fooled); add the code number-check from 6.6, sharpen the rubric, and keep spot-checking
- Faithfulness cannot be measured
why: A model-graded metric is evidence, not proof. Combine it with code checks and periodic human review, and treat a too-good number as a prompt to look.
```

## What a senior engineer should take from this

- **Two halves: retrieval (hit@k) and generation (correctness, faithfulness, refusal).** Low
  hit@k means fix retrieval first.
- **The eval runs the production pipeline**, on a golden set from real traffic, on every change.
- **Code checks where you can, judges where you must, humans on a sample.** Judges are biased.
- **A failing case is a gift**: normalise the checker, keep the case, move on.
