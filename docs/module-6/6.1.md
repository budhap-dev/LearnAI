## The one idea

Module 2 left you with a model that knows a lot, up to a cutoff, fuzzily, with no sources
(Lessons 2.6, 2.8). Your product needs answers from *your* documents — the refund policy as
it is this week, the runbook, the contract — and needs to show where each answer came from.
**Retrieval-augmented generation (RAG)** is the discipline of moving the facts you care about
from the model's memory into the prompt, per request:

> find the passages that are relevant to this question → put them in the prompt with ids →
> ask the model to answer *only* from them and cite.

The model supplies language and judgement; your documents supply the facts; retrieval decides
which facts. Everything else in this module is making each of those three reliable.

## Four ways to get knowledge into an answer

```diagram
rag-decision-matrix
```

| | What it really does | Use it for |
|---|---|---|
| **Prompting** | puts a *little* knowledge and the rules in every request | instructions, examples, the shape of the answer — always first |
| **Retrieval (RAG)** | puts the *relevant* slice of a large, changing corpus in each request, with ids | knowledge: private, recent, large, must be cited |
| **Fine-tuning** | changes the weights so the model *behaves* differently | format, tone, domain vocabulary, a consistent style — with hundreds of examples (Module 10) |
| **Long context** | lets you send *more* per request | one long document, low volume, high value |

Three facts that settle most arguments:

1. **Fine-tuning is bad at facts.** It shifts behaviour reliably and knowledge unreliably; a
   fine-tuned model still invents specifics, and every change to the facts means retraining.
   Retrieval changes what the model knows *right now* by changing an index.
2. **Long context is not retrieval.** Sending the whole corpus every time costs tokens on every
   request, loses the middle (Lesson 2.5), and still gives no citations. It is the right design
   for one document and one careful answer, not for a support desk.
3. **Provenance is the feature.** "Here is the answer and here is the article it came from" is
   what lets a user check, a reviewer audit, and your code verify (Lesson 6.6). Only retrieval
   gives you that for free.

```check
Your product must answer questions about a policy manual that changes every week, and auditors need to see the source for each answer. Which approach fits?
- Fine-tune the model on the manual each week
- * Retrieval over the manual, with citations to the passage ids
- Paste the whole manual into every prompt
why: Weekly change and required provenance are exactly what retrieval provides — update the index, cite the passage. Fine-tuning is slow and does not carry sources; whole-manual prompts pay per request and cannot cite reliably.
```

## What RAG buys — and what it costs

**Buys:** freshness (update the index, not the model); provenance (citations per claim); scope
control (the model answers from *your* documents, and can refuse when they do not cover the
question — Lesson 6.6); cost control (you send the relevant passages, not the corpus);
portability (the same index works with next year's model).

**Costs:** an ingest pipeline that runs on every document change; an embedding model and a
store (Lesson 6.4); chunking decisions that genuinely affect quality (Lesson 6.3); two extra
failure modes — the right passage not retrieved, or retrieved and ignored — each of which needs
its own metric (Lesson 6.7). None of that is exotic; all of it is engineering.

```check
A colleague says "our model hallucinated a pricing tier, so we need to fine-tune it on the pricing page". What is the better first response?
- Agree — fine-tuning fixes hallucination
- * Retrieve the pricing page into the prompt and require citations; fine-tuning changes behaviour, not facts, and the page will change again
- Increase the context window
why: Invented facts are a grounding problem. Put the facts in the prompt with ids and make the model cite them; keep fine-tuning for behaviour.
```

## What a senior engineer should take from this

- **Retrieval moves facts from the model's memory into the prompt**, per request, with ids.
- **Prompt for rules, retrieve for facts, fine-tune for behaviour, long context for one
  document** — and usually combine the first two.
- **Freshness and provenance are the point.** If either matters, you want retrieval.
- **RAG has its own failure modes and its own metrics.** Budget for the eval (6.7) from day one.
