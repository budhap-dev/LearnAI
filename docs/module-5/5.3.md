## The one idea

A model cannot look anything up, run anything, or change anything. **Tool calling** is the
protocol by which it asks your code to do those things: you describe functions — name,
purpose, a JSON schema for the arguments — and when the model decides one is needed it
replies with a structured request instead of prose. Your code runs the function and sends
the result back as a message. The model continues.

```diagram

```

Hold on to the shape: **the model proposes; your code disposes.** Nothing in the protocol
lets the model execute anything. Every capability, every permission, every side effect is a
line of code you wrote, which is why tool calling is both the most powerful feature in the
API and a perfectly governable one.

## The contract: tool schemas

```code
tools
```

Schemas do two jobs. They tell the model **when** to call (the description) and **how** (the
argument schema). Both are prompt text as far as the model is concerned — treat them with
Lesson 4.x discipline:

- Descriptions say what the tool is *for* and *when* it applies. "Evaluate an arithmetic
  expression exactly. Use this for any maths instead of doing it yourself" is a description
  that changes behaviour; "calculator" is not.
- Arguments are few, typed, enumerated where possible, with `additionalProperties: false`.
  Every optional argument is a place for the model to improvise.
- Tool schemas cost tokens on every request (Lesson 2.5). Ten verbose tools can eat
  thousands before the user speaks. Send the tools the step needs.

## The dispatcher: arguments are untrusted input

```code
run-tool
```

The model's arguments arrived in a response body from a service that predicts text. Treat
them exactly as you would a query parameter from the internet: parse, validate, allow-list,
and run with the least privilege the task needs. Two rules the example shows:

- **Errors go back as data.** `{"error": "no order with id 'ORD-9999'"}` is something the
  model can read and recover from. An exception in your process is not — it ends the loop
  and the user sees a 500.
- **No `eval`.** The calculator allow-lists characters before evaluating. A model that has
  read a malicious document (Lesson 4.6) will happily ask your calculator to evaluate
  something else.

```check
The model calls `delete_records({"where": "1=1"})`. What should have prevented this?
- The model's safety training
- A better description on the tool
- * The tool not existing in that form: destructive operations need narrow arguments, policy checks in code, and a human gate
why: Arguments are untrusted. Least privilege means the tool cannot express the dangerous action at all — not that the model is asked nicely.
```

## The loop — with a cap

```code

```

```output

```

Read the trace: the model looked up the order, then — because the description told it to —
called the calculator rather than adding in its head, then answered. Three model calls for
one question; each one is a full request with the history so far (Lesson 2.5: it grows).

Two things that are not optional:

- **A step cap.** A model that keeps calling tools, or calls the same tool with the same
  arguments twice, will do so forever without one. The cap bounds cost and turns a loop
  into an error you can see (Lesson 7.7).
- **Append the assistant turn that contained the tool calls** before the tool results. The
  conversation must show *what was asked* and *what came back*, in order, or the model
  loses the thread.

## What it buys — and where it leads

```output
contract
```

Tool calling is the basis of Module 7: agents are this loop with more tools, memory and
planning; MCP (Lesson 7.4) is a protocol for describing and hosting tools; guardrails (Lesson
9.7) and human gates (Lesson 7.6) are policies inside `run_tool`. Get the contract right
here and those are increments, not rewrites.

```check
A tool call's arguments validate and the tool returns `{"error": "rate limited by upstream"}`. The loop should…
- Raise and stop — errors end loops
- * Feed the error back as a tool result; the model can decide to retry, wait or tell the user — under the step cap
- Call the tool again in a tight loop until it succeeds
why: Errors as data keep the conversation coherent; the step cap bounds any retrying the model chooses to do.
```

## What a senior engineer should take from this

- **The model proposes; your code disposes.** Every capability is a function you wrote.
- **Schemas are prompts**: descriptions decide *when*, argument schemas decide *how*.
- **Arguments are untrusted input**: validate, allow-list, least privilege, no eval.
- **Errors as data; a step cap; the assistant turn before the results.** Every loop, every
  time.

## Exercises

1. Add a third tool, `refund_order`, with a `max_amount` enforced in code and a "requires
   approval" result above a threshold. What does the model do when told a refund needs
   approval?
2. Remove the calculator's description sentence "Use this for any maths…" and re-run (live
   mode). Does the model still call it? What does that tell you about descriptions?
3. Make the loop's step cap 1 and re-run the happy path. What does the user see? Design the
   message for that case.
4. Sketch the permission model: which tools can run with which identity, and where does the
   check live — in the tool, in the dispatcher, or in the gateway?

## Model answers (sketch)

1. It should explain that approval is required and stop — if it tries to call again, that is
   the loop cap's job. The "requires approval" result is the human gate (Lesson 7.6).
2. Often it does the arithmetic itself (and sometimes gets it wrong). Descriptions steer
   behaviour; the calculator's value is *exactness*, which the description has to sell.
3. "(no final answer — step cap reached)" — unacceptable as a user message. Show what was
   found, say the assistant could not finish, offer a human.
4. Dispatcher checks policy per tool per caller (who is asking, on whose behalf); tools run
   with scoped credentials; the gateway enforces quotas. Never the model.
