## The one idea

Lesson 2.4 mentioned the KV cache: the attention state for the prompt can be kept and
reused for the next token. Providers extend that across requests — **if the beginning of
your prompt is byte-identical to one they saw recently, they skip recomputing it and bill
those tokens at a fraction of the input price.** Two things follow immediately: only a
*prefix* can be cached, and it has to be *identical*.

## Only the unchanged prefix is cacheable

```code

```

```output

```

Same four parts, same content, same answer. In the cache-friendly layout the system prompt
and examples form a 3,700-token prefix that is identical on every request; in the hostile
layout the user's question comes first, so the identical prefix is zero tokens long and
nothing is cached. **Order is the whole trick**: stable first, variable last.

```check
Your system prompt begins "Today is 2026-08-19. You are…". What is the effect on prompt caching?
- None — the rest of the prompt is still identical
- * The cacheable prefix is broken every day (or every request, if the time is included) — move the date to the end or drop it
- Caching only applies to user messages
why: The cache needs a byte-identical prefix. Anything variable — dates, user names, request ids — placed before the stable parts ends the cacheable prefix there.
```

Those are illustrative prices — look up real ones on the [model reference](#/reference/models) —
but the *shape* holds for every vendor: cached input is typically an order of magnitude
cheaper than fresh input, so a large stable prefix with a high hit rate changes the bill by
a third or more. **And it is a refactor, not a model change**: same answers, same latency or
better (a cache hit also skips prompt-processing time), a prompt reordered.

What you have to do to get it:

1. Put system prompt, tool schemas and few-shot examples first; retrieved context next; the
   user's turn last.
2. Make the stable part actually stable: no timestamps, user names, request ids, or
   per-request tool lists in it.
3. Keep the prefix above the provider's minimum cacheable length (they have one).
4. **Read the usage fields** the API returns — cached vs uncached input tokens — and put the
   hit rate on a dashboard (Lesson 5.7). When it drops, someone edited the prefix.

Some providers cache automatically on matching prefixes; some need an explicit marker at the
boundary. Check which, and expect the prices and rules to change.

## Batch: when nobody is waiting

```output
batch
```

If the result is not needed now — nightly classification, backfills, evaluation runs,
report generation, re-indexing — an asynchronous batch endpoint does the same work for
(commonly) half the price, with results in minutes to hours. The engineering is a queue and
a place to collect results; the saving is automatic. The trick is to *notice* which of your
calls nobody is waiting for. Usually more than you think.


## What a senior engineer should take from this

- **Caching = byte-identical prefix.** Stable first, variable last; nothing per-request in the
  stable part.
- **It is a refactor with a large, measurable saving** — and the hit rate is a metric you
  should own.
- **Batch everything nobody is waiting for.** Half price for a queue.
- **Prices change; the shapes do not.** Keep the numbers on the reference page, the habits in
  the code.

## Exercises

1. Take a real prompt from your system and mark each part stable or variable. Reorder it
   for caching. What moved, and what had to be made stable?
2. Using the explorer, find the hit rate below which a 5,000-token stable prefix stops
   paying back the effort of keeping it stable. Is that a realistic number for your traffic?
3. List every model call your product makes and mark which ones a human is waiting for.
   What fraction could go to batch?
4. Design the alert for "cache hit rate dropped": what metric, what threshold, and what is
   the first thing on-call should check?

## Model answers (sketch)

1. Typically: a date or user name in the system prompt had to move to the user turn; tool
   lists had to be made constant per route.
2. The break-even is low (often under 20–30%), because cached tokens are so much cheaper —
   almost any real hit rate pays.
3. Commonly a third or more: reports, nightly jobs, evals, re-embedding.
4. `cached_input_tokens / input_tokens` per prompt id per hour; alert on a drop of more than
   X points; first check: what changed in the prompt registry (Lesson 4.4).
