## The one idea

Everything in Module 4 treated the model as a function. It is not; it is an HTTP endpoint
owned by someone else, with rate limits, occasional 5xx responses, variable latency and a
bill. **The first thing to build is the thin layer that makes it behave like a function** —
and that layer is the same for every vendor, which is why it lives in one place.


Three layers, three owners:

| Layer | Owns | Lesson |
|---|---|---|
| **Your code** | what to ask, what to do with the answer, validation | 4.x, 5.3 |
| **The wrapper** (this lesson) | timeout per attempt, retry policy, idempotency, accounting | here |
| **The gateway** | API keys, quotas, routing between models, fallbacks, central logging | 9.2 |

The wrapper in this lesson is deliberately small — under forty lines — because you will
read it many times in incident reviews.

## Errors: the only question is "retry or not?"

```code
errors
```

Every vendor's error list reduces to two classes. **Retryable**: rate limited (429),
overloaded (529/503), timeouts, transient 5xx. **Not retryable**: malformed request (400),
authentication (401/403), content too large, context length exceeded. The first class gets
backoff; the second gets raised immediately, because retrying a 400 four times is four 400s
and a slower failure.

```code

```


```output

```

Three details people get wrong:

- **The timeout lives in the HTTP client, not the retry loop.** The wrapper decides what to
  do *after* a timeout; it cannot impose one. Set a per-attempt timeout that matches the
  task — a classification should not wait 60 seconds; a long generation might need it.
- **Cap attempts, and back off exponentially with jitter.** Without a cap, an outage turns
  every client into a retry storm. Without jitter, all your clients retry in lockstep.
- **Log every attempt** with the error class. "Three 429s then success" is a capacity signal
  you want to see on a dashboard (Lesson 5.7).

```check
A call returns HTTP 400 "messages: content must not be empty". Your wrapper should…
- Retry with exponential backoff — it might succeed
- * Raise immediately — the request is wrong, and retrying cannot fix it
- Retry once, then raise
why: Only transient conditions (rate limits, overload, timeouts, 5xx) deserve retries. A 400 is a bug in the request; retries just add latency to the same failure.
```

## Idempotency: the model call is cheap to repeat — its consequences are not

```code
idempotency
```

```output
idempotency
```

Calling a model twice costs tokens. Creating a ticket twice, sending an email twice,
issuing a refund twice costs trust. Retries — and double-clicked buttons, and replayed
queue messages — make "twice" normal. So **anything the model's answer triggers** carries
an idempotency key derived from the user and the request; the downstream system stores the
key and treats a repeat as a no-op. This is ordinary distributed-systems hygiene; the model
just makes it easy to forget because the interesting part is the prompt.

```check
- * Any side effect the answer triggers carries an idempotency key, so the repeat is a no-op downstream
- Nothing — retries are always safe

```

## What a senior engineer should take from this

- **Treat the model as the flaky network dependency it is**: per-attempt timeout, retry only
  retryable errors, exponential backoff with jitter, a cap, a log line per attempt.
- **Idempotency keys on everything the answer triggers.** The call is safe to repeat; the
  side effect is not.
- **One wrapper, vendor-neutral,** so the next three lessons — and your next vendor — build on
  the same forty lines.
- **Three layers, three owners:** your code, the wrapper, the gateway. Do not let them blur.

## Exercises

   per model".

## Model answers (sketch)

1. Retry storms: every client backing off by the same amount retries at the same instant.
2. Without: retry → second "urgent" → second email. With: the email sender stores the key;
   the second send is a no-op. The key lives with the side effect (the email/ticket record).
3. In the client call (`timeout=`/`AbortSignal.timeout`). Connect = time to open the socket;
   read = time between bytes — for streams, read timeout must cover the gap between tokens.
4. `{ts, trace_id, model, attempt, status: 429|200|…, latency_ms, tokens_in, tokens_out}`.
