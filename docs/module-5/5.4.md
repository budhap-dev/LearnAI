## The one idea

A vision-capable model turns an image into tokens and then does what Lesson 2.1 said it
does: predicts the next token. Nothing about the loop changes. What changes for you is the
*input*: a picture costs far more tokens than the text in it, and the "facts" the model reads
off an image are recognised, not known.

Ground truth exists in this example; in production it does not, so check what you can:
**arithmetic** (subtotal + VAT = total), **formats** (invoice numbers, dates, currency
codes), **ranges** (no negative quantities, totals in a plausible band), and
**cross-references** (does that supplier exist; does that PO number match). A number the
model "read" from pixels carries the same risk as a number an OCR engine read — misreads
of 8/3, 1/7, dropped decimals — with the added risk that the model may *infer* a value that
is not there. The value checks from Lesson 4.3 are not optional here; they are the feature.

```check
A vision model extracts "total_due: 1088.85" from an invoice image. What should happen next?
- Post it to the ledger — the schema guaranteed a number
- * Check it against subtotal + VAT, format, range and cross-references; route to a human on any failure
- Ask the model if it is sure
why: The schema guarantees shape; the value came from pixel recognition. Treat it like OCR output: verify with code, escalate on failure.
```

## Images are tokens — budget them

```output
cost
```

A small PNG can cost several hundred to a few thousand input tokens depending on the model
and resolution; a text rendering of the same invoice is ~150 tokens. Rules of thumb:

| Situation | Do |
|---|---|
| The image *is* text (invoice, form, contract scan) | OCR or use the PDF's text layer; send text. Send the image only where layout carries meaning |
| Layout, charts, photos, screenshots, handwriting | send the image — that is what vision models are for |
| Large images | downscale to what a human needs to read; crop to the region of interest |
| Many pages | extract per page; send the pages that matter (retrieval, Module 6), not the PDF |
| High volume | a dedicated OCR/layout model first, the LLM only for the judgement step |

And the usual: different models accept different formats and sizes, charge differently for
images, and read with different accuracy — measure on *your* documents (Lesson 8.2) before
choosing.

```check
For 2,000 daily scans of printed forms, the cheapest reliable design is…
- Send every scan as an image to the largest vision model
- * OCR (or the text layer) first, the LLM for structuring, code for verification, humans for failures
- Ask users to retype the forms
why: Dense printed text is cheaper and usually more accurate as text; reserve images for where layout carries meaning.
```

## What a senior engineer should take from this

- **Images are ordinary prompts** — same API, same structured-output discipline.
- **Recognised, not known**: verify image-derived values like OCR output, escalate on failure.
- **Tokens first**: send text when you have text; send the image when layout carries meaning;
  downscale, crop, retrieve.
- **Measure accuracy on your documents**, not on a demo.

## Exercises

1. Re-render the fixture at half resolution and extract again (live mode). Which fields
   break first? What does that tell you about downscaling rules?
2. Add a cross-reference check: a list of known supplier names. What does your code do when
   the model reads a supplier that is not on the list?
3. Design the pipeline for 10,000 invoices a day: where does OCR sit, where does the model
   sit, what is verified where, and what goes to a human?
4. Your team wants to send full PDFs of 40-page contracts to the model "so it has all the
   context". Using Lesson 2.5 and this lesson, write the two-paragraph response.

## Model answers (sketch)

1. Small print and decimals go first — pick a floor resolution from where your own
   documents start failing, not from a guess.
2. Flag and route to a human; never "correct" the supplier name by nearest match without
   a review step.
3. OCR/layout model → text + bounding boxes → LLM extracts into schema → code verifies
   arithmetic/format/cross-refs → human queue for failures; sample successes for QA.
4. Pages as images are huge in tokens and the middle gets lost; use the text layer, chunk,
   retrieve the clauses that matter, and send images only for signatures/tables where layout
   matters.
