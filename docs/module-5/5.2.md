## The one idea

Lesson 2.1's loop produces one token per trip. A 300-token answer is 300 trips, and at
typical generation speeds that is several seconds. You can wait for all of it, or you can
**send each piece as it is produced**:

```diagram
streaming-timeline
```

Total time is the same. What changes is *which* latency the user experiences: the gap
before the first token (**time to first token, TTFT** — roughly, how long the prompt takes
to process) instead of the gap before the last. For anything a human is watching, that gap
is the product.

## What a stream actually looks like

```code
consume
```

```output
chunks
```

The chunk boundaries above are real — the cassette stores them — and they are not words,
sentences or tokens of any fixed size. Sometimes a chunk is a word, sometimes a fragment,
sometimes several words. **Never assume chunk boundaries mean anything.** Accumulate, and
treat the concatenation as the text.

Under the hood this is usually server-sent events (SSE) over HTTP: a long-lived response
with one small event per chunk, plus a final event carrying the stop reason and usage. SDKs
hide that; the adapter's `stream()` yields plain text pieces and fills in the accounting at
the end.

## JSON that arrives in pieces

Structured output (Lesson 4.3) streams too — as a growing prefix of a JSON document. You
cannot parse a prefix.

```code
partial-json
```

```output
partial-json
```

Three honest options, in order of effort:

1. **Wait for the end**, then parse. Correct, simple; you lose the streaming benefit for
   that call — fine when the consumer is code, not a person.
2. **Try to parse after every chunk**, use the first success (the example). Cheap, correct,
   slightly wasteful; good enough for small objects.
3. **A partial-JSON parser** that yields fields as they close — what you want when a UI
   should fill in a form field by field.

What you must not do is parse on a boundary you assumed ("it'll close after the second
brace"). It will not, reliably.

```check
Your UI renders a streamed JSON object as soon as it "looks complete" by counting braces. What goes wrong?
- Nothing — brace counting is how parsers work
- * Braces inside strings, escaped characters and nested objects break the count; parse properly or use a partial-JSON parser
- Streaming JSON is not possible
why: Chunk boundaries and brace counts are not structure. Use a parser — full or partial — and only trust fields it has actually closed.
```

## Cancellation — and why it saves money

```code
cancel
```

```output
cancel
```

When the user navigates away, scrolls past, or clicks "stop", break out of the loop and let
the client close the connection. The model stops generating, and **you stop paying for
tokens nobody will read** — output tokens are the expensive ones (Lesson 5.5). Two
production details:

- Make sure the cancellation reaches the model. Breaking a loop in the browser does nothing
  if your backend keeps reading the stream; propagate the abort (`AbortSignal`, cancelled
  task) all the way down.
- Streams can fail mid-way: a network blip, a rate limit on the next chunk, a content
  filter. Your consumer must handle "I have half an answer and an error" — show the partial
  text with a marker, or retry from scratch, but decide.

## Where streaming fits — and where it does not

```output
takeaway
```

| Use streaming when | Skip it when |
|---|---|
| a person is waiting and the answer is more than a sentence | the consumer is code (classification, extraction, routing) |
| the answer is long and the UI can render progressively | you need the whole output validated before anything is shown |
| you want cancel-to-save | requests are batched or asynchronous (Lesson 5.5) |

And one operational note you will meet in Module 9: **your gateway must stream too.** A
proxy that buffers the whole response before forwarding turns every streamed answer back
into a spinner.

```check
You stream a 1,200-token answer and the user clicks "stop" after 200. What has to be true for you to stop paying?
- * The abort propagates to the upstream request so the model stops generating
- Nothing — streaming is billed per chunk shown
- The user must refresh the page
why: Cancellation saves output tokens only if the connection to the model is actually closed — at every hop.
```

## What a senior engineer should take from this

- **Stream for humans; don't for code.** TTFT is the latency people feel.
- **Accumulate; never assume chunk boundaries.** Parse JSON only when complete, or with a
  partial parser.
- **Cancel all the way down** — it is a cost control, not just UX.
- **Handle the half-answer-plus-error case** explicitly; it will happen.

## Model answers (sketch)

1. Typically first chunk < 1 s, last several seconds — the ratio grows with output length;
   a longer prompt raises TTFT (prompt processing) but not the per-token rate.
2. idle (button) → streaming (text grows, stop button) → done (final, actions enabled) /
   cancelled (partial text marked, "stopped") / failed (partial text + error, retry).
3. Browser aborts fetch → server detects client disconnect → cancels the upstream request
   (abort signal / task cancel) → model stops. Any hop that swallows the abort keeps paying.
4. A long form being filled from a document: users see fields populate as the model reaches
   them; worth the parser. For short objects consumed by code, don't stream.
