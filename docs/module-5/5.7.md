## The one idea

Every incident review for an LLM feature starts with the same question: **what did the model
actually receive, and what did it actually say?** If the answer is "we don't log that", the
review ends in guesses. So the first thing to wire — before the second prompt, before the
launch — is a trace per request with a span per model call.

## The span

```code
span
```

That is the minimum. Field by field:

| Field | Why |
|---|---|
| `trace_id`, `step` | tie the call to the request and to its place in the pipeline |
| `prompt_id`, `prompt_hash` | *which* prompt version, exactly (Lesson 4.4) — a hash you did not deploy is an alert |
| `model` | the version that answered — vendors change it under you (Lesson 9.8) |
| `input_tokens`, `output_tokens`, `cost` | the bill, per call; output tokens are the expensive ones |
| `stop_reason` | `max_tokens` means truncated; `tool_use` means a round trip; neither is an error code |
| `validated` | did the output pass your checks — **the number you alert on** |
| `output_preview` | redacted, short; enough to recognise a failure class in a log |
| latency | missing here because replay has none; first column in production (Lesson 9.3) |

Add tokens *per part* (system / history / retrieved / answer, Lesson 2.5) when the prompt
is assembled, and cache hit counts (Lesson 5.5) from the usage fields.

Two model steps, one trace, every line machine-readable. The `validated` field is computed
by *your* validator — the schema check, the allow-list, the "did it promise a refund" rule —
because **"the API returned 200" tells you nothing about whether the feature worked.**

```check
Your LLM feature's error rate is 0.1% and users are complaining. What is the first metric to look at?
- Error rate by vendor status code
- * Validation-pass rate per prompt id — the model can answer "successfully" and still be useless
- CPU on the API servers
why: HTTP success is not feature success. Only your validator knows whether the output was usable; aggregate that per prompt version and model.
```

## What to aggregate, what to alert on

```output
aggregate
```

Dashboards that earn their place:

- **Validation-pass rate** per prompt id × model — the headline quality metric between evals.
- **Tokens per part** and **cost per request** (p50/p95) per feature and per tenant — drift
  here is the early warning for the bill (Lesson 5.6).
- **Latency**: time to first token and total, p50/p95 (Lesson 9.3).
- **Cache hit rate** (Lesson 5.5) and **stop_reason = max_tokens** rate (truncation).
- **Prompt hashes in use** — one you did not deploy means an unreviewed change.

Alerts: validation-pass rate drops by X points; cost per request p95 jumps; truncation rate
rises; an unknown prompt hash appears; vendor error rate rises. Each maps to one first
action, which is what makes it an alert and not a graph.

## Redact before it lands

```code
redact
```

```output
redaction
```

Prompts contain whatever users typed: emails, card numbers, names, medical details. Logs and
traces have longer retention and wider access than the request did. So: strip the obvious
PII before the span is written; store a **preview**, not the whole text; and if you need raw
prompts and outputs for debugging or evals, keep them in a separate store with short
retention and access control (Lesson 9.6). The model saw the card number; your logging
system should not.

```check
Where should the raw prompt and full model output live, if anywhere?
- In the application log with everything else
- * In a separate short-retention store with access control; the trace holds a redacted preview
- Nowhere — never keep them
why: Logs have long retention and wide access. Keep a preview in the span; raw text, when needed for debugging or evals, in a controlled store.
```

## What a senior engineer should take from this

- **One span per model call**: versions, tokens, cost, stop reason, validated, preview.
  Latency first in production.
- **Validation-pass rate is the quality metric between evals.** HTTP 200 is not success.
- **Alerts map to actions**: pass rate, cost p95, truncation, unknown prompt hash.
- **Redact before logging; raw text in a short-retention, access-controlled store.**

## Exercises

1. Add latency to the span (live mode) and print p50/p95 over ten runs of the classify step.
   How much of the variance is the model versus the network?
2. Extend `redact` for phone numbers and names from a known customer list. What is the
   false-positive cost of an over-eager redactor, and how would you measure it?
3. Design the "unknown prompt hash" alert end to end: where does the set of deployed hashes
   come from, and what does on-call do?
4. You have spans for every call. Write the query that answers "which prompt version is
   producing the most `max_tokens` stops this week, and what did those outputs look like?"

## Model answers (sketch)

1. Mostly model (generation) for long outputs, mostly network/TTFT for short ones; separate
   the two and you know which to optimise.
2. Over-redaction hides the detail you debug with; measure on a labelled sample and tune
   patterns per field type.
3. The prompt registry (Lesson 4.4) publishes the deployed set; the alert fires on any span
   whose hash is not in it; on-call finds who changed what, reverts or registers it.
4. Group spans by `prompt_id`, filter `stop_reason = 'max_tokens'`, count, join previews —
   then raise `max_tokens` or shorten the prompt for that version.
