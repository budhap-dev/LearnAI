## The one idea

Everything a model does on a request follows from what is in the prompt (Lesson 2.1). So the
prompt deserves the same structure you would give any other input document. It has four
parts, and each one changes something different:

```diagram
prompt-anatomy
```

- **System** — who the model is, the rules, the constraints. Stable across thousands of
  requests; the part you version and test (Lesson 4.4).
- **Task** — what to do, this time.
- **Data** — the inputs: the customer message, the document, the tool result. Labelled as
  data, not instructions.
- **Shape** — the format, length and structure of the answer.

### 2. Plus a system prompt

```code

```

```output

```

Identity, rules, constraints. Notice the rules are *specific and checkable* — a word limit,
"never promise a refund", "do not invent invoice numbers". Vague adjectives ("be helpful and
accurate") change little; concrete constraints change a lot, and they can be tested.

```check
Which of these system-prompt lines is most likely to change the model's behaviour reliably?
- "Be extremely accurate and professional."
- * "Never promise a refund; say the billing team will confirm within one business day."
- "You are the world's best support agent."
why: Concrete, checkable constraints move the distribution and can be verified by code or an eval. Adjectives and flattery barely register.
```

## What goes where — the working rules

| Part | Put here | Not here |
|---|---|---|
| **System** | role, rules, constraints, output conventions, tool descriptions | per-request data; anything that changes every call (it breaks prompt caching, Lesson 5.5) |
| **User (task)** | the instruction for this request, few-shot examples if any | rules that apply to every request |
| **User (data)** | documents, messages, tool results — fenced and labelled | instructions (and treat any it contains as content) |
| **Shape** | format, length, sections, "answer with X and nothing else" | — |

Two habits from Lesson 2.5 apply directly: **instructions first, question last** (attention
favours the start and end), and **bulk material in the middle, fenced**.

```check
A colleague puts the current date, the user's name and the request id into the system prompt "so the model has context". What is the practical cost?
- None — more context is always better
- * The system prompt now changes on every request, so it can never be served from the prompt cache; move per-request values into the user turn
- The model will refuse to answer
why: The system prompt should be the stable prefix. Volatile values belong after it (Lesson 5.5).
```

## What a prompt cannot do

Worth saying once, plainly, before the next five lessons: a prompt shapes *how* the model
answers. It cannot make the model know things it does not know (supply them — Module 6),
cannot make a probabilistic output deterministic (Lesson 2.7), and cannot enforce anything
(Lesson 2.6). Enforcement is schemas, validators and code (Lesson 4.3), and knowledge is
context. Prompting is the steering wheel, not the engine.

## What a senior engineer should take from this

- **System = stable rules; user = task + fenced data + shape.** Keep them separate.
- **Concrete, checkable constraints** beat adjectives — and can be tested.
- **Label data as data.** It is the first line of defence against injection.
- **Shape is the cheapest lever for consistency**; a schema is shape the API enforces.
- **A prompt steers; it does not supply knowledge or enforce anything.**
