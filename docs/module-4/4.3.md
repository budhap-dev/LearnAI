## The one idea

The moment a model's output feeds code — a database write, a routing decision, an API call —
free text becomes a liability: it must be parsed, and parsing prose is where LLM systems
break. The fix has two layers, and both are needed:

```diagram
schema-validate-retry
```

1. **Shape** — request output that conforms to a JSON schema. Modern APIs can *constrain*
   generation to the schema, so what comes back is guaranteed valid JSON with the right keys,
   types and enum values.
2. **Values** — code checks what the schema cannot: is the date real and in the future, does
   this combination make sense, is the text usable? A schema-valid answer can still be wrong.

And a third element that is really part of the shape: a first-class way for the model to say
**not found**, so it does not invent a ticket to be helpful (Lesson 2.6).

## The schema

```code
schema
```

Three decisions in that schema carry most of the value:

- **`additionalProperties: false` + `required`** — strict: no surprise keys, no missing ones.
- **Enums** for every field with a known vocabulary — `category`, `urgency`, `status`.
  Constrained choice (Lesson 4.2), enforced.
- **`status: found | not_found`** — the refusal path. Without it the model fills every field
  because the schema demands it.

`json.loads` / `JSON.parse` cannot fail: the API constrained the output to the schema. Every
key is present with the right type; every enum value is one of yours. That removes the whole
class of "the model wrapped the JSON in prose", "it added a trailing comment", "it used
'Billing' instead of 'billing'".

## Validate the values in code

```code
validate
```

The schema said `requested_by_date` is a string or null. Code checks that the string is a
real ISO date and not in the past; that the summary has enough words to be useful; that
`not_found` and `high` urgency do not co-occur. Each check is small, deterministic and
testable — and each one is a bug you will otherwise meet in production.

## When validation fails: the policy

A failed check is a normal event, not an exception. Decide the policy up front:

| Failure | Policy |
|---|---|
| Value check fails on a recoverable field | **Retry once** with the failure fed back ("`requested_by_date` was in the past; re-extract or set null"). Cap retries at one or two — a third try rarely helps and doubles cost |
| `not_found` | Route to a human; do not create the record |
| Repeated failure | Escalate; log the input and output; never silently default |
| Schema request unsupported (older model, other vendor) | Fall back to "reply with JSON only" + parse + full validation + retry — the same loop with weaker guarantees |

Log every validation outcome. The rate of retries and rejections per field is one of the best
early signals that a prompt, a model version or the input distribution has changed (Lesson 8.4).

```check
An extraction returns status not_found for an email that clearly contains a request. What should code do?
- Override to found and create the ticket with best-guess fields
- * Route to a human (or retry once with a hint) — never fabricate a record; and count these misses in the eval
- Raise an exception and drop the email
why: The refusal path exists to be honoured. A wrong not_found is a recall problem to measure and fix in the prompt/eval loop, not a reason to invent data.
```

## Designing schemas that models fill well

- **Flat beats deep.** A handful of top-level fields extracts more reliably than nested
  objects three levels down. Decompose (Lesson 4.2) rather than nest.
- **Describe fields** in the schema (`description`) — the model reads them.
- **Prefer enums to free strings** wherever the set is known; add `other` when it is not
  closed.
- **Nullable with meaning**: `null` = "not stated" is different from `""` = "stated as empty".
  Say which in the description.
- **Do not put reasoning in the schema you will parse.** If you want the model to think, use
  a reasoning setting (Lesson 4.5) or a separate field you ignore in code.

## What a senior engineer should take from this

- **Two layers**: schema for shape (enforced by the API), code for values.
- **Enums, strict objects and a `not_found` path** are where the value is.
- **Validation failure is a normal event with a policy**: retry once with feedback, route or
  escalate; never default silently.
- **Flat schemas, described fields, decomposition over nesting.**

2. Usually yes for value slips (dates); rarely for genuine ambiguity — that is what
   `not_found` and humans are for.
3. Enums: none obvious (maybe `kind: call|meeting|other`); nullable: end, location; code
   checks start < end, plausible window, attendees resolve to known contacts.

   and enums yourself, retry with the parse error — the same loop, more failures to handle.
