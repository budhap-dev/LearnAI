## The one idea

Prompt "engineering" accumulated a folklore of tricks. Three of them are real, general, and
worth learning as patterns; the rest are variants or noise. The three:

```diagram
pattern-cards
```

1. **Few-shot** — show examples of the exact output instead of describing it.
2. **Decomposition** — two small asks in sequence beat one big ask.
3. **Constrained choice** — make the model pick from your labels, not invent its own.

What they have in common: each makes the output **easier to check**. That is the design goal
of every prompt that goes into a system (Lesson 4.3).

## Few-shot beats adjectives

```code
tickets
```

```code
zero-shot
```

```output
zero-shot
```

A reasonable answer — and an unpredictable format. Ask a thousand times and you get
"billing", "Billing issue", "payment problem", bullets, sentences, sometimes commentary.

```code
few-shot
```

```output
few-shot
```

Three examples did what a paragraph of adjectives could not: pinned the label vocabulary,
the line format, and the granularity. Examples communicate *distribution* — what typical
outputs look like — and a model is a distribution machine.

```check
Your classifier prompt says "return the category as a short lowercase label". Outputs vary: "billing", "billing-issue", "Billing". Best fix?
- Add "please be consistent" to the prompt
- * List the allowed labels explicitly and show two or three worked examples in exactly the output format
- Raise the temperature
why: A constrained vocabulary plus few-shot examples pins format and labels; adjectives about consistency do not. A schema with an enum (Lesson 4.3) makes it enforceable.
```

Practical rules for few-shot:
- **Three to five examples**, covering the boring case and the edge cases you care about.
- **Exact output format** in the examples — the model copies format even more faithfully
  than content.
- **Balance the classes** shown, or the model leans toward the ones it saw.
- Examples are tokens; keep them in the stable prefix (Lesson 5.5) and count them (Lesson 2.5).

## Decomposition: two small asks beat one big ask

```code
decomposition
```

```output
one-big-ask
```

Category, urgency, reply and summary in one prompt: each job dilutes the others, and if the
category is wrong it is buried in a wall of text nobody checks.

```output
two-small-asks
```

Step one extracts the facts in a fixed shape; step two writes the reply *from those facts*.
Now the facts can be checked (and, in Lesson 4.3, schema-enforced) before anything customer-
facing is written; each step can use a different model, budget or effort; and a wrong reply
traces to a specific step. The pattern generalises: extract → decide → act; retrieve →
answer → cite; draft → critique → revise (Lesson 7.1).

```check
A single prompt asks the model to read a contract, extract the parties and dates, assess risk, and draft an email to legal. Reviews find the dates are often wrong. First move?
- Ask for more careful reading in the prompt
- * Split it: one call extracts parties and dates into a schema that code validates; later steps consume the validated facts
- Use a larger model for the whole thing
why: Decomposition makes each step small and checkable; a validated extraction step stops date errors from ever reaching the email.
```

## Constrained choice

Whenever the answer is one of a known set — labels, routes, tools, yes/no — say so, list the
set, and (in Lesson 4.3) enforce it with an enum. Free text where a choice was needed is the
single most common source of parsing bugs in LLM systems.

## Folklore, sorted

| Technique | Verdict |
|---|---|
| "Think step by step" / chain of thought | Real for multi-step problems; modern reasoning modes do it better and cheaper (Lesson 4.5). Do not ask for reasoning in the *output* you will parse — ask for it separately or use a reasoning setting |
| Role prompting ("you are an expert…") | Mild; specific rules and examples matter far more (Lesson 4.1) |
| Emotional pressure, threats, tips | Noise; measured effects are tiny and unstable |
| "Reply in JSON" without a schema | Fragile — use structured output (Lesson 4.3) |
| Repeating instructions three times | A hack for a placement problem: put them first and last instead (Lesson 2.5) |
| Self-critique ("check your answer") | Real as a *second call* with the first answer as data — an evaluator step (Lesson 7.1, 8.3) |
| Long lists of "do not…" | Weak; each negative is a distraction. State the positive shape and validate |

## What a senior engineer should take from this

- **Few-shot pins format and vocabulary**; three to five examples, exact format, balanced.
- **Decompose**: small asks with checkable outputs, chained. Extract → decide → act.
- **Constrain the choice** whenever the answer is from a known set.
- **The goal is checkability**, not cleverness. If you cannot validate the output, restructure
  the prompt until you can.

## Exercises

1. Add a fourth ticket that is genuinely ambiguous (bug or how-to?). Does few-shot help? What
   would you add to the examples?
2. Take the "one big ask" and decompose it into three steps with a shape for each. Which
   steps could run on a smaller model?
3. Find one prompt in your codebase that asks for prose where a constrained choice would
   do. Rewrite it.

## Model answers (sketch)

1. Ambiguity needs a rule, not more examples: add an "if unclear, prefer X" instruction or an
   `unclear` label, and route those to a human.
2. Extract facts (small model, schema) → decide urgency/route (rules or small model) → draft
   reply (larger model, from facts). Only the last needs a strong writer.
3. Typical: "decide whether this needs escalation and explain" → `{escalate: bool, reason: enum}`.
