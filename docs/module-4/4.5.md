## The one idea

A next-token predictor answers immediately — the first tokens of the answer condition the
rest, so a wrong start is hard to recover from. **Reasoning modes** let the model produce
intermediate tokens first — working the problem — and only then answer. Those tokens are real
work: they improve results on multi-step problems, and they are billed as output and take
time. Newer APIs expose a dial (effort / thinking budget) rather than a switch:


The curve is the whole lesson: steep where the task needs steps, flat where it does not, and
always costing tokens along the x-axis.

## Where thinking pays, and where it does not

| Task | Thinking helps? | Why |
|---|---|---|
| Multi-constraint planning, scheduling, maths, tricky code | Usually yes | the answer depends on holding several steps together |
| Analysis with trade-offs, debugging from evidence | Often | intermediate conclusions feed later ones |
| Extraction, classification, routing | Rarely | the answer is in the input; shape and examples matter more |
| Summaries, rewrites, translations | Rarely | transforms of the input |
| Lookups | No | there is nothing to work out |
| Agentic loops with tools (Module 7) | Yes, in bursts | deciding *what to do next* is reasoning; formatting the tool call is not |

The honest way to fill this table for *your* tasks is the same as everywhere in this course:
run the golden set at two settings and compare accuracy, tokens and latency.

## How to use the dial

- **Set effort per prompt**, not per application. Different steps of a decomposed pipeline
  (Lesson 4.2) want different settings — extraction low, planning high.
- **Budget for it.** Thinking tokens count against `max_tokens` and against your context
  budget (Lesson 2.5); leave room or the answer is truncated.
- **Do not ask for the reasoning in the parsed output.** If you want to *see* it, use the
  API's option to return a summary; if you want it in your JSON, you are paying twice and
  parsing prose (Lesson 4.3).
- **Latency**: high effort can turn a one-second answer into many seconds. Stream where a
  person is waiting (Lesson 5.2), and set timeouts with fallbacks (Lesson 9.3).
- **Provider semantics differ**: some models think by default, some need it switched on, some
  reject sampler settings when thinking is on. Read the model reference before you tune.

## The limits — reasoning is still text

- It **conditions later text**; it does not consult an oracle. A wrong premise reasoned
  through carefully produces a confident wrong answer.
- It can **rationalise**: produce a plausible chain that does not reflect how the answer was
  reached. Treat visible reasoning as an aid to debugging, not as proof.
- It does not fix **exact search** over many possibilities, arithmetic at scale, or facts the
  model lacks — tools, code and retrieval do (Lesson 2.8).
- So: **verify the answer in code either way.** The example checks the puzzle answer against
  the known solution; production checks against schemas, tests and sources.

```check

why: More thinking raises the odds on multi-step problems; it is not a correctness guarantee. Checks against schemas, tests, sources or known answers remain necessary.
```

## What a senior engineer should take from this

- **Thinking tokens buy accuracy on multi-step problems and nothing on lookups**; they are
  billed as output and add latency.
- **Set effort per prompt; measure on the golden set** at two settings before choosing.
- **Budget the tokens; keep reasoning out of parsed output; stream when someone is waiting.**
- **Reasoning is text.** Verify answers in code regardless.

## Model answers (sketch)

1. Typically a jump from low → medium and little from medium → high; the last step costs the
   most tokens for the least gain — the flat part of the curve.
2. Extraction/classification steps usually show no accuracy change and a large token
   difference; planning/analysis steps show the opposite.
3. High for planning, analysis, code with tests to verify; low for extract/classify/route;
   change on eval evidence, re-checked when the model version changes.
