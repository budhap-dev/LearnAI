## The one idea

Lesson 3.5 said a model is an artefact with a version, stored with its metrics, logged with
every prediction. **A prompt is the same kind of thing.** It changes behaviour as much as a
model change does; it deserves the same lifecycle:

```diagram
prompt-lifecycle
```

Author → test against a golden set → version → deploy → log the id and hash with every
request → observe → change (new version, tested) → roll back if needed. Prompts pasted into
a string constant, edited by whoever noticed a problem, skip every one of those steps.

## A registry, not a string constant

```code
registry
```

Two versions of one prompt. Version 2 fixes a real defect in version 1: it never said what to
do with a question the policy does not cover, so the model would guess (Lesson 2.6). Notice
the fix is not "be more careful" — it is a **concrete, checkable behaviour** (`NOT_COVERED`) and
a fence around the data.

```code
render
```

Templates render from data. The hash of the rendered prompt travels with the request into
logs and traces: it groups traces by exact prompt, and it makes "someone edited the string
in production" visible as a hash that matches no version.

```check
Production answers changed on Tuesday and nobody deployed anything. What does the prompt hash in the traces let you do?
- Nothing — hashes are for caching
- * See that Tuesday's requests carry a hash matching no registered version, i.e. the prompt was edited outside the release process — or, if the hash is unchanged, rule the prompt out and look at the model version
- Automatically roll back
why: Versioned prompts plus a logged hash turn "something changed" into a diff.
```

## A golden set is a prompt's unit test

```code
golden
```

You cannot assert the exact answer (Lesson 2.7). You *can* assert properties: contains the
policy's number, says `NOT_COVERED` when it should, is under a length, matches a schema. Real
questions, real expectations, checked by code. This is Module 8's discipline in miniature.

Read the recording carefully — it did not go the way a tidy lesson would script it, and
that is the lesson. Version 2 **fixed** the case v1 failed (it now says `NOT_COVERED` for the
student-discount question instead of improvising) and **"failed"** the refund question that
v1 passed — because the checker looks for the literal phrase `14 days` and the model wrote
"the 14-day refund period". The answer is right; the checker is brittle. So the honest
reading is: v2 is better on behaviour, the golden set's checker needs fixing (accept
`14-day`, or check for the number and the unit separately), and a one-run 2/3 vs 2/3 tells you
to look, not to ship.

That is still the discipline working. The comparison is a number you can argue about, not a
feeling; the failure is *legible* (which case, which version, which hash); and the fix is a
one-line change to a checker, versioned like everything else. Keep both prompts in the
registry (rollback is a config change), fix the checker, re-run — and when the golden set is
this small, remember Lesson 2.7: run it several times and look at rates before trusting a
one-case difference.

```check
Version 2 of a prompt passes 3/3 golden cases; version 1 passed 2/3. A colleague says "so v2 is better". What is the honest caveat?
- None — 3/3 beats 2/3
- * With three cases and sampled outputs, run each several times and look at pass rates; grow the golden set from real traffic before treating the difference as settled
- Version numbers do not matter
why: Small golden sets and non-deterministic outputs make single runs noisy. The habit — measure, compare, then ship — is right; the confidence should scale with the evidence.
```

## The lifecycle, concretely

| Stage | What exists | Tool |
|---|---|---|
| Author | template with placeholders, an owner, a changelog line | the registry (a file, a table, a prompt-management service) |
| Test | golden set + property checks; run several times | your eval runner (Module 8) |
| Version | immutable id like `faq-answer@2` | registry |
| Deploy | which id is live per environment | config, not code edits |
| Observe | prompt id + hash + model version on every trace | tracing (Lesson 5.7) |
| Change | new version, same tests, compare | PR review of the diff |
| Roll back | point config at the previous id | config |

Where the registry lives is secondary — a JSON file in the repo is a fine start. That it
exists, has versions, and is the *only* place prompts come from is what matters.

## Who owns the prompt

The commonest organisational failure in Lesson 1.6 was "no owner". A prompt has an owner
the way a schema or an API contract has one: someone reviews changes, someone maintains the
golden set, someone is paged when the eval regresses. Prompts touched by product, support
and engineering without a review path drift until they break.

## What a senior engineer should take from this

- **Prompts are versioned artefacts** in a registry, rendered from data — never edited
  strings.
- **Log the prompt id and hash** with every request; incidents become diffs.
- **A golden set of property checks is a prompt's unit test**; compare versions by numbers.
- **Deploy by config, roll back by config; give the prompt an owner.**

## Exercises

1. Add a third golden case that version 2 fails (e.g. a question partially covered by the
   policy). Write version 3 and re-run.
2. Extend `render` to reject unknown placeholders and missing values at render time. Why is
   that worth failing loudly for?
3. Design the trace fields for one request in a system with a prompt registry: what would you
   need to answer "which prompt produced this answer and was it the tested one?"
4. Where would you store the registry in your organisation, and who owns `faq-answer`?

## Model answers (sketch)

1. Partial coverage usually needs a rule ("answer the covered part, say NOT_COVERED for the
   rest") — and a golden case that checks both halves.
2. A missing placeholder silently produces a prompt with `{policy}` literally in it; the model
   answers anyway. Fail at render, not in production.
3. `prompt_id`, `prompt_hash`, `model`, `model_version`, `index_version` (if RAG), plus tokens
   and finish reason; compare `prompt_hash` with the registry.
4. Anywhere reviewed and versioned; owner is whoever owns the feature's behaviour — and it
   should be a name, not a team.
